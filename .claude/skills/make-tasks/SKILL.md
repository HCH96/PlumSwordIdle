# 작업 만들기 (make-tasks)

사양을 작업 문서 여러 개로 쪼개 `tasks/todo/` 에 넣는다.

`tasks/todo/` 에 들어간 문서는 그 자체로 승인된 것이고, 루프 안의 에이전트는 사람에게 질문할 수 없다. 에이전트는 작업 문서와 거기 적힌 참고 문서만 보고 일한다. 이 대화에서 오간 말은 모른다. 그래서 **문서에 적히지 않은 것은 없는 것**이라고 생각하고 쓴다.

**작업 문서는 사람이 결과를 보기 전의 마지막 확인 지점이다.** 루프는 작업마다 테스트 → 관문(스크립트의 규칙 검사) → 교차 리뷰(구현하지 않은 쪽 에이전트)를 거치고, 묶음이 끝나면 사람에게 묻지 않고 통합 브랜치(`integration`)에 합친 뒤 다음 묶음으로 넘어간다. 사람은 todo 가 다 빈 뒤에 증거(`docs/evidence/`)를 한 번에 보고 main 에 올린다 (`docs/dev/loop.md`). 교차 리뷰어도 **이 문서의 완료 조건을 기준으로** 테스트가 충분한지 판정하므로, 완료 조건이 흐리면 리뷰도 흐려진다.

공통 실행 기준은 `docs/dev/workflow.md`를 먼저 읽는다. 이 본문과 템플릿이 Claude/Codex의 공통 원본이다. 아래 도구 이름(Read, AskUserQuestion 등)은 현재 환경의 파일 읽기·질문 도구로 대응하고, 질문 도구가 없으면 일반 대화로 묻는다. 기존 답변과 명시적 승인은 이어서 적용한다.

## 지킬 것

- 승인받기 전에는 `tasks/` 에 아무것도 쓰지 않는다. 초안은 `tasks/` 밖의 임시 폴더에 쓴다.
- 쓰는 곳은 `tasks/todo/` 뿐이다. 다른 폴더(wait, doing, blocked, done)의 문서는 옮기지도 고치지도 않는다. 이미 `todo` 에 있는 문서도 고치지 않는다.
- `docs/`, `tools/loop/`, 코드는 고치지 않는다. 커밋·푸시도 하지 않는다 (사용자가 따로 시키면 그때 한다).
- `tasks/` 는 깃에서 제외된 로컬 상태판이다. 항상 **프로젝트 폴더(main)의 `tasks/`** 를 쓴다. 루프 worktree(`../PlumSwordIdle_loop`)의 것은 쓰지 않는다.

## 순서

### 1. 읽는다

먼저 main과 integration의 SHA를 고정한다. 아래 `<통합 SHA>`는 그 값이다 (integration이 없으면 main). 참고한 SHA를 제안에 적고, todo에 넣기 직전에 검사기를 다시 실행한다.

1. 입력: 사용자가 가리킨 사양 문서(`docs/spec/<기능>.md`). 없으면 대화 내용.
2. `docs/index.md`, `docs/dev/task_template.md`, `docs/dev/architecture.md`.
3. 색인에서 이 기능과 관련된 공용 문서. 이 기능이 다른 기능의 연결 지점을 쓰면 그 기능의 사양 문서(`docs/spec/<그 기능>.md`)의 "연결 지점" 절.
4. 이 기능이 기대는 코드가 실제로 있는지: `Assets/Scripts/Core/`, `Assets/Scripts/Game/`, `Assets/Tests/` 의 폴더와 공개 타입.
5. 지금 `tasks/` 다섯 폴더와 `docs/history/` 에 있는 문서 이름 (겹치는 작업이 없는지, 선행 작업으로 가리킬 것이 있는지). 통합 브랜치에 합쳐졌지만 아직 main 에 올리지 않은 작업의 기록은 프로젝트 폴더에 없다. `git ls-tree -r --name-only <통합 SHA> -- docs/history/` 로 본다 (3·6단계의 스크립트는 이것까지 본다).
6. 이 기능이 기대는 코드가 통합 브랜치에만 있을 수 있다 (아직 main 에 올리지 않은 루프가 만든 것). 프로젝트 폴더에 없으면 `git show <통합 SHA>:<경로>` 로 확인한다. 루프는 통합 브랜치에서 일하므로 거기 있으면 쓸 수 있다.
7. **고친 사양인지 본다.** 이 사양으로 이미 구현된 작업이 있으면(`docs/history/`(main 과 통합 브랜치)나 `tasks/` 의 문서가 참고 문서에 이 사양을 적었으면) 고친 사양이다. 아래 "고친 사양에서 만들 것"을 따른다.

#### 고친 사양에서 만들 것

고친 사양에는 이미 구현된 규칙과 새로 구현할 규칙이 섞여 있다. **이번에 바뀐 것만 작업으로 만든다.** 이미 구현된 규칙을 다시 작업으로 만들면 같은 코드를 두 번 쓰거나, 있던 테스트와 겹치는 테스트를 만들게 된다.

1. **바뀐 것을 찾는다.**
   - 사양 끝에 `## 변경 기록`이 있으면 그것이 기준이다. 항목마다 "바뀐 뒤"가 `<통합 SHA>`의 코드·테스트에 이미 들어 있는지 본다. 들어 있지 않은 항목이 이번에 만들 범위다 (보통 마지막 항목 하나). 항목의 "바뀌기 전 → 바뀐 뒤"가 `git diff <기준 커밋> -- docs/spec/<기능>.md` 와 맞는지도 본다. 다르면 사용자에게 알린다.
   - 변경 기록이 없으면(이 규칙 전에 고친 사양) 직접 만든다: `git log --format="%h %ad %s" --date=short -- docs/spec/<기능>.md` 로 이 사양으로 마지막 작업이 끝난 뒤의 커밋을 찾고, 그 커밋부터 지금까지의 diff(커밋되지 않은 변경 포함)를 본다. 그 diff 를 "바뀌기 전 → 바뀐 뒤" 표, 새로 생기거나 바뀐 완료 조건 번호, 바뀌는 연결 지점으로 정리해 7단계 목록에 함께 보여 준다. 사람이 이 정리를 확인해야 한다.
2. **기존 테스트를 찾는다.** 바뀌는 공개 타입·메서드를 `git grep <이름> <통합 SHA> -- Assets/Tests/` 로 찾아, 바뀐 규칙에서 기대값이 바뀌거나 성립하지 않게 되는 테스트를 메서드 이름까지 모은다. 변경 기록의 "기존 테스트" 표가 있으면 그것과 맞춰 보고, 빠진 것이 있으면 사용자에게 알린다.
3. **작업 범위.** 변경 기록에서 "새로"·"바뀜"인 완료 조건과 고쳐야 할 기존 코드만 작업으로 만든다. "그대로"인 완료 조건은 옮기지 않는다. 다만 바뀐 연결 지점을 쓰는 기존 코드(예: 화면 코드)는 같은 작업이나 바로 뒤 작업에서 고치게 해서 컴파일이 깨진 채 합쳐지지 않게 한다.
4. **기존 테스트는 요구사항에 하나씩 적는다.** "`<테스트 클래스>.<메서드>`: 이름은 그대로 두고, 기대값을 A 에서 B 로 바꾼다. 검사 수는 줄이지 않는다." 관문은 있던 테스트 메서드가 사라지거나(지움·이름 바꿈) 검사 수가 줄면 예외 없이 합치지 않는다. 그래서 성립하지 않게 되는 테스트도 지우라고 쓰지 않는다. 이름을 그대로 둘 수 없는 테스트(사양에 처리가 "사람이 이름을 바꾼다"로 적혔거나 처리가 없음)가 있으면 작업 문서를 만들기 전에 사용자에게 알리고 멈춘다. 이름 바꾸기는 사람이 대화에서 먼저 해 커밋한다.
5. 참고 문서에는 사양 문서를 그대로 적고, 요구사항 첫 줄에 "이 사양의 `## 변경 기록` `<날짜> — <요약>` 항목만 구현한다. 그 밖의 규칙은 이미 구현되어 있다."를 적는다. 루프 에이전트가 사양 전체를 다시 구현하지 않게 하려는 것이다.

### 2. 구멍을 찾는다

아래 중 하나라도 사양에서 답을 찾을 수 없으면 **작업 문서를 만들지 않는다.** 한두 가지면 사용자에게 바로 묻고, 여러 가지거나 기능의 뼈대가 안 정해졌으면 `plan-feature` 스킬을 먼저 쓰라고 안내한다.

- 수치와 공식: 시작값, 올라가는 양, 비용, 상한. (임시값이어도 된다. 다만 숫자가 적혀 있어야 한다)
- 경계 상황: 재화가 모자랄 때, 최대 단계일 때, 0이나 음수가 들어올 때 무슨 일이 일어나는가.
- 다른 기능과 만나는 곳: 이 기능이 내놓는 연결 지점이 사양 문서의 "연결 지점" 절에 타입 이름과 메서드 모양까지 적혀 있는가. 이 기능이 쓰는 다른 기능의 연결 지점이 그 기능의 사양 문서와 코드에 이미 있는가. 없으면 누가 만드는가 (이번에 같이 만들지, 다른 작업을 기다릴지).
- 화면: 무엇을 어디에 보여 주고, 무엇을 누르면 무슨 일이 일어나는가.
- 범위: 저장, 오프라인 보상처럼 걸쳐 있는 것 중 이번에 하지 않는 것.

사소한 것(이름, 폴더, 메시지 글귀)은 묻지 말고 직접 정해 요구사항에 적는다. 정한 것은 5단계 목록에서 "내가 정한 것"으로 알린다.

**새로 작성한 사양은 main 에, 기존 구현이 만든 사양은 integration 에 커밋되어 있는지 확인한다.** 루프는 별도 worktree 에서 일하고, 새 루프를 시작할 때마다 main 의 새 커밋을 통합 브랜치에 합쳐 가져간다. 그래서 커밋되지 않은 문서는 에이전트가 읽지 못한다. (푸시는 필요 없다. 새 사양은 로컬 main 에 커밋되어 있으면 된다) `git status --short docs/` 로 보고, 커밋되지 않았으면 사용자에게 알린다 (직접 커밋하지 않는다). 사양 문서 없이 대화만으로 만들 때는 필요한 내용을 전부 요구사항 칸에 옮겨 적는다.

같은 묶음의 루프가 이미 진행 중이면 새 main 사양은 아직 들어 있지 않을 수 있다. 검사기가 이를 지적하면 다른 새 묶음으로 분리해 다음 루프의 동기화 뒤에 실행되게 한다. `tasks/done/`만으로 선행 작업 완료를 판단하지 않는다.

### 3. 번호를 정한다

```
python tools/skills/check_tasks.py --next-number
```

`tasks/` 다섯 폴더와 `docs/history/`(main 과 통합 브랜치)의 모든 문서 번호 중 가장 큰 값의 다음 번호가 나온다. 거기서부터 하나씩 올려 쓴다. 빈 번호를 채워 넣지 않는다.

- 파일 이름: `번호_짧은영문이름.md`. 번호는 세 자리(`007`), 이름은 영문 소문자·숫자·밑줄 (예: `007_stat_upgrade_cost.md`). 이 이름이 브랜치 이름(`task/007_stat_upgrade_cost`)이 된다.
- 먼저 해야 하는 작업에 작은 번호를 준다. 루프는 번호가 작은 것부터 꺼낸다.

### 4. 쪼갠다

**크기.** 작업 하나는 에이전트 실행 한 번(시간 제한 60분)에 끝나야 한다. 이 시간에 문서 읽기, 구현, 테스트 작성, 유니티 테스트 실행, 공용 문서 갱신, 보고서가 다 들어간다. 대략 이 정도가 한 작업이다.

- 공개 타입 한두 개(많아야 서너 개)와 그 테스트
- 완료 조건 3~8개
- 넘치면 쪼갠다. "A 하고 B 도 한다"로 읽히는 목표는 두 작업이다.

**순서.**

1. 연결 지점(인터페이스)을 정하는 작업을 맨 앞에 둔다. 여러 작업이 함께 쓰는 타입과 메서드가 여기서 정해진다.
2. 그것을 쓰는 작업은 선행 작업 칸에 그 문서를 적는다.
3. 로직(`PlumSword.Core`)과 화면(`PlumSword.Game`)은 가능하면 다른 작업으로 나눈다. 화면 작업은 로직 작업을 선행 작업으로 가리킨다.
4. 화면에 보여 줄 글자, 버튼을 누를 수 있는지 같은 **표시 판단은 Core 의 표시용 클래스**로 빼서 로직 작업으로 만든다. 그러면 에딧 모드 테스트로 판정할 수 있고, 화면 작업에는 "그리기와 입력 전달"만 남는다.

**연결 지점의 원본은 사양 문서다.** 연결 지점은 그 기능의 사양 문서(`docs/spec/<기능>.md`)의 "연결 지점" 절에 적혀 있고, 그것이 원본이다. 연결 지점 문서를 따로 만들지 않는다.

- 연결 지점을 정하는(구현하는) 작업의 요구사항에는 사양의 "연결 지점" 절에 있는 타입 이름, 메서드 모양, 네임스페이스를 그대로 옮겨 적는다 (예: `bool TrySpend(double amount)`). 그리고 이 요구사항을 넣는다: "구현하다 모양이 사양과 달라지면 사양 문서의 연결 지점 절을 고치고 보고서의 가정에 적는다."
- 그것을 쓰는 작업 문서에도 같은 이름을 적는다. 두 문서를 같은 자리에서 쓰기 때문에 가능한 일이고, 이렇게 해야 뒤 작업의 에이전트가 앞 작업 결과를 추측하지 않는다.
- 다른 기능의 연결 지점을 쓰는 작업은 **그 기능의 사양 문서**를 참고 문서에 넣는다 (예: 강화 작업이 재화를 쓰면 `docs/spec/currency.md`).

**없는 것에 기대지 않는다.** 이 기능이 쓰는 다른 기능(예: 강화가 쓰는 재화)이 코드에도, `tasks/` 에도, `docs/history/` 에도 없으면 그냥 있다고 치고 쓰지 않는다. 그 연결 지점을 만드는 작업을 이번에 맨 앞에 넣을지, 그 기능의 작업이 만들어질 때까지 미룰지 사용자에게 묻는다. 앞 기능이 없어 확인할 수 없는 것(예: 재화를 벌 방법이 없어 강화 버튼을 눌러 볼 수 없음)은 화면 작업의 요구사항에 임시 방편(예: 초기 잔액 1000)을 숫자로 적는다.

**묶음.** 함께 검증하고, 함께 합치고, 함께 되돌릴 단위가 묶음 하나다.

- 루프 하나는 묶음 하나만 처리한다. 묶음의 todo 가 비면 루프가 전체를 검증하고 통합 브랜치에 **병합 커밋 하나**로 합친 뒤, 사람을 기다리지 않고 다음 묶음을 시작한다. 묶음마다 증거 보고서 하나(`docs/evidence/<루프>/report.md`)와 태그 하나(`loop-merged/<루프>`)가 남는다.
- 그래서 묶음은 **되돌리기의 단위**다. 사람이 나중에 "이 묶음은 빼자"고 하면 그 병합 커밋 하나를 되돌린다. 묶음 안의 작업 하나만 골라 뺄 수는 없다. 마음에 안 들면 통째로 빼고 싶을 것끼리 묶는다.
- 묶음이 너무 크면(작업 열 개 이상) 하나가 잘못됐을 때 버리는 것이 많고 증거 보고서도 길어진다. 너무 작으면 화면 갈무리와 보고서가 잘게 흩어진다. 작업 3~8개가 알맞다.
- 한 묶음이 합치기 전 검증에서 떨어지면 그 묶음의 작업이 전부 보류로 간다. 서로 상관없는 작업을 한 묶음에 넣으면 남의 실패에 함께 끌려간다.
- 보통 기능 하나가 묶음 하나다. 묶음 이름은 띄어쓰기와 괄호가 없는 짧은 한 단어(한글·영문·숫자)로 하고, 같은 묶음의 문서는 **글자 하나까지 똑같이** 적는다 (`강화`와 `능력치강화`는 다른 묶음이다).
- 선행 작업이 다른 묶음에 있으면, 그 묶음이 검증을 통과해 통합 브랜치에 합쳐질 때까지 기다린다 (사람이 main 에 올릴 때까지가 아니다). 앞 묶음이 검증에서 떨어지거나 그 선행 작업이 보류되면 뒤 묶음의 그 작업은 답이 올 때까지 wait 에 머문다. 서로 기대는 작업은 같은 묶음에 넣는다.
- 여러 기능의 묶음을 한꺼번에 todo 에 쌓아도 된다. 루프는 번호가 가장 작은 문서의 묶음부터 차례로 처리한다.
- 앞 묶음에 작은 번호를 준다. 새 루프는 꺼낼 수 있는 문서 중 번호가 가장 작은 것의 묶음을 고른다.
- 이미 `tasks/` 에 있는 묶음에 이어 붙일 때는 그 문서의 묶음 이름을 그대로 쓴다.

### 5. 문서를 쓴다 (초안)

초안은 `tasks/` 밖의 임시 폴더에 쓴다 (세션의 임시 폴더, 없으면 운영체제의 임시 폴더 아래 새 폴더). 양식은 `docs/dev/task_template.md` 이고, 칸 제목 일곱 개는 글자와 순서를 바꾸지 않는다. 칸을 더하지도 않는다 (아래 "관문 예외"만 예외다).

```markdown
# 007_stat_upgrade_cost — 강화 비용 계산

## 목표
## 묶음
## 선행 작업
## 참고 문서
## 요구사항
## 완료 조건
## 하지 말 것
```

**목표.** 무엇을 만드는지 한두 줄. 어느 어셈블리(Core / Game)의 일인지 드러나게 쓴다.

**묶음.** 묶음 이름만 한 줄. 설명을 붙이지 않는다. 루프는 이 칸의 첫 줄 전체를 묶음 이름으로 읽는다.

**선행 작업.** 한 줄에 하나씩 `- 문서이름`. 없으면 `없음` 한 줄.

- **문서 이름 말고 아무것도 쓰지 않는다.** 설명, 괄호, 쉼표, 마침표, `.md` 를 붙이지 않는다. 루프는 이 칸의 글자를 그대로 이름으로 읽어서, `- 001_wallet (재화, 강화에 필요)` 라고 쓰면 `강화에`까지 선행 작업으로 읽고, `없음.` 은 `없음.` 이라는 문서를 기다린다. 이유를 남기고 싶으면 요구사항 칸에 쓴다.
- 실제로 있는 문서만 적는다: 이번에 함께 만드는 문서, 또는 `tasks/` 다섯 폴더나 `docs/history/` 에 있는 문서.
- 이 작업이 **직접** 쓰는 것만 적는다. A → B → C 라면 C 에는 B 만 적어도 된다. 다만 C 가 A 의 타입을 직접 쓰면 A 도 적는다.
- 순환이 없어야 한다. 번호가 작은 쪽만 가리키면 순환은 생기지 않는다.

**참고 문서.** 에이전트가 반드시 읽을 문서를 프로젝트 폴더 기준 경로로 적는다.

- `docs/index.md`, `docs/dev/architecture.md`, 해당 사양 문서(`docs/spec/<기능>.md`)는 항상 넣는다. 사양 문서가 길면 어느 장을 볼지도 적는다.
- 이 작업이 다른 기능의 연결 지점을 쓰면 그 기능의 사양 문서를 넣고, "연결 지점" 절을 보라고 적는다 (예: `- docs/spec/currency.md ("연결 지점" 절)`).
- **사람용 문서를 적지 않는다**: `docs/design/`(게임 기획 원본), `docs/project/`, `docs/archive/`. 구현하는 에이전트는 이 폴더를 읽지 않는다. 기획 문서에만 있고 사양에 없는 내용이 필요하면 요구사항 칸에 옮겨 적거나, 사양이 비어 있는 것이니 `plan-feature` 로 사양을 먼저 고친다.
- 없는 파일을 적지 않는다. 사양 문서 없이 만들 때는 빼고, 필요한 내용을 요구사항에 다 적는다.

**요구사항.** 구체적인 동작을 항목으로 적는다.

- 만들 것의 위치와 이름: 폴더, 네임스페이스, 타입 이름, 공개 메서드 모양. `docs/dev/architecture.md` 의 규칙(기능별 하위 폴더, 파일 하나에 공개 타입 하나)에 맞춘다.
- 수치는 숫자로, 공식은 식으로 적는다. 임시값이면 "(임시값)"이라고 붙인다.
- 경계 상황마다 무슨 일이 일어나는지 적는다.
- 선행 작업이 만든 것 중 무엇을 쓰는지 이름으로 적는다.
- Core 작업이면 시간·난수·저장을 어떻게 받는지 적는다 (`docs/dev/architecture.md` "순수 C# 규칙": 경과 시간과 현재 시각은 인자로, 난수는 주입).
- 대화에서 정한 결정은 여기에 옮겨 적는다. "앞에서 말한 대로" 같은 말은 에이전트에게 통하지 않는다.

**완료 조건.** 가장 중요한 칸이다. 루프는 에이전트가 끝났다고 하면 유니티 테스트 전체(에딧 모드와 플레이 모드)를 돌려 통과 여부를 보고, 관문이 "테스트가 필요한 조건이 있는데 새 테스트가 없다", "있던 테스트를 지우거나 검사를 줄였다"를 막고, 교차 리뷰어가 **조건마다 그것을 실제로 검사하는 테스트가 있는지** 표로 만든다. 그러니 완료 조건은 **에이전트가 테스트로 옮길 수 있고, 리뷰어가 테스트와 하나씩 짝지을 수 있는 문장**이어야 한다. 한 문장에 조건을 두 개 넣지 않는다.

- 문장 하나가 에딧 모드 테스트 하나(이상)가 되게 쓴다: "무엇을 주면(상황) 무엇이 나온다(기대 결과)". 숫자를 넣는다.
  - 좋음: `잔액 100에서 TrySpend(150)은 false 를 돌려주고 잔액은 100 그대로다.`
  - 나쁨: `재화 소비가 잘 동작한다.` / `비용이 적절히 오른다.` / `예외 상황을 처리한다.`
- 첫 항목은 테스트가 어디에 있는지다: `Assets/Tests/EditMode/<기능>/<대상>Tests.cs 에 아래 조건마다 테스트가 하나 이상 있고 모두 통과한다.`
- 마지막 항목은 `기존 테스트가 모두 통과한다.`
- 요구사항에 적은 경계 상황은 빠짐없이 완료 조건에도 있어야 한다.

화면 작업(`PlumSword.Game`)은 에딧 모드 테스트가 닿지 않는다 (테스트 어셈블리는 Core 만 참조한다). 무엇으로 판정할지 항목마다 앞에 표시를 붙여 적는다.

- `[테스트]` 표시용 판단을 Core 로 뺀 부분. 에딧 모드 테스트로 판정한다. (가능하면 앞선 로직 작업에서 이미 끝내 둔다)
- `[컴파일]` 화면 코드가 컴파일되고 기존 테스트가 모두 통과한다. 루프가 판정한다. 화면 작업에 항상 넣는다. 기존 테스트에는 플레이 모드의 `GameBootTests`(게임을 켜서 `[Game]` 이 조립되고 오류 로그가 없는지 본다)가 들어 있어, 조립 중에 예외가 나는 화면 코드는 여기서 걸린다.
- `[플레이 모드]` 실제 실행으로만 확인되는 것 중 기계로 볼 수 있는 것 (예: 실행하면 `[Game]` 아래에 `StatUpgradePanel` 오브젝트가 있고 버튼이 3개다). 플레이 모드 테스트 어셈블리(`Assets/Tests/PlayMode/` 의 `PlumSword.Game.Tests`)는 이미 있다. 테스트를 `Assets/Tests/PlayMode/<기능>/<대상>Tests.cs` 에 쓰라고 적고, 쓰는 법은 `docs/dev/architecture.md` "테스트" 절을 따르게 한다 (빈 씬에서 시작하므로 카메라가 필요하면 첫 씬을 불러온다). 플레이 모드 테스트는 에딧 모드보다 느리고 쓰기 어려우니, Core 의 표시용 클래스로 뺄 수 있는 판단은 `[테스트]` 로 한다.
- `[사람 확인]` 보기 좋은지, 위치가 맞는지처럼 기계가 판정할 수 없는 것. 루프는 이것을 판정하지 않는다. 루프가 묶음을 합칠 때 증거 보고서의 "사람이 볼 것"에 이 항목을 모으고, 게임을 실행해 찍은 **화면 갈무리(실행 후 1초·10초·30초)** 를 함께 남긴다. 사람은 main 에 올리기 전에 그것을 본다 (`review-loop`). 그래서 가능하면 **멈춘 화면 한 장으로 확인할 수 있게** 적는다 (예: `[사람 확인] 실행하고 10초 뒤 화면 아래쪽에 강화 버튼 3개가 겹치지 않고 보인다.`). 누르는 동작이나 움직임처럼 갈무리로 알 수 없는 것은 "에디터에서 ○○ 를 눌러 본다"처럼 무엇을 해 봐야 하는지 적는다. 에이전트는 이 항목을 보고서의 `### 사람이 확인할 것` 소제목 아래에 옮겨 적는다. 루프의 보고서 양식에 이 소제목이 정해져 있으므로 작업 문서에 따로 지시를 쓰지 않는다.

`[사람 확인]`만 있는 작업은 만들지 않는다. 적어도 `[컴파일]`은 있어야 한다.

**관문 예외** (선택 칸. 거의 쓰지 않는다). 관문은 어셈블리 정의, 씬·프리팹·에셋 파일, `ProjectSettings/`·`Packages/` 변경을 위반으로 보고 합치지 않는다. 작업이 정말로 그것을 바꿔야 할 때만 `## 하지 말 것` **바로 앞**에 이 칸을 두고 한 줄에 하나씩 적는다.

```markdown
## 관문 예외
- asmdef
```

| 이름 | 허용되는 변경 |
| --- | --- |
| `asmdef` | `.asmdef`, `.asmref`, `csc.rsp` |
| `scene` | `.unity`, `.prefab`, `.asset` |
| `settings` | `ProjectSettings/`, `Packages/` |

- 이 칸이 있으면 그 변경은 **사람의 확인 없이 합쳐진다.** 그러니 요구사항에 무엇을 왜 바꾸는지 구체적으로 적고, 7단계에서 사용자에게 따로 짚어 승인받는다.
- 루프 자체(`tools/loop/`, `CLAUDE.md`, `AGENTS.md`, `.claude/`, `docs/dev/loop.md` 등)와 사람용 문서를 바꾸는 예외는 없다. 그런 변경은 작업 문서로 만들지 않는다 (사람이 대화에서 직접 한다).
- 테스트를 지우거나 약하게 만드는 예외도 없다. 기존 테스트의 기대값을 바꿔야 하는 작업이면(사양이 바뀜), 요구사항에 "어느 테스트의 어느 기대값이 무엇에서 무엇으로 바뀐다"를 적는다. 검사 **수**를 줄이지 않고 값만 바꾸면 관문은 통과하고, 리뷰어가 요구사항과 맞는지 본다.

**하지 말 것.** 건드리면 안 되는 범위.

- 다른 기능의 내부 코드. 연결 지점(공개된 인터페이스)으로만 쓴다고 적고, 어느 폴더를 고치면 안 되는지 이름으로 적는다.
- 씬·프리팹·에셋 파일(`.unity`, `.prefab`, `.asset`). 화면은 코드로 조립한다.
- 새 어셈블리 정의, 어셈블리 정의 변경 (관문이 막는다. 꼭 필요하면 위 "관문 예외").
- 루프 자체와 그 문서: `tools/loop/`, `CLAUDE.md`, `AGENTS.md`, `.claude/`, `docs/dev/loop.md`, `docs/dev/task_template.md`, `docs/history/`, `docs/evidence/`. 관문이 예외 없이 막으므로 모든 작업에 적지 않아도 되지만, 작업이 그 근처(예: `docs/dev/architecture.md`)를 고칠 때는 어디까지인지 적는다.
- 루프의 증거용 갈무리 `Assets/Tests/PlayMode/Capture/`.
- 이번 작업 범위 밖의 것: 뒤 작업이 할 일(예: "화면은 만들지 않는다. 009 가 한다"), 이번 묶음에서 하지 않기로 한 것(예: 저장).
- Core 작업이면 `UnityEngine` 을 쓰지 않는다.
- 화면 작업이 `GameRoot` 에 조립 호출을 추가할 때는 "자기 기능의 줄만 추가하고 다른 기능의 줄은 고치지 않는다".

### 6. 검사한다

```
python tools/skills/check_tasks.py <초안 폴더>
```

이 스크립트는 루프 스크립트의 `Doc` 클래스로 초안을 직접 읽어, 루프가 읽게 될 묶음과 선행 작업을 보여 준다. 아무것도 쓰거나 옮기지 않는다. 확인하는 것: 파일 이름과 번호, 칸 제목(선택 칸 `관문 예외`의 위치와 이름 포함), 묶음·선행 작업 칸의 모양, 선행 작업이 실제로 있는지, 순환, 참고 문서가 있고 main 에 커밋되어 있는지, 완료 조건의 두루뭉술한 말. 관문 예외가 있으면 경고로 알려 준다 (7단계에서 사용자에게 짚는다).

- `[오류]`는 모두 고친다. `[경고]`는 하나씩 보고, 의도한 것이면 7단계에서 사용자에게 알린다.- 완료 조건의 숫자는 요구사항의 공식으로 직접 계산해 맞는지 본다 (예: 비용 `floor(10 × 1.15^3)` = 15). 틀린 기대값이 들어가면 에이전트가 재시도만 하다 보류된다.
- "루프가 읽은 내용"이 내가 의도한 묶음·선행 작업과 같은지 눈으로 확인한다.

스크립트가 못 보는 것은 직접 본다.

- 문서 하나만 읽고도 일을 시작할 수 있는가 (다른 초안이나 이 대화를 봐야 알 수 있는 내용이 없는가).
- 뒤 작업이 쓰는 타입·메서드 이름이 앞 작업 문서에 적힌 것과 글자까지 같은가.
- 요구사항의 경계 상황이 완료 조건에 다 있는가.
- 두 작업이 같은 파일을 만들거나 같은 일을 하지 않는가.
- 사양의 모든 항목이 어느 작업엔가 들어갔는가. 일부러 뺀 것은 무엇인가. 고친 사양이면 "사양의 모든 항목" 대신 이번 변경 기록 항목의 모든 줄(바뀐 절, 새로·바뀜 완료 조건, 고쳐야 할 코드, 기존 테스트 표)이다.
- 고친 사양이면, 기존 테스트 하나하나가 어느 작업의 요구사항에 "이름 유지, 기대값 A → B"로 적혔는가. 이미 구현된 규칙을 다시 만드는 작업이 없는가.
- 완료 조건 하나하나가 테스트 하나와 짝지어지는가 (리뷰어가 표로 만든다). 한 문장에 조건이 둘이면 나눈다.
- 묶음이 "통째로 되돌려도 되는 단위"인가. 서로 상관없는 작업이 한 묶음에 들어가 있지 않은가.
- `[사람 확인]` 항목이 화면 갈무리(1초·10초·30초의 멈춘 화면)로 볼 수 있는 것인지, 아니면 에디터에서 해 봐야 하는 것인지 문장에서 드러나는가.

### 7. 보여 주고 승인을 받는다

아래를 대화에 보여 준다.

1. **목록** (표): 번호, 이름, 묶음, 선행 작업, 한 줄 목표.
2. **내가 정한 것**: 사양에 없어 직접 정한 사소한 결정, 임시값.
3. **뺀 것**: 사양에 있지만 이번 작업들에 넣지 않은 것과 이유.
4. **남은 경고**: 검사 스크립트의 경고 중 의도한 것. 사양 문서가 커밋되지 않았으면 그것도. **관문 예외가 있는 문서는 반드시 따로 짚는다**: 어느 문서가 무엇을 바꾸는지, 그 변경이 사람 확인 없이 합쳐진다는 것.
5. **묶음과 합쳐지는 순서**: 묶음마다 어떤 작업이 들어가고 어느 순서로 처리되는지. 묶음 하나가 병합 커밋 하나이고 되돌리기의 단위라는 것. 이 묶음들이 끝나면 사람의 확인 없이 통합 브랜치에 합쳐지고, main 에 올리는 것은 사용자가 나중에 한다는 것.
6. **각 문서 전문**: 줄이지 않고 그대로.

그리고 "이대로 `tasks/todo/` 에 넣을까요?"라고 묻는다. 고쳐 달라는 말이 있으면 초안을 고치고 6단계 검사부터 다시 한다. **"넣어라"는 분명한 답이 있기 전에는 넣지 않는다.** 일부만 승인하면 그것만 넣되, 넣지 않는 문서를 선행 작업으로 가리키는 문서가 있으면 먼저 알린다.

### 8. 넣는다

승인된 문서를 **번호가 작은 것부터** `tasks/todo/` 에 쓴다. 루프가 돌고 있을 수 있어서다. 뒤 문서가 먼저 들어가면 루프가 "선행 작업이 아직 없음" 알림을 보낸다.

- 승인받은 초안과 글자 하나 다르지 않게 쓴다 (UTF-8).
- 같은 이름의 파일이 이미 있으면 덮어쓰지 않고 멈춘 뒤 알린다 (그 사이 번호가 쓰였을 수 있다. 3단계부터 다시 한다).
- 넣은 뒤 `tasks/todo/` 의 파일 목록을 보여 주고, 다음에 할 일을 알린다: 루프 실행은 `python tools/loop/run_loop.py` (todo 가 빌 때까지 묶음을 차례로 처리하고 끝난다. 계속 켜 두려면 `--watch`), 사양 문서가 커밋되지 않았으면 먼저 커밋. 다 끝나면 디스코드에 "모든 작업 끝: 확인할 차례"가 오고, 그때 `review-loop` 로 증거를 확인한 뒤 main 에 올리면 된다.
- 루프가 선행 작업이 남은 문서를 `tasks/wait/` 로 옮기는 것은 정상이다.

| 기존 테스트의 기대값이 바뀌는데 적지 않음 | 관문·리뷰가 "테스트를 구현에 맞춰 비틀었다"고 본다 | 요구사항에 어느 테스트의 값이 어떻게 바뀌는지 적는다 |

| 성립하지 않게 된 테스트를 지우라고 씀 | 관문이 "있던 테스트가 사라짐"으로 합치지 않는다 | 이름은 두고 기대값만 바꾸게 쓴다. 이름을 꼭 바꿔야 하면 사람이 먼저 한다 |
