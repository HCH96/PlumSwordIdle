# 작업 만들기 (make-tasks)

사양을 작업 문서 여러 개로 쪼개 `tasks/todo/` 에 넣는다.

`tasks/todo/` 에 들어간 문서는 그 자체로 승인된 것이고, 루프 안의 에이전트는 사람에게 질문할 수 없다. 에이전트는 작업 문서와 거기 적힌 참고 문서만 보고 일한다. 이 대화에서 오간 말은 모른다. 그래서 **문서에 적히지 않은 것은 없는 것**이라고 생각하고 쓴다.

## 지킬 것

- 승인받기 전에는 `tasks/` 에 아무것도 쓰지 않는다. 초안은 `tasks/` 밖의 임시 폴더에 쓴다.
- 쓰는 곳은 `tasks/todo/` 뿐이다. 다른 폴더(wait, doing, blocked, done)의 문서는 옮기지도 고치지도 않는다. 이미 `todo` 에 있는 문서도 고치지 않는다.
- `docs/`, `tools/loop/`, 코드는 고치지 않는다. 커밋·푸시도 하지 않는다 (사용자가 따로 시키면 그때 한다).
- `tasks/` 는 깃에서 제외된 로컬 상태판이다. 항상 **프로젝트 폴더(main)의 `tasks/`** 를 쓴다. 루프 worktree(`../PlumSwordIdle_loop`)의 것은 쓰지 않는다.

## 순서

### 1. 읽는다

1. 입력: 사용자가 가리킨 사양 문서(`docs/spec/<기능>.md`). 없으면 대화 내용.
2. `docs/index.md`, `docs/dev/task_template.md`, `docs/dev/architecture.md`.
3. 색인에서 이 기능과 관련된 공용 문서. 이 기능이 다른 기능의 연결 지점을 쓰면 그 기능의 사양 문서(`docs/spec/<그 기능>.md`)의 "연결 지점" 절.
4. 이 기능이 기대는 코드가 실제로 있는지: `Assets/Scripts/Core/`, `Assets/Scripts/Game/`, `Assets/Tests/` 의 폴더와 공개 타입.
5. 지금 `tasks/` 다섯 폴더와 `docs/history/` 에 있는 문서 이름 (겹치는 작업이 없는지, 선행 작업으로 가리킬 것이 있는지).

### 2. 구멍을 찾는다

아래 중 하나라도 사양에서 답을 찾을 수 없으면 **작업 문서를 만들지 않는다.** 한두 가지면 사용자에게 바로 묻고, 여러 가지거나 기능의 뼈대가 안 정해졌으면 `plan-feature` 스킬을 먼저 쓰라고 안내한다.

- 수치와 공식: 시작값, 올라가는 양, 비용, 상한. (임시값이어도 된다. 다만 숫자가 적혀 있어야 한다)
- 경계 상황: 재화가 모자랄 때, 최대 단계일 때, 0이나 음수가 들어올 때 무슨 일이 일어나는가.
- 다른 기능과 만나는 곳: 이 기능이 내놓는 연결 지점이 사양 문서의 "연결 지점" 절에 타입 이름과 메서드 모양까지 적혀 있는가. 이 기능이 쓰는 다른 기능의 연결 지점이 그 기능의 사양 문서와 코드에 이미 있는가. 없으면 누가 만드는가 (이번에 같이 만들지, 다른 작업을 기다릴지).
- 화면: 무엇을 어디에 보여 주고, 무엇을 누르면 무슨 일이 일어나는가.
- 범위: 저장, 오프라인 보상처럼 걸쳐 있는 것 중 이번에 하지 않는 것.

사소한 것(이름, 폴더, 메시지 글귀)은 묻지 말고 직접 정해 요구사항에 적는다. 정한 것은 5단계 목록에서 "내가 정한 것"으로 알린다.

**사양 문서가 main 에 커밋되어 있는지 확인한다.** 루프는 main 에서 딴 worktree 에서 일하므로, 커밋되지 않은 문서는 에이전트가 읽지 못한다. `git status --short docs/` 로 보고, 커밋되지 않았으면 사용자에게 알린다 (직접 커밋하지 않는다). 사양 문서 없이 대화만으로 만들 때는 필요한 내용을 전부 요구사항 칸에 옮겨 적는다.

### 3. 번호를 정한다

```
python .claude/skills/make-tasks/check_tasks.py --next-number
```

`tasks/` 다섯 폴더와 `docs/history/` 의 모든 문서 번호 중 가장 큰 값의 다음 번호가 나온다. 거기서부터 하나씩 올려 쓴다. 빈 번호를 채워 넣지 않는다.

- 파일 이름: `번호_짧은영문이름.md`. 번호는 세 자리(`007`), 이름은 영문 소문자·숫자·밑줄 (예: `007_stat_upgrade_cost.md`). 이 이름이 브랜치 이름(`task/007_stat_upgrade_cost`)이 된다.
- 먼저 해야 하는 작업에 작은 번호를 준다. 루프는 번호가 작은 것부터 꺼낸다.

### 4. 쪼갠다

**크기.** 작업 하나는 에이전트 실행 한 번(시간 제한 60분)에 끝나야 한다. 이 시간에 문서 읽기, 구현, 테스트 작성, 유니티 테스트 실행, 공용 문서 갱신, 보고서가 다 들어간다. 대략 이 정도가 한 작업이다.

- 공개 타입 한두 개(많아야 서너 개)와 그 테스트
- 완료 조건 3~8개
- 넘치면 쪼갠다. "A 하고 B 도 한다"로 읽히는 목표는 두 작업이다.

**순서.**

1. 연결 지점(인터페이스)을 정하는 작업을 맨 앞에 둔다. 여러 작업이 함께 쓰는 타입과 메서드가 여기서 정해진다.
2. 그것을 쓰는 작업은 선행 작업 칸에 그 문서를 적는다.
3. 로직(`PlumSword.Core`)과 화면(`PlumSword.Game`)은 가능하면 다른 작업으로 나눈다. 화면 작업은 로직 작업을 선행 작업으로 가리킨다.
4. 화면에 보여 줄 글자, 버튼을 누를 수 있는지 같은 **표시 판단은 Core 의 표시용 클래스**로 빼서 로직 작업으로 만든다. 그러면 에딧 모드 테스트로 판정할 수 있고, 화면 작업에는 "그리기와 입력 전달"만 남는다.

**연결 지점의 원본은 사양 문서다.** 연결 지점은 그 기능의 사양 문서(`docs/spec/<기능>.md`)의 "연결 지점" 절에 적혀 있고, 그것이 원본이다. 연결 지점 문서를 따로 만들지 않는다.

- 연결 지점을 정하는(구현하는) 작업의 요구사항에는 사양의 "연결 지점" 절에 있는 타입 이름, 메서드 모양, 네임스페이스를 그대로 옮겨 적는다 (예: `bool TrySpend(double amount)`). 그리고 이 요구사항을 넣는다: "구현하다 모양이 사양과 달라지면 사양 문서의 연결 지점 절을 고치고 보고서의 가정에 적는다."
- 그것을 쓰는 작업 문서에도 같은 이름을 적는다. 두 문서를 같은 자리에서 쓰기 때문에 가능한 일이고, 이렇게 해야 뒤 작업의 에이전트가 앞 작업 결과를 추측하지 않는다.
- 다른 기능의 연결 지점을 쓰는 작업은 **그 기능의 사양 문서**를 참고 문서에 넣는다 (예: 강화 작업이 재화를 쓰면 `docs/spec/currency.md`).

**없는 것에 기대지 않는다.** 이 기능이 쓰는 다른 기능(예: 강화가 쓰는 재화)이 코드에도, `tasks/` 에도, `docs/history/` 에도 없으면 그냥 있다고 치고 쓰지 않는다. 그 연결 지점을 만드는 작업을 이번에 맨 앞에 넣을지, 그 기능의 작업이 만들어질 때까지 미룰지 사용자에게 묻는다. 앞 기능이 없어 확인할 수 없는 것(예: 재화를 벌 방법이 없어 강화 버튼을 눌러 볼 수 없음)은 화면 작업의 요구사항에 임시 방편(예: 초기 잔액 1000)을 숫자로 적는다.

**묶음.** 사용자가 함께 확인하고 main 에 합칠 단위가 묶음 하나다.

- 루프 하나는 묶음 하나만 처리하고, 사람이 그 루프 브랜치를 main 에 합친 뒤에야 다음 묶음이 시작된다.
- 보통 기능 하나가 묶음 하나다. 묶음 이름은 띄어쓰기와 괄호가 없는 짧은 한 단어(한글·영문·숫자)로 하고, 같은 묶음의 문서는 **글자 하나까지 똑같이** 적는다 (`강화`와 `능력치강화`는 다른 묶음이다).
- 선행 작업이 다른 묶음에 있으면, 그 묶음이 main 에 합쳐질 때까지 기다린다. 서로 기대는 작업은 같은 묶음에 넣는다.
- 앞 묶음에 작은 번호를 준다. 새 루프는 꺼낼 수 있는 문서 중 번호가 가장 작은 것의 묶음을 고른다.
- 이미 `tasks/` 에 있는 묶음에 이어 붙일 때는 그 문서의 묶음 이름을 그대로 쓴다.

### 5. 문서를 쓴다 (초안)

초안은 `tasks/` 밖의 임시 폴더에 쓴다 (세션의 임시 폴더, 없으면 운영체제의 임시 폴더 아래 새 폴더). 양식은 `docs/dev/task_template.md` 이고, 칸 제목 일곱 개는 글자와 순서를 바꾸지 않는다. 칸을 더하지도 않는다.

```markdown
# 007_stat_upgrade_cost — 강화 비용 계산

## 목표
## 묶음
## 선행 작업
## 참고 문서
## 요구사항
## 완료 조건
## 하지 말 것
```

**목표.** 무엇을 만드는지 한두 줄. 어느 어셈블리(Core / Game)의 일인지 드러나게 쓴다.

**묶음.** 묶음 이름만 한 줄. 설명을 붙이지 않는다. 루프는 이 칸의 첫 줄 전체를 묶음 이름으로 읽는다.

**선행 작업.** 한 줄에 하나씩 `- 문서이름`. 없으면 `없음` 한 줄.

- **문서 이름 말고 아무것도 쓰지 않는다.** 설명, 괄호, 쉼표, 마침표, `.md` 를 붙이지 않는다. 루프는 이 칸의 글자를 그대로 이름으로 읽어서, `- 001_wallet (재화, 강화에 필요)` 라고 쓰면 `강화에`까지 선행 작업으로 읽고, `없음.` 은 `없음.` 이라는 문서를 기다린다. 이유를 남기고 싶으면 요구사항 칸에 쓴다.
- 실제로 있는 문서만 적는다: 이번에 함께 만드는 문서, 또는 `tasks/` 다섯 폴더나 `docs/history/` 에 있는 문서.
- 이 작업이 **직접** 쓰는 것만 적는다. A → B → C 라면 C 에는 B 만 적어도 된다. 다만 C 가 A 의 타입을 직접 쓰면 A 도 적는다.
- 순환이 없어야 한다. 번호가 작은 쪽만 가리키면 순환은 생기지 않는다.

**참고 문서.** 에이전트가 반드시 읽을 문서를 프로젝트 폴더 기준 경로로 적는다.

- `docs/index.md`, `docs/dev/architecture.md`, 해당 사양 문서(`docs/spec/<기능>.md`)는 항상 넣는다. 사양 문서가 길면 어느 장을 볼지도 적는다.
- 이 작업이 다른 기능의 연결 지점을 쓰면 그 기능의 사양 문서를 넣고, "연결 지점" 절을 보라고 적는다 (예: `- docs/spec/currency.md ("연결 지점" 절)`).
- **사람용 문서를 적지 않는다**: `docs/design/`(게임 기획 원본), `docs/project/`, `docs/archive/`. 구현하는 에이전트는 이 폴더를 읽지 않는다. 기획 문서에만 있고 사양에 없는 내용이 필요하면 요구사항 칸에 옮겨 적거나, 사양이 비어 있는 것이니 `plan-feature` 로 사양을 먼저 고친다.
- 없는 파일을 적지 않는다. 사양 문서 없이 만들 때는 빼고, 필요한 내용을 요구사항에 다 적는다.

**요구사항.** 구체적인 동작을 항목으로 적는다.

- 만들 것의 위치와 이름: 폴더, 네임스페이스, 타입 이름, 공개 메서드 모양. `docs/dev/architecture.md` 의 규칙(기능별 하위 폴더, 파일 하나에 공개 타입 하나)에 맞춘다.
- 수치는 숫자로, 공식은 식으로 적는다. 임시값이면 "(임시값)"이라고 붙인다.
- 경계 상황마다 무슨 일이 일어나는지 적는다.
- 선행 작업이 만든 것 중 무엇을 쓰는지 이름으로 적는다.
- Core 작업이면 시간·난수·저장을 어떻게 받는지 적는다 (`docs/dev/architecture.md` "순수 C# 규칙": 경과 시간과 현재 시각은 인자로, 난수는 주입).
- 대화에서 정한 결정은 여기에 옮겨 적는다. "앞에서 말한 대로" 같은 말은 에이전트에게 통하지 않는다.

**완료 조건.** 가장 중요한 칸이다. 루프는 에이전트가 끝났다고 하면 유니티 테스트 전체를 돌려 통과 여부만 본다. 그러니 완료 조건은 **에이전트가 테스트로 옮길 수 있는 문장**이어야 한다.

- 문장 하나가 에딧 모드 테스트 하나(이상)가 되게 쓴다: "무엇을 주면(상황) 무엇이 나온다(기대 결과)". 숫자를 넣는다.
  - 좋음: `잔액 100에서 TrySpend(150)은 false 를 돌려주고 잔액은 100 그대로다.`
  - 나쁨: `재화 소비가 잘 동작한다.` / `비용이 적절히 오른다.` / `예외 상황을 처리한다.`
- 첫 항목은 테스트가 어디에 있는지다: `Assets/Tests/EditMode/<기능>/<대상>Tests.cs 에 아래 조건마다 테스트가 하나 이상 있고 모두 통과한다.`
- 마지막 항목은 `기존 테스트가 모두 통과한다.`
- 요구사항에 적은 경계 상황은 빠짐없이 완료 조건에도 있어야 한다.

화면 작업(`PlumSword.Game`)은 에딧 모드 테스트가 닿지 않는다 (테스트 어셈블리는 Core 만 참조한다). 무엇으로 판정할지 항목마다 앞에 표시를 붙여 적는다.

- `[테스트]` 표시용 판단을 Core 로 뺀 부분. 에딧 모드 테스트로 판정한다. (가능하면 앞선 로직 작업에서 이미 끝내 둔다)
- `[컴파일]` 화면 코드가 컴파일되고 기존 테스트가 모두 통과한다. 루프가 판정한다. 화면 작업에 항상 넣는다.
- `[플레이 모드]` 실제 실행으로만 확인되는 것 중 기계로 볼 수 있는 것 (예: 실행하면 `[Game]` 아래에 `StatUpgradePanel` 오브젝트가 있고 버튼이 3개다). 플레이 모드 테스트 어셈블리는 아직 없으므로, 처음 쓰는 작업의 요구사항에 "`Assets/Tests/PlayMode/` 에 `PlumSword.Game.Tests` 어셈블리를 만들고 `docs/dev/architecture.md` 표에 추가한다"를 넣는다. 그만큼 작업이 커지니 꼭 필요할 때만 쓴다.
- `[사람 확인]` 보기 좋은지, 위치가 맞는지처럼 기계가 판정할 수 없는 것. 루프는 이것을 판정하지 않고, 사람이 리뷰(review-loop) 때 본다. 무엇을 어떻게 보면 되는지 한 줄로 적는다 (예: `[사람 확인] 플레이하면 화면 아래쪽에 강화 버튼 3개가 겹치지 않고 보인다.`). 에이전트는 이 항목을 보고서의 `### 사람이 확인할 것` 소제목 아래에 옮겨 적는다. 루프의 보고서 양식에 이 소제목이 정해져 있으므로 작업 문서에 따로 지시를 쓰지 않는다.

`[사람 확인]`만 있는 작업은 만들지 않는다. 적어도 `[컴파일]`은 있어야 한다.

**하지 말 것.** 건드리면 안 되는 범위.

- 다른 기능의 내부 코드. 연결 지점(공개된 인터페이스)으로만 쓴다고 적고, 어느 폴더를 고치면 안 되는지 이름으로 적는다.
- 씬·프리팹·에셋 파일(`.unity`, `.prefab`, `.asset`). 화면은 코드로 조립한다.
- 새 어셈블리 정의 (플레이 모드 테스트를 처음 만드는 작업만 예외).
- 이번 작업 범위 밖의 것: 뒤 작업이 할 일(예: "화면은 만들지 않는다. 009 가 한다"), 이번 묶음에서 하지 않기로 한 것(예: 저장).
- Core 작업이면 `UnityEngine` 을 쓰지 않는다.
- 화면 작업이 `GameRoot` 에 조립 호출을 추가할 때는 "자기 기능의 줄만 추가하고 다른 기능의 줄은 고치지 않는다".

### 6. 검사한다

```
python .claude/skills/make-tasks/check_tasks.py <초안 폴더>
```

이 스크립트는 루프 스크립트의 `Doc` 클래스로 초안을 직접 읽어, 루프가 읽게 될 묶음과 선행 작업을 보여 준다. 아무것도 쓰거나 옮기지 않는다. 확인하는 것: 파일 이름과 번호, 칸 제목, 묶음·선행 작업 칸의 모양, 선행 작업이 실제로 있는지, 순환, 참고 문서가 있고 main 에 커밋되어 있는지, 완료 조건의 두루뭉술한 말.

- `[오류]`는 모두 고친다. `[경고]`는 하나씩 보고, 의도한 것이면 7단계에서 사용자에게 알린다.- 완료 조건의 숫자는 요구사항의 공식으로 직접 계산해 맞는지 본다 (예: 비용 `floor(10 × 1.15^3)` = 15). 틀린 기대값이 들어가면 에이전트가 재시도만 하다 보류된다.
- "루프가 읽은 내용"이 내가 의도한 묶음·선행 작업과 같은지 눈으로 확인한다.

스크립트가 못 보는 것은 직접 본다.

- 문서 하나만 읽고도 일을 시작할 수 있는가 (다른 초안이나 이 대화를 봐야 알 수 있는 내용이 없는가).
- 뒤 작업이 쓰는 타입·메서드 이름이 앞 작업 문서에 적힌 것과 글자까지 같은가.
- 요구사항의 경계 상황이 완료 조건에 다 있는가.
- 두 작업이 같은 파일을 만들거나 같은 일을 하지 않는가.
- 사양의 모든 항목이 어느 작업엔가 들어갔는가. 일부러 뺀 것은 무엇인가.

### 7. 보여 주고 승인을 받는다

아래를 대화에 보여 준다.

1. **목록** (표): 번호, 이름, 묶음, 선행 작업, 한 줄 목표.
2. **내가 정한 것**: 사양에 없어 직접 정한 사소한 결정, 임시값.
3. **뺀 것**: 사양에 있지만 이번 작업들에 넣지 않은 것과 이유.
4. **남은 경고**: 검사 스크립트의 경고 중 의도한 것. 사양 문서가 커밋되지 않았으면 그것도.
5. **각 문서 전문**: 줄이지 않고 그대로.

그리고 "이대로 `tasks/todo/` 에 넣을까요?"라고 묻는다. 고쳐 달라는 말이 있으면 초안을 고치고 6단계 검사부터 다시 한다. **"넣어라"는 분명한 답이 있기 전에는 넣지 않는다.** 일부만 승인하면 그것만 넣되, 넣지 않는 문서를 선행 작업으로 가리키는 문서가 있으면 먼저 알린다.

### 8. 넣는다

승인된 문서를 **번호가 작은 것부터** `tasks/todo/` 에 쓴다. 루프가 돌고 있을 수 있어서다. 뒤 문서가 먼저 들어가면 루프가 "선행 작업이 아직 없음" 알림을 보낸다.

- 승인받은 초안과 글자 하나 다르지 않게 쓴다 (UTF-8).
- 같은 이름의 파일이 이미 있으면 덮어쓰지 않고 멈춘 뒤 알린다 (그 사이 번호가 쓰였을 수 있다. 3단계부터 다시 한다).
- 넣은 뒤 `tasks/todo/` 의 파일 목록을 보여 주고, 다음에 할 일을 알린다: 루프 실행은 `python tools/loop/run_loop.py` (계속 켜 두려면 `--watch`), 사양 문서가 커밋되지 않았으면 먼저 커밋.
- 루프가 선행 작업이 남은 문서를 `tasks/wait/` 로 옮기는 것은 정상이다.
