# 기획 (plan-feature)

사용자가 말한 기능을 대화로 구체화해서 사양 문서 `docs/spec/<기능>.md` 로 남긴다.

이 프로젝트는 구현을 자동 개발 루프에 맡긴다. 루프 안의 에이전트는 사람에게 물을 수 없고, 이 대화도 모른다. 그래서 이 스킬의 목표는 하나다. **사양 문서만 읽고도 아무것도 물을 필요가 없게 만든다.** 문서에 적히지 않은 것은 없는 것이다.

다음 단계(작업 문서로 쪼개기)는 `make-tasks` 스킬이 한다. 이 스킬은 작업 문서를 만들지 않는다.

## 지킬 것

- **쓰는 파일은 두 개뿐이다**: `docs/spec/<기능>.md` 와 `docs/spec/index.md` (한 줄 추가). 그것도 사용자가 정리본을 승인한 뒤에만 쓴다.
- 다른 문서(`docs/design/` 의 기획 문서, `docs/dev/architecture.md`, 다른 기능의 사양 등), `CLAUDE.md`, `AGENTS.md`, `tools/loop/`, 코드는 고치지 않는다. 고쳐야 할 것이 보이면 마지막에 **제안만** 한다.
- `tasks/` 는 읽지도 쓰지도 않아도 된다. 특히 쓰지 않는다. 루프가 돌고 있을 수 있다.
- 커밋·푸시하지 않는다. (커밋이 필요하다는 안내만 한다. 7단계)
- 사용자에게 보여 주는 말과 문서는 한글로, 쉬운 말로 쓴다. 코드 이름(타입, 메서드)만 영문이다.

## 순서

### 1. 이미 정해진 것을 모은다

아래를 읽는다. 전부 꼼꼼히 읽을 필요는 없고, 이 기능과 닿는 부분만 본다.

1. `docs/index.md` — 폴더 구성. 폴더마다 색인(`index.md`)이 있다.
2. `docs/design/index.md` — 게임 기획 원본의 색인. 사용자가 쓴 기획이고, 이 스킬의 가장 중요한 입력이다.
   - 색인의 표에서 **이 기능에 닿는 절만** 골라 읽는다 (문서 이름과 절 제목이 적혀 있다). 문서 전체를 읽지 않는다. 다만 기능이 서로 얽혀 있으면(예: 강화 → 전투의 공격 타이밍) 닿는 절은 빠짐없이 읽는다.
   - 사용자가 단계를 말하지 않았으면 가장 앞 단계(지금 만드는 마일스톤)의 규칙으로 기획한다. 뒤 단계에서 바뀔 것(예: 3단계에서 공격 속도 강화가 내공 강화로 바뀜)은 "범위 밖"에 적어 둔다.
   - `game_overview.md` 의 "프로젝트 범위"에서 기간과 범위를 읽는다.
   - 기획 문서에 숫자와 규칙으로 적힌 것은 **이미 정해진 것**이다. 다시 묻지 않는다. `(임시)` 수치도 그 값 그대로 쓰고 "(임시)" 표시를 유지한다.
   - 각 문서의 **미결 사항 절**("아직 정하지 않거나 확인해야 할 사항", "미결 사항") 중 이 기능에 닿는 것은 2단계 질문 후보로 쓴다.
   - `docs/project/`, `docs/archive/` 는 읽지 않는다 (사람용이고 기획의 원본이 아니다).
3. `docs/dev/architecture.md` — 어디에 코드가 생기는지(Core/Game, 네임스페이스), Core 에서 못 쓰는 것(시간·난수·저장은 인자로 받는다), 화면은 코드로 조립한다는 것.
4. `docs/spec/index.md` 와, 거기 적힌 기존 사양 문서의 "연결 지점" 절 — 이 기능이 쓸 수 있는 것, 이 기능을 기다리는 것. 같은 기능의 사양이 이미 있으면 처음부터 다시 만들지 않고 **고치기 모드**로 간다 (아래 "이미 사양이 있을 때").
   - **연결 지점의 원본은 각 사양 문서의 "연결 지점" 절이다.** 따로 모은 연결 지점 문서는 두지 않는다.
5. 코드에 이미 있는 것: `Assets/Scripts/Core/` 아래 기능 폴더와 공개 타입 이름. (`docs/history/` 의 파일 이름을 보면 무엇이 이미 구현됐는지 알 수 있다)

**예시는 결정이 아니다.** 공용 문서에 예시로만 나온 것(예: `docs/dev/architecture.md` 의 테스트 이름 예 `Spend_MoreThanBalance_Fails`, 기획 문서에서 "예:"로 든 것)은 단서일 뿐이다. 추천안으로 삼되 질문은 한다. 규칙·표로 정한 것만 "이미 정해진 것"이다.

읽은 뒤 사용자에게 **"이미 정해진 것"을 짧게 목록으로 먼저 보여 준다** (출처 문서와 함께). 사용자가 "그건 바꾸고 싶다"고 하면 그때만 그 주제를 다시 연다. 공용 문서와 다르게 정하게 되면, 결정 기록에 남기고 마지막 제안에 "어느 문서를 어떻게 고쳐야 하는지"를 넣는다.

### 2. 질문한다

**규칙**

- **한 번에 한 주제**만 묻는다. 한 주제 안에서 서로 붙어 있는 질문은 두세 개까지 묶어도 된다.
- 질문마다 **선택지 2~4개와 추천안**을 준다. 추천안에는 이유를 한 줄 붙인다. 방치형 게임의 흔한 방식, 프로젝트 기간과 범위(1단계에서 `docs/design/game_overview.md` 로 읽은 것), 루프 판정 쉬움(테스트로 확인 가능한 쪽)을 기준으로 고른다.
- `AskUserQuestion` 도구를 쓸 수 있으면 쓴다 (추천안을 첫 선택지로, 이름 끝에 "(추천)"). 없으면 대화로 번호를 붙여 묻는다.
- 사용자가 "추천대로", "알아서 해"라고 하면 추천안으로 정하고 결정 기록에 "추천 수락"이라고 남긴다.
- 사용자가 모르겠다고 하는 수치는 **임시값**으로 정하고 "(임시)"라고 표시한다. 수치를 비워 두지 않는다.
- 이름, 폴더, 표시 문구 같은 사소한 것은 묻지 말고 직접 정한다. 정한 것은 정리본의 "내가 정한 것"에 모아 보여 준다.
- 이미 답이 나온 것, 1단계에서 찾은 것은 다시 묻지 않는다.
- 한 주제가 끝날 때마다 무엇이 정해졌는지 한두 줄로 확인하고 다음 주제로 간다.

**주제 순서** (빠뜨리면 안 된다. 해당 없는 주제는 "해당 없음"으로 정하고 넘어간다)

| 순서 | 주제 | 정해야 하는 것 |
| --- | --- | --- |
| 1 | 범위 | 이번에 만들 것의 한 줄 정의. 무엇까지 이번에 하고 무엇은 나중인지 (큰 틀만) |
| 2 | 동작 | 무엇이 언제 어떻게 바뀌는지. 누가(어느 기능이) 그 변화를 일으키는지. 같은 시점에 여러 일이 생기면 어떤 순서인지 |
| 3 | 경계 상황 | 재화·자원 부족, 최대 레벨·상한, 0 이나 음수 입력, 아주 큰 값(넘침), 같은 동작을 연달아 할 때. 각각 **실패로 돌려주는지, 예외를 던지는지, 값을 잘라내는지**. 값이 바뀌지 않았을 때(0 지급, 실패한 소비) **알림(이벤트)이 가는지 안 가는지**도 |
| 4 | 수치 | 공식(식으로)과 초기값, 오르는 양, 상한. 숫자 타입(`long` / `double` / `decimal`)과 반올림(내림·올림·반올림, 언제 하는지). 정해지지 않으면 임시값. 아래 "수치의 주인" |
| 5 | 연결 지점 | 이 기능이 **다른 기능에 제공하는** 것과 **다른 기능에서 필요한** 것. 아래 "연결 지점 정하는 법" |
| 6 | 화면 | 무엇을 어디에 보여 주는지, 무엇을 누르면 무슨 일이 생기는지, 누를 수 없을 때 어떻게 보이는지. 화면은 코드로 조립한다(`docs/dev/architecture.md`). 화면이 없는 기능이면 "해당 없음". **보여 줄 글자를 만드는 규칙**(숫자 표기, 버튼을 누를 수 있는지)은 수치처럼 예와 함께 정한다. 이 판단은 Core 의 표시용 클래스가 맡아 에딧 모드 테스트로 판정된다 |
| 7 | 저장 | 저장해야 하는 값과 타입, 처음 시작할 때의 값, **저장된 값으로 되살리는 방법**(생성자 인자 등. 연결 지점에도 적는다), 잘못된 저장 값(음수 등)이 들어올 때, 오프라인 보상에 주는 영향(꺼져 있는 동안 이 값이 바뀌는지) |
| 8 | 범위 밖 | 이번에 하지 않는 것. 1단계에서 나중으로 미룬 것, 대화 중 나왔다가 뺀 것 |

질문 예시 (이 모양으로 묻는다):

> **경계 상황 — 잔액보다 많이 쓰려고 할 때**
> 1. 실패(`false`)를 돌려주고 잔액은 그대로 (추천: 버튼 쪽에서 확인 없이 바로 불러도 안전하고, 테스트로 판정하기 쉽다)
> 2. 예외를 던진다
> 3. 가진 만큼만 쓰고 0 으로 만든다

**수치의 주인**

수치는 그 값을 만들어 내는 규칙을 가진 기능이 정한다. 예: 몬스터 한 마리가 주는 엽전은 전투·스테이지 기능의 수치이고, 강화 비용은 강화 기능의 수치다. 재화 기능은 "받은 만큼 늘고 쓴 만큼 준다"만 정한다. 다른 기능의 수치가 대화에 나오면 여기서 정하지 말고 범위 밖에 "○○ 기능이 정한다"로 적는다. 사용자가 지금 정하고 싶어 하면 결정 기록에 메모로만 남기고, 그 기능을 기획할 때 쓰라고 알린다.

**연결 지점 정하는 법**

연결 지점은 루프에서 여러 작업이 서로의 코드를 건드리지 않게 하는 약속이다. 그래서 **C# 모양 그대로** 정한다.

- 기준은 순수 C# 이다: 네임스페이스 `PlumSword.Core.<기능>`, 타입 이름, 공개 메서드·속성·이벤트의 모양.
  예: `public bool TrySpend(long amount)`, `public long Balance { get; }`, `public event Action<long> BalanceChanged`.
- 메서드마다 경계 상황의 동작을 한 줄씩 붙인다 (3번 주제에서 정한 것).
- 시간·현재 시각·난수가 필요하면 인자로 받는 모양으로 적는다 (`docs/dev/architecture.md` "순수 C# 규칙").
- **제공하는 것**: 이 기능을 쓸 다른 기능(기획 문서의 "기능 간 연결" 절과 게임 흐름에서 찾는다)이 무엇을 부를지 떠올려 보고 정한다. 아직 사양이 없는 기능도 "이 기능은 아마 이것을 부를 것"으로 생각해 본다.
- **필요한 것**: 다른 기능의 사양·코드에 이미 있으면 그 이름을 그대로 적는다. 없으면 사용자에게 고르게 한다: (가) 이 기능이 임시로 대신한다(예: 테스트용 값 직접 넣기), (나) 그 기능을 먼저 기획한다, (다) 이 기능의 범위에서 뺀다. 다른 기능의 사양 문서를 이 스킬이 고치지는 않는다.
- 객체를 누가 만들고 누가 들고 있는지도 정한다 (예: `GameRoot` 가 하나 만들어 필요한 기능에 넘긴다).

**질문을 끝내도 되는지 확인한다.** 아래가 모두 "예"일 때 3단계로 간다. 하나라도 "아니오"면 그 주제를 더 묻는다.

- 주제 8개가 모두 정해졌거나 "해당 없음"이다.
- 모든 수치에 숫자가 있다 (임시값 포함). "적당히", "나중에" 가 없다.
- 경계 상황마다 결과가 하나로 정해졌다.
- 연결 지점이 C# 모양(이름, 인자, 돌려주는 값)까지 적혀 있다.
- 완료 조건 초안을 숫자가 들어간 문장으로 쓸 수 있다.
- 이 문서만 읽은 에이전트가 "이건 어떻게 하지?" 할 곳이 없다.

### 3. 정리본을 보여 주고 승인을 받는다

[spec_template.md](spec_template.md) 양식으로 사양 문서 전문을 대화에 보여 준다. 줄이지 않는다. 그 위에 두 가지를 짧게 덧붙인다.

- **내가 정한 것**: 묻지 않고 직접 정한 사소한 결정.
- **임시값 목록**: "(임시)"가 붙은 수치 전부.

완료 조건 초안의 숫자는 수치 절의 공식으로 **직접 계산해서** 맞는지 본 뒤 보여 준다. 틀린 기대값은 루프에서 재시도만 반복하다 보류된다.

그리고 "이대로 `docs/spec/<기능>.md` 에 쓸까요?"라고 묻는다. 고쳐 달라고 하면 고친 부분을 결정 기록에도 반영하고 다시 보여 준다. **"쓰라"는 분명한 답이 있기 전에는 파일을 쓰지 않는다.**

### 4. 사양 문서를 쓴다

- 경로: `docs/spec/<기능 영문 이름>.md`. 이름은 영문 소문자·숫자·밑줄, 짧게 (예: `currency.md`, `stat_upgrade.md`). `docs/spec/` 폴더가 없으면 만든다.
- 같은 이름의 파일이 이미 있으면 덮어쓰지 않는다 (고치기 모드는 아래).
- 승인받은 정리본과 글자 하나 다르지 않게 쓴다. "내가 정한 것"과 "임시값 목록"은 문서에 넣지 않는다 (내용은 이미 각 절과 결정 기록에 들어 있다).
- UTF-8 로 쓴다.

### 5. 색인에 한 줄 추가한다

`docs/spec/index.md` 의 표 맨 아래에 한 줄 넣는다. 다른 줄은 고치지 않는다. 최상위 색인(`docs/index.md`)은 고치지 않는다.

```
| [currency.md](currency.md) | 금화. 지급·소비 동작, 수치, 저장 값 | `PlumSword.Core.Currency.Wallet` |
```

칸은 문서, 기능(무슨 기능의 사양인지), 연결 지점 타입(다른 기능이 찾을 이름)이다.

### 6. 마지막으로 확인한다

- 사양 문서의 절 제목이 양식과 같은가 (빠진 절이 없는가).
- 연결 지점의 이름이 수치·동작·완료 조건 절에서 쓴 이름과 글자까지 같은가.
- 경계 상황 표의 줄마다 완료 조건 초안에 같은 경우가 있는가.
- 다른 공용 문서와 어긋나는 곳이 있는가 (있으면 7단계 제안에 넣는다).

### 7. 안내한다

대화 끝에 아래를 알린다.

1. 쓴 파일 두 개의 경로.
2. **커밋이 필요하다.** 루프는 main 에서 딴 worktree 에서 일하므로, main 에 커밋되지 않은 사양 문서는 에이전트가 읽지 못한다. 이 스킬은 커밋하지 않는다.
3. 다른 문서를 고쳐야 할 것이 있으면 그 제안 (어느 문서, 어느 절, 무엇을).
4. "작업 문서로 쪼개려면 `make-tasks` 스킬을 쓰세요. (예: `docs/spec/currency.md 로 작업 만들어 줘`)"

## 이미 사양이 있을 때 (고치기 모드)

같은 기능의 사양이 `docs/spec/` 에 있으면:

1. 그 문서를 읽고 무엇을 바꾸고 싶은지 묻는다.
2. 바꾸는 주제만 2단계 규칙대로 묻는다.
3. 바뀐 부분이 보이게 정리해서(바뀌기 전 → 바뀐 뒤) 보여 주고 승인을 받는다.
4. 승인되면 문서를 고치고, 결정 기록에 새 질문과 답을 **덧붙인다** (예전 기록은 지우지 않는다. 뒤집힌 결정은 "→ 바뀜: 날짜, 이유"를 단다).
5. 연결 지점이 바뀌었으면 경고한다: 이미 그 연결 지점을 쓰는 코드(`Assets/Scripts/`)나 작업 문서가 있을 수 있다. 그것을 고치는 작업이 필요하다고 알린다 (작업 문서는 `make-tasks`).
6. 색인 줄은 설명이 달라졌을 때만 고친다.

## 자주 틀리는 것

| 틀린 것 | 왜 문제인가 | 이렇게 |
| --- | --- | --- |
| 수치를 "나중에 정함"으로 비움 | 에이전트가 아무 숫자나 넣거나 보류한다 | 임시값을 숫자로, "(임시)" 표시 |
| 경계 상황을 "적절히 처리" | 에이전트마다 다르게 만들고 테스트로 판정할 수 없다 | 경우마다 결과 하나 (실패 / 예외 / 잘라냄) |
| 연결 지점을 말로만 적음 ("재화를 쓸 수 있게 한다") | 뒤 작업이 이름을 추측해서 서로 안 맞는다 | C# 모양 그대로 |
| 숫자 타입을 안 정함 | 한 작업은 `int`, 다른 작업은 `double` 로 만든다 | 타입과 반올림 방식을 수치 절에 |
| 완료 조건 초안이 "잘 동작한다" | 테스트로 옮길 수 없다 | "무엇을 주면 무엇이 나온다" + 숫자 |
| 저장을 빼먹음 | 저장 기능을 만들 때 무엇을 저장할지 다시 기획해야 한다 | 저장할 값과 시작값, 오프라인 영향 |
| 사용자가 이미 문서에 정한 것을 다시 물음 | 대화만 길어진다 | 1단계에서 "이미 정해진 것"을 먼저 보여 준다 |
| 한 번에 질문 열 개 | 답이 대충 나오고 빠지는 것이 생긴다 | 한 주제씩 |
| 승인 전에 파일을 씀 | 승인되지 않은 사양을 make-tasks 가 집어갈 수 있다 | 승인 후에만 |
