# 보류 답하기 (answer-blocked)

루프가 막히면 문서 끝에 `## 보류 사유 (날짜 시각)` 절(사유, 질문, 추천안, 기능 브랜치, 작업 에이전트)을 적고 `tasks/blocked/` 로 옮긴다. **보류가 하나라도 남아 있으면 그 루프는 끝나지 않고 다른 묶음도 시작되지 않는다.** 이 스킬은 사람의 답을 문서에 적고 문서를 `todo` 로 되돌려 루프가 다시 돌게 한다.

다시 `todo` 로 간 문서는 루프가 다시 꺼내 처리한다. 이때 루프는 같은 기능 브랜치(`task/<문서이름>`)를 이어 쓰고, 에이전트에게 "작업 중 커밋이 있으니 확인하고 이어서 하라"고 알린다. 에이전트는 **이 문서만 읽고** 일한다. 이 대화에서 오간 말은 모른다. 그래서 답은 문서에 적힌 것만으로 이해되게 쓴다.

## 지킬 것

- **옮길 수 있는 것은 `tasks/blocked/` 의 문서뿐이다.** `todo`, `wait`, `doing`, `done` 의 문서는 옮기지 않는다. 고치는 것도 blocked 문서뿐이다. 예외는 "선행 작업 순환"에서 사용자가 고르고 승인한 문서의 `## 선행 작업` 칸 하나다 (아래 3-C).
- blocked → todo 는 **사용자가 답하고 옮기라고 확인한 뒤에만** 한다.
- 코드, `docs/`, `tools/loop/`, `CLAUDE.md`, `AGENTS.md` 는 고치지 않는다.
- 깃은 **조회만** 한다 (`log`, `diff`, `show`, `rev-parse`, `for-each-ref`). 체크아웃, 커밋, 병합, 리셋, 브랜치 삭제는 하지 않는다. 루프가 옆 worktree(`../PlumSwordIdle_loop`)에서 돌고 있을 수 있다. 브랜치를 지워야 하면 명령을 알려 주고 사용자가 직접 하게 한다.
- `tasks/` 는 항상 **프로젝트 폴더(main)의 것**을 쓴다. worktree 의 `tasks/` 는 보지 않는다.
- `.env` 는 읽지 않는다.
- 커밋·푸시는 하지 않는다.

## 보조 스크립트

`blocked_info.py` 가 조회와 옮기기를 맡는다. 프로젝트 폴더에서 실행한다.

| 명령 | 하는 일 |
| --- | --- |
| `python .claude/skills/answer-blocked/blocked_info.py list` | 루프 상태와 보류 문서 목록(번호 순, 보류 종류, 묶음) |
| `python .claude/skills/answer-blocked/blocked_info.py show <문서이름>` | 목표, 마지막 보류 사유, 이전 보류·답변, 보고서, 기능 브랜치의 커밋과 바뀐 파일, 관련 로그, 이 문서를 기다리는 문서 |
| `python .claude/skills/answer-blocked/blocked_info.py stamp` | 답변 절 제목에 쓸 지금 시각 (`2026-11-13 21:05` 꼴) |
| `python .claude/skills/answer-blocked/blocked_info.py move <문서이름> todo` | blocked → todo. 다른 폴더에 같은 이름이 있으면 옮기지 않는다 |
| `python .claude/skills/answer-blocked/blocked_info.py move <문서이름> <폴더>` | blocked → tasks/ 밖 폴더 (버릴 때). tasks/ 안이면 거부한다 |

`<문서이름>` 은 `.md` 없는 파일 이름이다 (예: `003_stat_upgrade`). 스크립트는 blocked 가 아닌 문서는 옮기지 않는다. 옮길 때는 이 스크립트만 쓴다.

## 순서

### 1. 목록

`list` 를 실행한다.

- 보류 문서가 없으면 "보류 문서가 없습니다"라고 알리고 끝낸다.
- "루프가 지금 ○○ 를 처리 중" 이라는 주의가 나오면 사용자에게 알린다. 에이전트가 실행되는 동안 `tasks/` 의 파일이 바뀌면 루프가 디스코드 STOPPED 채널로 "사용자 폴더가 바뀜" 경고를 보낸다. 이 스킬이 한 일이면 무시해도 된다고 말해 둔다 (루프는 멈추지 않는다).
- 여러 건이면 번호 순으로 하나씩 처리한다. 사용자가 특정 문서를 먼저 하자고 하면 그것부터 한다.

### 2. 문서 하나 보여 주기

`show <문서이름>` 을 실행하고, 필요하면 문서 전체를 Read 로 읽는다. 사용자에게 아래를 짧게 정리해 보여 준다.

1. **목표** 한 줄, 묶음.
2. **마지막 보류 사유**: 종류, 사유, 질문, 추천안. 같은 문서가 전에도 보류됐으면(이전 보류·답변이 있으면) 그 사실과 지난번 답을 함께 알린다. 같은 데서 또 막혔다면 지난 답이 부족했다는 뜻이다.
3. **에이전트 보고서**가 있으면 요약 (한 일, 가정, 테스트 결과). 보고서는 여러 개일 수 있다 (재시도마다 갱신, 보류가 여러 번).
4. **기능 브랜치에 남은 작업 중 커밋**: 루프 브랜치 대비 커밋 목록과 바뀐 파일. 필요하면 `git diff <루프 브랜치>...<기능 브랜치> -- <파일>` 로 내용을 본다 (조회만).
   - 루프 브랜치는 `.loop/state.json` 의 `loop_branch` 다. 루프가 진행 중(`active`)이 아니면 스크립트는 `main` 과 비교한다.
5. **이 문서를 선행 작업으로 가리키는 문서**가 있으면 알린다. 이 작업을 버리면 그 문서들이 영영 기다리게 된다.

### 3. 종류별로 다루기

보류 종류는 사유의 첫머리로 정해진다 (스크립트가 판단해 준다).

#### A. 에이전트의 질문 (그 밖의 모든 사유)

에이전트가 결과 파일에 `blocked` 를 쓴 경우다.

1. 질문을 쉬운 말로 다시 설명하고, 왜 에이전트가 스스로 정하지 못했는지 보고서·기능 브랜치 내용으로 짚어 준다.
2. 선택지를 2~4개 낸다. **추천안을 첫 번째**에 두고 "(추천)"을 붙인다. 선택지마다 결과가 어떻게 달라지는지 한 줄씩 적는다. 필요하면 공용 문서(`docs/`)와 코드를 읽어 근거를 찾는다. AskUserQuestion 을 쓸 수 있으면 쓴다.
3. 답이 정해지면 4단계로.

질문이 "권한이 막혀서 못 한다"류이면 `docs/loop.md` 의 "클로드가 정상 작업 중에 막힐 때 확인하는 곳"에 따라 `.loop/logs/guard.log` 와 해당 시도의 `.loop/logs/<문서이름>_attempt<n>_claude.out.txt` 의 `permission_denials` 를 보고 원인을 알린다. 설정(`loop_config.json` 등)은 이 스킬에서 고치지 않고, 무엇을 고치면 되는지만 알려 준다.

#### B. 재시도 한도 초과 (사유가 `재시도 한도(` 로 시작)

질문이 아니라 **실패 기록**이다. 질문 칸의 "실패 원인을 확인하고…"는 매번 같은 고정 문구다.

1. 원인을 찾는다.
   - 사유에 붙은 "마지막 실패" 내용 (테스트 실패면 실패한 테스트 이름·메시지, 컴파일 오류면 `error CS…` 줄, 시간 초과·실행 실패면 그 내용).
   - `show` 는 마지막 시도의 에이전트 마지막 메시지와, 실행 로그 중 이 문서를 처리한 구간만 잘라 보여 준다. 시도 로그 파일 이름의 번호는 처리할 때마다 1부터 다시 세므로, 전에도 보류됐던 문서는 앞 번호 파일이 이번 것으로 덮어써져 있다 (수정 시각으로 구분).
   - `show` 가 알려 준 `.loop/logs/` 의 로그: `run_<날짜-시간>.log` 의 이 문서 줄들(재시도 횟수, 테스트 결과, 권한 거부), 시도별 출력 `<문서이름>_attempt<n>_<에이전트>.out.txt` (클로드는 JSON 의 `result`, 코덱스는 `.codex_last.txt`). 처음과 마지막 시도를 비교하면 같은 데서 계속 막혔는지, 매번 다른 데서 막혔는지 보인다.
   - 테스트 결과는 worktree 의 `.loop/test/` 에 남아 있을 수 있다 (다음 테스트가 돌면 덮어써진다). 읽기만 한다.
   - 기능 브랜치의 바뀐 파일과 보고서.
2. 원인을 쉬운 말로 설명한다: 무엇이 실패했는지, 왜 에이전트가 고치지 못했다고 보는지. 확실하지 않으면 추측이라고 밝힌다.
3. 셋 중 무엇을 할지 정하게 한다 (원인에 맞는 것을 추천).
   - **완료 조건을 고친다**: 완료 조건이 틀렸거나, 테스트로 판정할 수 없거나, 요구사항과 서로 어긋날 때. `## 완료 조건` 칸을 고친다.
   - **작업을 쪼갠다**: 한 번 실행(시간 제한)에 다 못 끝낼 만큼 크거나, 시간 초과가 반복될 때. 이 스킬은 새 작업 문서를 만들지 않는다. 이 문서의 범위를 줄이도록 요구사항·완료 조건을 고치고, 뺀 부분은 `make-tasks` 스킬로 새 작업을 만들라고 안내한다. 뺀 부분이 이 문서보다 먼저 있어야 하면, 그 새 문서를 이 문서의 선행 작업으로 넣을지 함께 정한다 (그러면 이 문서는 todo 로 간 뒤 wait 로 갈 수 있다).
   - **힌트를 준다**: 조건은 맞는데 에이전트가 방법을 못 찾았을 때. 원인과 고치는 방향을 답변 절에 구체적으로 적는다 (파일, 타입, 테스트 이름까지).
   - 환경 문제(유니티 실행 불가, 권한 설정)로 보이면 문서를 고쳐도 소용없다. 사용자가 무엇을 고쳐야 하는지 알려 주고, 고친 뒤에 todo 로 옮기자고 한다.

#### C. 선행 작업 순환 (사유가 `선행 작업이 서로를 가리키는 순환` 으로 시작)

사유에 순환 경로(`A → B → A`)가 적혀 있다. 순환에 걸린 문서는 todo·wait 에 있던 것만 blocked 로 왔고, 나머지는 다른 폴더(주로 blocked)에 있을 수 있다.

1. 순환 경로의 각 문서가 지금 어느 폴더에 있는지, 각 문서의 `## 선행 작업` 칸을 보여 준다.
2. 어느 문서의 선행 작업 칸에서 무엇을 뺄지 정하게 한다. 목표·요구사항을 보고 "실제로 먼저 끝나야 하는 쪽"을 추천한다.
3. 그 칸을 고친다. **고칠 수 있는 문서는 blocked 에 있는 것뿐**이다. 고쳐야 할 문서가 todo·wait 에 있으면, 이 스킬은 고치지 않고 사용자가 직접 고치게 한다 (또는 순환을 다른 쪽에서 끊게 한다). doing·done 이면 고치지 않는다.
   - 칸 제목 `## 선행 작업` 은 그대로 두고, 한 줄에 하나씩 `- 이름` 꼴, 없으면 `없음`.
4. 순환에 걸린 blocked 문서는 모두 답변 절을 적고 todo 로 옮겨야 한다. 하나만 옮기고 순환이 남아 있으면 루프가 다시 blocked 로 보낸다. 옮기기 전에 남은 문서들의 선행 작업으로 순환이 정말 풀렸는지 확인한다.

#### D. done 인데 기록이 없음 (사유가 `done 폴더에 있지만 docs/history 에 기록이 없음` 으로 시작)

`tasks/done/` 에 있었지만 완료 커밋(`docs/history/<문서이름>.md`)이 루프 브랜치에도 기능 브랜치에도 없던 경우다. 사람이 문서를 손으로 done 에 넣었거나, 루프 브랜치를 버리고 done 문서를 남겨 둔 경우가 흔하다.

1. 확인해서 알려 준다 (조회만): `main` 에 `docs/history/<문서이름>.md` 가 있는지 (`git log --oneline main -- docs/history/<문서이름>.md`), 기능 브랜치가 있는지, 문서에 `## 보고서`·`## 루프 기록` 이 있는지.
2. 정하게 한다.
   - **다시 처리한다**: 답변 절을 적고 todo 로. 남은 보고서·루프 기록이 다음 에이전트를 헷갈리게 하지 않게, 답변 절에 "앞의 보고서는 이전 실행의 것이고 기록되지 않았다. 처음부터 다시 처리한다" 처럼 적는다.
   - **이미 main 에 들어가 있다** (history 가 main 에 있음): 이 루프에서 다시 할 필요가 없다. 6단계(버리기)로 tasks/ 밖에 둔다. done 으로 옮기지는 않는다 (이 스킬은 done 에 넣지 않는다).
   - **버린다**: 6단계.

### 4. 답변 적기

`stamp` 로 시각을 얻어 문서 **맨 끝**에 붙인다. 형식:

```markdown


## 답변 (2026-11-13 21:05)

- 보류 종류: 에이전트의 질문 (2026-11-13 20:40 보류 사유에 대한 답)
- 결정: (한두 문장. 무엇을 하기로 했는지)
- 이유: (왜 그렇게 정했는지. 에이전트가 비슷한 다른 결정을 할 때 기준이 되게)
- 할 일: (다음 에이전트가 할 것. 파일·타입·메서드·테스트 이름을 구체적으로)
- 바꾼 칸: (고친 칸과 고친 내용. 없으면 "없음")
- 기능 브랜치: task/<문서이름> 의 작업 중 커밋은 (살려서 이어간다 / 이 부분은 버리고 다시 한다 …)
```

종류에 따라 덧붙일 줄:

- 재시도 한도 초과: "보류 종류" 다음에 `- 원인:` 줄 (무엇이 몇 번 어떻게 실패했고 왜인지). 테스트 이름이나 기대값이 바뀌면 "할 일"에 새 이름·값을 적는다. 기능 브랜치의 옛 테스트는 다음 에이전트가 고쳐야 하기 때문이다.
- 선행 작업 순환: `- 바꾼 칸:` 에 어느 문서의 선행 작업에서 무엇을 뺐는지. 순환에 걸린 다른 blocked 문서의 답변 절에도 같은 내용을 적는다.
- done 인데 기록이 없음: 앞의 보고서·루프 기록을 어떻게 볼지 (위 3-D).

쓸 때 지킬 것:

- **대화 맥락 없이 이해되게.** "아까 말한 2번", "추천안대로" 처럼 쓰지 않는다. 고른 내용을 그대로 풀어 쓴다.
- 질문에 대한 답만 쓰지 말고, 그 답 때문에 **무엇을 해야 하는지**까지 쓴다.
- 답변 절 안에서는 `## ` 제목을 쓰지 않는다. 루프 스크립트가 `## 선행 작업`, `## 묶음` 제목을 처음 나온 것으로 찾기 때문에, 답변 안에 같은 제목이 생기면 칸을 잘못 읽을 수 있다. 소제목이 필요하면 `###` 나 굵은 글씨를 쓴다.
- 앞의 `## 보류 사유`, `## 보고서`, 이전 `## 답변` 절은 지우거나 고치지 않는다. 기록으로 남긴다.

**칸을 고칠 때** (요구사항, 완료 조건, 선행 작업, 하지 말 것 등):

- 해당 칸을 직접 고친다 (문서 위쪽의 원래 칸). 칸 제목은 바꾸지 않는다.
- 답변 절의 "바꾼 칸"에 무엇을 어떻게 바꿨는지 적는다 (예: "완료 조건: `x 가 0 이면 예외` → `x 가 0 이면 false 반환`").
- 묶음 칸은 고치지 않는다. 묶음이 바뀌면 이번 루프가 끝나지 않거나 엉뚱한 루프에서 처리된다. 정말 바꿔야 하면 사용자에게 그 결과를 설명하고 확인받는다.
- 고친 뒤의 문서 모양(바뀐 칸과 답변 절)을 사용자에게 보여 준다.

### 5. todo 로 옮기기

1. "이 문서를 tasks/todo/ 로 옮길까요?" 라고 확인받는다. 답변만 적어 두고 옮기지 않는 것도 된다 (나중에 직접 옮기거나 다시 이 스킬을 쓴다).
2. 확인받으면 `move <문서이름> todo` 를 실행한다.
3. "같은 이름의 문서가 이미 있음" 으로 거부되면 옮기지 않고 사용자에게 어느 폴더에 있는지 알린다. 직접 덮어쓰거나 이름을 바꾸지 않는다.
4. 옮긴 뒤 알려 줄 것:
   - 루프가 진행 중이면 다음 실행(감시 모드면 다음 확인 때)에 다시 꺼낸다. 루프가 멈춰 있으면 `python tools/loop/run_loop.py` 로 다시 실행해야 한다.
   - 선행 작업이 아직 안 끝났으면 루프가 wait 로 옮긴다 (정상).

### 6. 버리기

사용자가 이 작업을 하지 않기로 하면:

1. `docs/loop.md` 에 적힌 방법을 설명한다: 이번 묶음에서 빼려면 문서를 **`tasks/` 밖으로** 옮긴다. 그러면 남은 보류가 없을 때 다음 실행에서 루프가 끝나고 "루프 종료" 알림이 온다.
2. 함께 알려 줄 것:
   - 이 문서를 선행 작업으로 가리키는 문서가 있으면 그 문서들은 계속 기다린다 (wait 에 있으면 영영 안 올라온다). 그 문서들의 선행 작업 칸을 고치거나 함께 빼야 한다. 그 문서들은 이 스킬이 고치지 않는다 (blocked 에 있는 것만 예외).
   - 기능 브랜치 `task/<문서이름>` 은 남아 있다. 필요 없으면 사용자가 직접 지운다: `git branch -D task/<문서이름>` (이 스킬은 실행하지 않는다). 같은 이름의 작업을 나중에 다시 넣으면 루프가 이 브랜치를 이어 쓰니 주의한다.
3. 어디로 옮길지 묻는다. 추천: 프로젝트 폴더 **옆**의 `../PlumSwordIdle_discarded/` (루프 worktree 처럼 프로젝트 밖이라 깃에 잡히지 않는다). 프로젝트 폴더 안에 두면 `tasks/` 와 달리 깃에서 제외되지 않아 커밋될 수 있으니, 사용자가 안쪽을 원하면 그 점을 알린다. 문서에 버린 이유를 `## 답변` 절로 적어 둘지도 묻는다.
4. 확인받으면 `move <문서이름> <폴더>` 를 실행한다. 지우지 않는다.

### 7. 마무리

모든 보류 문서를 다 봤거나 사용자가 그만하자고 하면 요약한다.

- 처리한 문서: 이름, 종류, 결정 한 줄, 어디로 옮겼는지 (todo / tasks 밖 / 그대로 둠), 고친 칸.
- 남은 보류: 이름과 종류. 남은 보류가 있으면 그 루프는 끝나지 않는다는 것.
- 사용자가 할 일: 루프 다시 실행, 브랜치 정리, 설정 수정, `make-tasks` 로 새 작업 만들기 등.
