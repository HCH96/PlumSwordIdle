# 루프 리뷰 (review-loop)

자동 개발 루프는 묶음 하나를 `loop/<날짜-시간>` 브랜치에서 처리하고, **검증을 통과하면 사람의 확인 없이 통합 브랜치(`integration`)에 합친 뒤** 곧바로 다음 묶음으로 넘어간다. main 과 원격은 건드리지 않는다. todo 가 다 비면 디스코드로 "모든 작업 끝: 확인할 차례"를 알린다. 이 스킬은 그다음, **사람이 main 에 올리기 전의 마지막 확인**을 돕는다.

합쳐지기 전에 이미 통과한 것 (`docs/dev/loop.md` "검증"):

| 겹 | 판정한 쪽 | 믿을 수 있는 정도 |
| --- | --- | --- |
| 테스트 (작업마다, 합치기 직전 전체) | 스크립트 | 테스트가 통과했다는 사실은 확실하다. 다만 "에이전트가 쓴 테스트가 통과했다"는 뜻일 뿐이다 |
| 관문 (금지된 파일, Core 의 유니티 의존, 약해진 테스트 등) | 스크립트 | 규칙에 적힌 것은 확실히 걸러졌다. 규칙에 없는 것은 보지 않는다 |
| 교차 리뷰 (완료 조건별 테스트, 요구사항, 하지 말 것, 가정) | 구현하지 않은 쪽 에이전트 | **판단이다. 증명이 아니다.** 리뷰어도 틀리고, 두 모델이 같은 것을 놓칠 수 있다 |

그래서 이 리뷰에서 볼 것은 **교차 리뷰의 판단이 맞았는지**, **사람이 몰랐던 결정(가정)이 무엇인지**, **화면이 실제로 어떻게 보이는지**다. 루프 안의 에이전트는 사람에게 묻지 못한 채 일했고, 애매한 것은 스스로 정해 보고서의 "가정"에만 적어 두었다.

기록이 있는 곳:

- 루프별 증거: 통합 브랜치의 `docs/evidence/index.md`(루프마다 한 줄)와 `docs/evidence/<루프>/report.md`, `results.json`, `screenshots/`.
- 완료된 작업 문서 원본(보고서, 가정, 루프 기록 포함): 통합 브랜치의 `docs/history/<문서이름>.md`.
- 루프 하나는 통합 브랜치의 병합 커밋 하나이고, 태그 `loop-merged/<루프>` 가 그 커밋을 가리킨다.

루프 동작의 기준은 `docs/dev/loop.md`, 코드 규칙의 기준은 `docs/dev/architecture.md` 다.

공통 실행 기준은 `docs/dev/workflow.md`를 먼저 읽는다. 이 본문과 템플릿이 Claude/Codex의 공통 원본이다. 아래 도구 이름(Read, AskUserQuestion 등)은 현재 환경의 파일 읽기·질문 도구로 대응하고, 질문 도구가 없으면 일반 대화로 묻는다. 기존 답변과 명시적 승인은 이어서 적용한다.

## 지킬 것

- **코드를 고치지 않는다.** 문제를 찾으면 보고만 한다. 고칠 것은 후속 작업으로 넘긴다 (7단계).
- 깃은 **조회만** 한다: `git show`, `git diff`, `git log`, `git ls-tree`, `git merge-base`, `git for-each-ref`, `git status`, `git rev-parse`. 체크아웃·커밋·브랜치 삭제·태그 변경은 하지 않는다. 통합 브랜치의 파일은 체크아웃하지 말고 `git show <브랜치>:<경로>` 로 읽는다.
- 예외는 하나뿐이다. **사용자가 분명히 "올려 줘"(또는 "합쳐 줘")라고 하면** main 에 올린다 (7단계). 결론이 "올려도 됨"이라고 해서 알아서 올리지 않는다.
- **푸시는 하지 않는다.** 사용자가 이 스킬 안에서 분명히 시켜도, 올린 뒤 무엇이 올라갔는지 보여 주고 한 번 더 확인받은 다음에만 한다.
- **사용자 폴더에서 통합 브랜치를 체크아웃하지 않는다.** 루프가 그 브랜치에 합치지 못하고 멈춘다.
- `tasks/` 와 `.loop/` 는 읽기만 한다. `.env` 는 읽지 않는다.
- 루프가 진행 중일 때는 worktree(`../PlumSwordIdle_loop`)에서 아무것도 실행하지 않는다.

## 순서

### 1. 확인할 대상을 찾는다

프로젝트 폴더에서 보조 스크립트를 실행한다. 읽기만 하는 스크립트다.

```
python tools/skills/review_scan.py
```

스크립트는 main 과 통합 브랜치를 비교해 아직 main 에 올리지 않은 루프를 찾고, 아래 단계에 쓸 자료를 한 번에 출력한다. 출력의 "1. 확인할 대상"을 먼저 본다. **리뷰 기준 SHA·리뷰 대상 SHA·확인 시점 main SHA를 기록한다.** 이후 코드·이력·증거 조회는 이 SHA로만 한다. 브랜치나 태그 이름을 다시 해석해 대상을 바꾸지 않는다. `--loop`는 부분 리뷰이며, main 반영 전에 `--base <main SHA> --head <대상 SHA>`로 누적 범위를 리뷰해야 한다.

| 상황 | 할 일 |
| --- | --- |
| main 에 올리지 않은 루프가 있다 | **그 전체(<기준 SHA>..<대상 SHA>)를 한 번에 본다.** 스크립트가 기본으로 이렇게 고른다 |
| 루프가 여러 개라 너무 길다, 또는 하나만 다시 보고 싶다 | `--loop <날짜-시간>` 으로 루프 하나만 본다. 여러 개를 차례로 볼 때는 오래된 것부터 본다 (뒤 루프가 앞 루프 위에 쌓였다) |
| 올릴 루프가 없다 | 리뷰할 것이 없다고 알리고 끝낸다. 루프가 진행 중이면 그 사실과 묶음을 알린다 |
| 검증에서 떨어진 루프 브랜치(`rejected/<날짜-시간>`)가 있다 | 올릴 대상이 아니다. 사용자가 원하면 `--branch rejected/<날짜-시간>` 으로 무엇이 왜 떨어졌는지 본다. 그 작업들은 보류로 가 있으니 `answer-blocked` 로 안내한다 |
| 진행 중이 아닌데 통합 브랜치에 안 합쳐진 `loop/*` 가 있다 | 새 루프가 시작되지 않는 상태다. 자동 합치기(`auto_merge`)가 꺼져 있거나, 합치는 도중에 끊겼거나, 루프 밖에서 만든 브랜치다. `--branch loop/<날짜-시간>` 으로 보고 사용자에게 알린다 |
| 루프가 **진행 중**이다 | 이미 합쳐진 루프만 본다. 진행 중인 묶음은 자료에 없다는 것을 결과 맨 위에 적고, 5단계 테스트는 돌리지 않는다. 사용자가 "다 끝나면 한 번에 보겠다"고 하면 거기서 멈춘다 |

보류(blocked)가 남아 있으면 그 사실도 알린다. 보류 작업과 그것을 기다리는 작업은 이번에 올라가는 범위에 없고, `answer-blocked` 로 답해야 다음 루프에서 처리된다.

### 2. 증거를 먼저 읽고, 범위 전체를 요약한다

스크립트 출력의 "2. 묶음 요약"에 이 범위의 루프와 증거 위치가 있다. **루프마다 증거 보고서를 먼저 읽는다.**

```
git show <대상 SHA>:docs/evidence/index.md
git show <대상 SHA>:docs/evidence/<루프>/report.md
```

보고서에는 사람이 볼 것, 가정 전부, 화면 갈무리, 작업별 구현·리뷰 에이전트와 시도, 리뷰어가 만든 완료 조건별 테스트 표, 관문의 "확인 필요" 항목이 있다. 이것은 **주장**이고, 3단계에서 코드와 맞는지 확인한다.

화면 갈무리는 직접 본다. 작업 폴더를 바꾸지 않도록 임시 폴더로 꺼내서 읽는다.

```
python tools/skills/export_evidence.py --revision <대상 SHA> --path docs/evidence/<루프>/screenshots/game_030s.png --output <저장소 밖 임시 폴더>/game_030s.png
```

요약에서 눈여겨볼 것:

- **시도 횟수가 많은 작업(3회 이상).** 테스트 실패, 관문 위반, 리뷰의 "고쳐라"가 모두 시도로 세어진다. 테스트를 통과시키려고 테스트나 요구사항을 비튼 경우가 여기서 나온다.
- **"같은 에이전트"가 리뷰한 작업.** 단독 운영 설정이거나 다른 쪽의 사용량 한도로 같은 모델의 새 세션이 리뷰한 것이다. 더 꼼꼼히 본다.
- **리뷰가 "고침 n회" 뒤에 통과한 작업.** 리뷰어가 무엇을 지적했고 어떻게 고쳐졌는지(또는 구현 에이전트가 지적이 틀렸다고 설명하고 넘어갔는지) 작업 문서의 보고서에서 확인한다.
- **증거가 없는 루프, 화면 갈무리가 0장인 루프.** 증거는 합칠 때 스크립트가 쓴다. 없으면 정상 경로로 합쳐진 것이 아니다.
- **"루프 스크립트가 만든 것으로 보이지 않는 커밋"** 경고. 누가 통합 브랜치를 직접 건드렸다는 뜻일 수 있다. 그 커밋을 `git show` 로 본다.
- 보고서의 "합치기 전 테스트 실행이 만든 변경은 버렸다" 항목. 유니티가 저절로 고친 파일이 대부분이지만, 매번 같은 파일이 나오면 그 파일을 main 에 넣어 두어야 한다고 알린다.

### 3. 작업마다 확인한다

스크립트 출력의 "3. 작업별 자료"에 작업마다 변경 범위, 바뀐 파일, 완료 조건, 새 테스트 이름, 하지 말 것, 가정, 보고서 원문이 있다. 이것은 자료일 뿐이고 **판단은 직접 코드를 읽고 한다.** 작업마다 그 범위의 변경을 읽는다.

```
git diff <이전 커밋> <완료 커밋>                    # 스크립트가 작업마다 적어 준다
git show <대상 SHA>:docs/history/<문서이름>.md      # 작업 문서 원본
git show <대상 SHA>:<경로>                         # 파일 전체
```

작업이 많으면 전부 같은 깊이로 볼 수 없다. **깊게 볼 작업을 고른다**: 시도가 많은 것, 같은 에이전트가 리뷰한 것, 리뷰가 고침을 요구했던 것, 화면 코드나 다른 기능의 파일을 건드린 것, 가정이 많은 것. 나머지는 리뷰어의 표에서 조건 두세 개를 뽑아 실제 테스트와 맞는지 확인한다 (표본 확인). 어느 작업을 깊게 봤고 어느 작업을 표본으로 봤는지 결과에 적는다.

**완료 조건 앞의 표시 읽는 법.** `make-tasks` 는 화면 작업의 완료 조건 앞에 표시를 붙인다.

| 표시 | 뜻 | 리뷰에서 할 일 |
| --- | --- | --- |
| `[테스트]` 또는 표시 없음 | 에딧 모드 테스트로 판정한다 | 대응하는 테스트를 찾는다. 없으면 "빠짐" |
| `[플레이 모드]` | 실제 실행이 필요한 것을 플레이 모드 테스트로 판정한다 | `Assets/Tests/PlayMode/` 에서 대응하는 테스트를 찾는다. 없으면 "빠짐" |
| `[컴파일]` | 컴파일되고 기존 테스트가 모두 통과한다. 루프가 이미 판정했다 (플레이 모드의 `GameBootTests` 가 게임이 오류 없이 켜지는 것까지 본다) | 테스트를 찾지 않는다. 표에는 "루프가 판정"이라고 적는다 |
| `[사람 확인]` | 보기 좋은지, 위치가 맞는지처럼 기계가 판정할 수 없는 것 | 테스트를 찾지 않는다. **화면 갈무리로 확인할 수 있으면 여기서 확인하고**, 갈무리로 알 수 없으면 "사람이 직접 봐야 하는 것"에 옮긴다 |

**보고서 읽는 법.** 보고서는 `## 보고서` 아래에 정해진 소제목 다섯 개로 적힌다: `### 한 일`, `### 바뀐 파일`, `### 가정`, `### 사람이 확인할 것`, `### 테스트 결과`. 스크립트는 이 소제목을 먼저 찾고, 없으면 어림으로 찾은 뒤 어느 쪽으로 찾았는지 적어 준다. "어림으로 찾음"이나 "찾지 못함"이면 보고서 원문을 직접 읽어 빠진 것이 없는지 확인한다. 리뷰가 고침을 요구했던 작업은 구현 에이전트가 "지적이 틀린 이유"를 `### 가정` 아래에 적었을 수 있다.

작업마다 다섯 가지를 본다.

1. **리뷰어의 "완료 조건별 테스트" 표가 맞는가.** 증거 보고서의 표를 믿지 않고 확인한다. 표에 "있음"으로 적힌 테스트를 테스트 코드에서 찾아, 본문의 검사(Assert)가 그 조건의 상황과 기대 결과(숫자 포함)를 실제로 확인하는지 읽는다. 표에 없는 완료 조건이 있는지도 센다. 결과는 조건별 표로 적는다: 있음 / 약함(이름은 맞는데 검사가 비었거나 다른 것을 확인함) / 빠짐. 리뷰어의 판정과 다르면 그 차이를 적는다.
2. **보고서의 한 일과 실제 변경이 맞는가.** 보고서에 "했다"고 적힌 것이 코드에 정말 있는지, 보고서에 없는 변경이 끼어 있는지 본다. 스크립트의 "보고서와 실제 변경 비교"는 파일 이름만 어림한 것이니 출발점으로만 쓴다. 요구사항 중 구현되지 않은 것도 여기서 찾는다.
3. **"가정"을 전부 모은다.** 줄이거나 고르지 말고 전부 보여 준다. 사람이 몰랐던 결정이 여기 있다. 보고서에 가정이 없다고 되어 있는데 코드에 임시 수치나 스스로 정한 동작이 보이면 "적히지 않은 가정"으로 따로 적는다. 가정마다 사양(`docs/spec/`)과 어긋나는 것이 있으면 표시한다. 리뷰어가 통과시킨 가정이라도 사람이 판단할 것은 사람에게 보인다.
4. **"하지 말 것" 범위를 건드렸는가.** 작업 문서의 "하지 말 것" 항목을 하나씩 놓고, 바뀐 파일과 변경 내용이 그 범위에 들어가는지 본다. 건드렸으면 무엇이 달라졌는지(예: 다른 기능의 공개 메서드 동작이 바뀜)까지 적는다. 앞 작업이 만든 코드를 뒤 작업이 고친 경우가 여기에 자주 걸린다. 다른 기능의 내부 코드를 직접 고친 것(연결 지점을 거치지 않은 것)도 여기서 적는다.
5. **관문 예외를 썼는가.** 작업 문서에 `## 관문 예외` 칸이 있으면(`asmdef`, `scene`, `settings`), 그 작업은 평소 금지된 변경을 사람 확인 없이 합친 것이다. 무엇을 바꿨는지 반드시 보여 준다.

보류됐다가 풀린 작업은 문서에 `## 보류 사유` 와 `## 답변` 이 남아 있다. 사람이 한 답대로 구현됐는지도 본다.

### 4. 규칙 위반을 다시 찾는다

합쳐진 루프는 관문을 통과했다. 그래도 스크립트 출력의 "4. 규칙 점검"이 같은 종류의 검사를 **범위 전체**에 다시 돌린다. 여기서 `[위반]` 이 나오면 셋 중 하나다: 작업 문서의 관문 예외로 허용된 것, 관문이 놓친 것, 루프 밖에서 들어온 변경. 어느 것인지 가려 적는다. `[위반]` 과 `[확인 필요]` 항목은 **가리키는 줄을 직접 열어 보고** 진짜인지 확인한 뒤 보고한다. 주석이나 문자열 안의 낱말처럼 잘못 잡힌 것은 빼고, 뺀 이유를 한 줄 적는다.

같은 고정 범위의 자료와 공통 관문 검사를 다시 볼 수 있다 (읽기만 한다).

```
python tools/skills/review_scan.py --base <기준 SHA> --head <대상 SHA>
```

| 점검 | 기준 | 스크립트가 못 잡는 것 (직접 본다) |
| --- | --- | --- |
| `PlumSword.Core` 에 유니티 의존 | `Assets/Scripts/Core/` 는 순수 C#. `UnityEngine`, `Time.*`, `Debug.Log`, `DateTime.Now`, `PlayerPrefs`, `Mathf` 등을 쓰지 않는다 | 반대 방향: 계산이 Game(화면 코드)에 들어간 것. 화면 코드는 입력 전달과 표시만 한다 |
| 어셈블리 정의 변경 | `.asmdef` 는 바꾸지 않는다. 바꿨다면 작업 문서에 관문 예외(`asmdef`)와 근거가 있고 `docs/dev/architecture.md` 도 함께 고쳐야 한다 | `noEngineReferences` 를 끄거나 참조를 늘린 것은 특히 무겁게 본다 |
| 씬·프리팹·설정 변경 | `.unity`, `.prefab`, `.asset`, `ProjectSettings/`, `Packages/` 는 고치지 않는다 (관문 예외 `scene`, `settings`). 화면은 코드로 조립한다 | 예외로 허용됐더라도 합치기 전에 사람이 알아야 한다 |
| `.meta` 짝 | `Assets/` 아래 모든 파일·폴더에 `.meta` 가 있다 | — |
| 루프 자체를 바꾸는 변경 | `tools/loop/`, `tools/skills/`, `CLAUDE.md`, `AGENTS.md`, `.claude/`, `.agents/`, `.codex/`, `.github/`, `.gitignore`, `docs/dev/loop.md`, `docs/dev/workflow.md`, 지난 `docs/history/` 기록, `docs/evidence/` 를 스크립트 아닌 쪽이 고친 것 | 관문이 예외 없이 막는 것이다. 여기서 보이면 사람이 main 에서 직접 고친 것이거나(정상), 루프 밖에서 들어온 것이다. 어느 쪽인지 커밋을 보고 가린다. 루프가 자기 검사 장치를 고친 것이면 가장 무거운 위반이다 |
| 테스트를 지우거나 약하게 만든 변경 | 있던 테스트 삭제, `[Ignore]`, 검사(Assert) 삭제·완화, 검사 없는 테스트. 작업 단계마다 비교하므로 **앞 작업이 쓴 테스트를 뒤 작업이 약하게 만든 것**도 잡는다 | 기대값을 구현에 맞춰 바꾼 것, 조건을 느슨하게 한 것 (`EqualTo` → `LessThanOrEqualTo` 등). 관문은 검사 **수**가 줄어든 것만 막고, 뜻이 약해진 것은 "확인 필요"로 넘긴다. 스크립트가 지워진 검사와 새 검사를 나란히 보여 주니 뜻이 약해졌는지 읽고 판단한다 |
| 줄 끝만 바뀐 파일 | 내용은 같고 CRLF/LF 만 바뀐 파일. 규칙 위반은 아니지만 올리면 main 의 파일이 통째로 바뀐 것으로 남는다 | 스크립트는 이런 파일을 다른 목록과 통계에서 뺀다. 수가 많으면 에이전트의 편집 도구나 깃 설정(`core.autocrlf`) 문제이니 따로 알린다 |

규칙 위반은 서로 이어져 있는 경우가 많다. 예를 들어 Core 가 유니티를 쓰는데도 합쳐졌다면, 그것을 막는 세 장치(`noEngineReferences`, `CoreAssemblyTests`, 관문)가 같이 뚫렸다는 뜻이다. 위반 하나를 찾으면 **"이것이 왜 테스트와 관문에 안 걸렸는가"** 를 따라가 본다. 관문이 놓친 것이 확인되면, 관문 규칙(`tools/loop/loop_gate.py`)을 고쳐야 한다고 사용자에게 알린다 (이 스킬이 고치지 않는다. 루프 자체는 사람이 대화에서 고친다).

이 밖에 `docs/dev/architecture.md` 의 다른 규칙도 눈에 띄면 적는다: 네임스페이스가 폴더와 맞는지, 파일 하나에 공개 타입 하나인지, 테스트 이름이 `<상황>_<기대 결과>` 인지, 새 연결 지점이 `docs/spec/` 에 반영됐는지. 이런 것은 가벼운 지적으로 분류한다.

### 5. 테스트 결과를 확인한다

루프는 작업마다, 그리고 합치기 직전에 전체 테스트를 통과해야 합친다. 합계는 증거 보고서와 `results.json` 에 있다. 그래도 사용자가 원하면 통합 브랜치 끝에서 한 번 더 돌려 확인한다. **먼저 돌릴지 묻는다** (몇 분 걸린다).

- 루프가 끝나면 worktree 는 통합 브랜치 끝에 detached 상태로 있다. 스크립트 출력의 "worktree" 절이 "테스트 다시 돌리기: 가능"일 때만 돌린다.
  ```
  python tools/loop/run_unity_tests.py --project <worktree 경로>
  ```
  종료 코드 0 이면 통과, 2 는 환경 문제(유니티를 못 찾음, 에디터가 그 폴더를 열고 있음)라 판정할 수 없음, 그 밖은 실패다. 에딧 모드와 플레이 모드를 모두 돌린다.
- **루프가 진행 중이면 돌리지 않는다.** 루프가 그 worktree 를 쓰고 있다.
- worktree 가 확인할 대상의 끝이 아니거나 변경이 남아 있으면 돌리지 않는다. 돌려도 그 대상의 결과가 아니다. worktree 를 직접 옮기지도 않는다. 사실만 알린다.
- 돌리지 않았으면 결과에 "다시 돌리지 않음 (루프가 합치기 전에 전체 테스트 통과를 확인함. 증거의 합계: …)"이라고 적는다. 돌리지 않은 것을 직접 확인했다고 적지 않는다.

### 6. 결론을 낸다

셋 중 하나로 정한다.

| 결론 | 언제 |
| --- | --- |
| **올려도 됨** | 위반이 없고, 완료 조건마다 테스트가 있고(리뷰어의 표가 맞고), 가정이 받아들일 만하다 (가벼운 지적만 있음) |
| **올리고 후속 작업으로 고침** | 올려도 main 이 망가지지는 않지만 빠진 것이 있다: 테스트 없는 완료 조건, 약한 테스트, 사양과 어긋난 가정, 가벼운 규칙 위반. 통합 브랜치에는 이미 다음 루프가 쌓였을 수 있으므로, 고칠 때는 되돌리기보다 후속 작업 문서로 고치는 쪽을 먼저 권한다 |
| **올리지 않음 (어디까지 올릴지 정함)** | main 에 들어가면 안 되는 것이 있다: 루프가 자기 자신을 바꾼 변경, 구조 규칙을 무너뜨린 변경(Core 의 유니티 의존, `noEngineReferences` 해제), 테스트를 지우거나 무력화한 변경, 다시 돌린 테스트의 실패, "하지 말 것" 침범으로 다른 기능이 망가진 것 |

- **루프 단위로 판정한다.** 루프 하나(묶음 하나)는 병합 커밋 하나라 통째로 올라가거나 통째로 빠진다. 작업 하나만 골라 올릴 수 없으므로, 가장 나쁜 작업이 그 루프의 결론을 정한다.
- 범위에 루프가 여러 개면 **어디까지 올릴 수 있는지**를 적는다. 문제가 있는 루프 앞까지만 올릴 수 있다 (그 루프의 SHA까지 누적 리뷰하고 `git merge --ff-only <승인 SHA>`). 문제가 있는 루프 뒤의 루프는 그 위에 쌓여 있어, 문제 루프를 빼고는 올릴 수 없다. 그럴 때의 선택지(그대로 올리고 후속 작업으로 고친다 / 문제 루프부터 뒤를 버리고 다시 처리한다)를 결과와 함께 보여 주고 사용자가 고르게 한다.
- 근거는 **중요한 순서로** 적는다. 위반 → 빠지거나 약한 테스트(리뷰어의 표와 다른 것) → 사람이 판단할 가정 → 가벼운 지적.
- **사람이 직접 봐야 하는 것**을 따로 적는다. 스크립트 출력의 "5. 사람이 직접 볼 후보"에 세 가지가 모여 있다: 완료 조건의 `[사람 확인]`, 보고서의 "사람이 확인할 것", 바뀐 화면 코드·리소스. 앞의 둘은 빼지 말고 전부 다루되, **화면 갈무리로 확인한 것은 확인했다고 적고 갈무리 파일을 댄다.** 갈무리는 실행 후 1초·10초·30초의 멈춘 화면이라, 누르는 동작, 움직임, 속도감, 수치 균형은 알 수 없다. 그런 것은 에디터에서 무엇을 열고 무엇을 눌러 무엇을 보면 되는지 구체적으로 적는다. 볼 것이 없으면 없다고 적는다.
- 확인하지 못한 것은 못 했다고 적는다 (예: 테스트 다시 돌리지 않음, 에디터에서 실행해 보지 않음, 작업 n개는 표본만 확인함).

결과는 아래 "결과 모양"대로 보여 준다.

### 7. 올리는 명령을 보여 주고, 시키면 올린다

스크립트가 출력한 고정 대상 SHA의 명령을 보여 준다. main부터 그 SHA까지 누적 범위 전체를 리뷰한 경우에만 반영 대상으로 제안한다. 루프가 계속 돌아도 새 커밋은 이번 승인 범위에 포함되지 않는다.

```
git merge --ff-only <리뷰하고 승인한 대상 SHA>
```

되돌리는 명령도 함께 보여 준다 (실행하지 않는다. 자세한 경우는 `docs/dev/loop.md` "되돌릴 때"):

```
git revert -m 1 loop-merged/<루프>                                 # (main 에 올린 뒤, 푸시 전) 이 루프만 되돌린다
git branch -f integration loop-merged/<마지막으로 남길 루프>         # (루프를 멈춘 뒤, main 에 올리기 전) 그 뒤 루프를 통합 브랜치에서 버린다
```

- 올린 뒤 에디터에서 플레이해 "사람이 직접 봐야 하는 것"을 확인하고, 그다음에 푸시하라고 알린다.
- **되돌리는 명령**(`git revert`, `git branch -f integration …`, `git branch -D rejected/…`)은 보여 주기만 한다. 되돌릴 수 없거나 루프를 멈춰야 하는 일이라 이 스킬이 하지 않는다. 통합 브랜치를 되돌리는 방법과 주의할 점은 스크립트 출력과 `docs/dev/loop.md` 에 있다.
- **고칠 것이 있으면** `make-tasks` 스킬로 후속 작업을 만들라고 안내한다. 후속 작업에 넣을 내용(무엇을 고칠지, 어느 완료 조건의 테스트가 빠졌는지)을 목록으로 정리해 주면 `make-tasks` 에 그대로 넘길 수 있다. 사양 자체가 바뀌어야 하면 `plan-feature` 를 먼저 안내한다.
- 관문이나 리뷰가 놓친 것이 있었으면, 같은 것이 다시 통과하지 않도록 무엇을 고치면 되는지(관문 규칙, 리뷰 프롬프트, 작업 문서의 완료 조건 쓰는 법) 한 줄로 알린다.

**사용자가 분명히 "올려 줘"라고 하면** 아래 순서로 한다. 하나라도 걸리면 멈추고 알린다.

1. 원본 프로젝트가 main이고 작업 트리에 미커밋 변경이 없는지 확인한다. 브랜치를 바꾸거나 변경을 버리지 않는다.
2. 리뷰 결론·사람이 확인할 항목·반영할 정확한 대상 SHA에 대한 사용자 승인을 확인한다. 결론이 "올리지 않음"이면 이유를 알리고 명시적 재승인 없이 반영하지 않는다.
3. `git rev-parse HEAD`가 리뷰 때 기록한 main SHA와 같은지 확인한다. 다르면 새 main을 기준으로 다시 리뷰한다. `git merge-base --is-ancestor <대상 SHA> integration`으로 대상이 여전히 통합 브랜치에 포함되는지도 확인한다. 제외됐다면 반영하지 않는다.
4. `git merge --ff-only <승인한 대상 SHA>`만 실행한다. 실패하면 다른 병합 방식으로 바꾸지 않는다. integration이나 태그를 다시 해석한 값으로 바꾸지 않는다.
5. HEAD가 승인한 SHA인지 확인하고 결과를 보여 준다. 푸시는 하지 않는다. 에디터 확인과 푸시는 사람이 한다.

## 결과 모양

아래 틀로 보여 준다. 결론을 맨 위에 둔다. 내용이 없는 절은 "없음"이라고 적고 절 자체는 남긴다 (봤는데 없다는 것과 안 본 것을 구분하기 위해서다).

```markdown
# 루프 리뷰: <기준 SHA>..<대상 SHA> (루프 n개, 작업 m건)

## 결론: 올려도 됨 / 올리고 후속 작업으로 고침 / 올리지 않음
한두 문장으로 이유. 루프가 여러 개면 어디까지 올릴 수 있는지.

### 근거 (중요한 순서)
1. [위반] ... (파일:줄)
2. [빠진 테스트] 작업 <이름>의 완료 조건 n) ... (리뷰어는 "있음"으로 적었다)
3. [가정] ...

### 사람이 직접 봐야 하는 것
- 화면 갈무리로 확인한 것: 무엇을, 어느 파일에서
- 에디터에서 봐야 하는 것: 무엇을 열고, 무엇을 눌러, 무엇을 보면 되는지

### 확인하지 못한 것
- 테스트 다시 돌리지 않음 / 작업 n개는 표본만 확인함 / ...

## 루프 요약
| 루프 (태그) | 묶음 | 작업 | 테스트 | 판정 |
(main 대비 통계 한 줄)

## 작업별 확인
### <문서이름> (깊게 봄 / 표본 확인)
- 구현과 리뷰: 에이전트, 시도, 리뷰어(교차인지), 고침 횟수
- 보고서와 실제 변경: 맞음 / 다름 (무엇이)
- 완료 조건과 테스트:
  | 완료 조건 | 대응하는 테스트 | 리뷰어의 판정 | 내 판정 |
  (판정: 있음 / 약함 / 빠짐. [컴파일] 은 "루프가 판정", [사람 확인] 은 "사람 확인"으로 적고 빠짐으로 세지 않는다)
- 하지 말 것: 지킴 / 건드림 (무엇을)
- 관문 예외: 없음 / 있음 (무엇을 바꿨는지)
- 가정: (전부)

## 가정 모음
작업 구분 없이 전부. 사람이 판단해야 하는 것에는 표시.

## 규칙 점검
| 점검 | 결과 | 근거 |

## 테스트
다시 돌린 결과, 또는 돌리지 않은 이유와 증거에 적힌 합계.

## 다음에 할 일
올리는 명령, 또는 후속 작업으로 만들 것 목록 (make-tasks). 관문·리뷰가 놓친 것이 있으면 무엇을 고칠지.
```

## 스크립트가 안 될 때

같은 내용을 손으로 본다 (모두 조회만 한다). 먼저 `git rev-parse main`과 `git rev-parse integration`으로 기준·대상 SHA를 고정한다. 부분 루프 태그도 SHA로 풀어 기록한 뒤 사용한다.

```
git log --first-parent --merges --oneline <기준 SHA>..<대상 SHA>      # 올리지 않은 루프 (병합 커밋)
git for-each-ref --format="%(refname:short)" refs/tags/loop-merged/ refs/heads/rejected/ refs/heads/loop/
git show <대상 SHA>:docs/evidence/index.md
git diff --stat <기준 SHA>..<대상 SHA>
git diff --name-status <기준 SHA>..<대상 SHA>
git diff --name-status --diff-filter=A <기준 SHA>..<대상 SHA> -- docs/history   # 이 범위에서 끝난 작업
git diff loop-merged/<루프>^1 loop-merged/<루프>                   # 루프 하나의 변경
git ls-tree -r --name-only <대상 SHA> -- Assets                  # .meta 짝 확인
python tools/skills/review_scan.py --base <기준 SHA> --head <대상 SHA>     # 관문
```

- 상태 파일: `.loop/state.json` (`status`: active / finished / rejected, `loop_branch`, `bundle`, `processed`, `merged_into`, `tag`, `evidence`)
- 작업별 에이전트·시도·리뷰: 작업 문서 끝의 `## 루프 기록`
- 통합 브랜치 이름, 태그 앞부분, worktree 위치: `tools/loop/loop_config.json` 의 `integration_branch`, `merge_tag_prefix`, `worktree_path`

## 예행 연습

`--root <폴더>` 로 다른 폴더(복제본)를 볼 수 있다. 복제본에서 가짜 에이전트로 루프를 돌려 통합 브랜치와 증거를 만든 뒤 스킬을 따라가 볼 때 쓴다.
