# 루프 리뷰 (review-loop)

자동 개발 루프는 묶음 하나를 `loop/<날짜-시간>` 브랜치에 쌓고, 끝나면 디스코드로 "루프 종료"를 알린다. 루프 스크립트는 main 에 합치지 않는다. 사람이 확인하고 직접 합치며, 합쳐야 다음 묶음이 시작된다. 이 스킬은 그 **"합치기 전 확인"** 을 돕는다.

루프 안의 에이전트는 사람에게 묻지 못한 채 일했다. 그래서 애매한 것은 스스로 정했고, 그 결정은 보고서의 "가정"에만 적혀 있다. 테스트가 통과했다는 것은 "에이전트가 쓴 테스트가 통과했다"는 뜻일 뿐이다. 리뷰에서 볼 것은 **테스트가 완료 조건을 정말 검사하는지**와 **사람이 몰랐던 결정이 무엇인지**다.

완료된 작업 문서의 원본(보고서, 가정, 루프 기록 포함)은 루프 브랜치의 `docs/history/<문서이름>.md` 에 있다. 루프 동작의 기준은 `docs/dev/loop.md`, 코드 규칙의 기준은 `docs/dev/architecture.md` 다.

## 지킬 것

- **코드를 고치지 않는다.** 문제를 찾으면 보고만 한다. 고칠 것은 후속 작업으로 넘긴다 (7단계).
- 깃은 **조회만** 한다: `git show`, `git diff`, `git log`, `git ls-tree`, `git merge-base`, `git for-each-ref`, `git status`. 체크아웃·커밋·브랜치 삭제는 하지 않는다. 루프 브랜치의 파일은 체크아웃하지 말고 `git show <브랜치>:<경로>` 로 읽는다.
- 예외는 하나뿐이다. **사용자가 분명히 "합쳐 줘"라고 하면** main 에 합친다 (7단계). 결론이 "합쳐도 됨"이라고 해서 알아서 합치지 않는다.
- **푸시는 하지 않는다.**
- `tasks/` 와 `.loop/` 는 읽기만 한다. `.env` 는 읽지 않는다.
- 루프가 진행 중일 때는 worktree(`../PlumSwordIdle_loop`)에서 아무것도 실행하지 않는다.

## 순서

### 1. 확인할 루프 브랜치를 찾는다

프로젝트 폴더에서 보조 스크립트를 실행한다. 읽기만 하는 스크립트다.

```
python .claude/skills/review-loop/review_scan.py
```

스크립트는 `.loop/state.json` 과 main 에 안 합쳐진 `loop/*` 브랜치를 보고 확인할 브랜치를 고른 뒤, 아래 단계에 쓸 자료를 한 번에 출력한다. 출력의 "1. 확인할 루프 브랜치"를 먼저 본다.

| 상황 | 할 일 |
| --- | --- |
| 안 합쳐진 루프 브랜치가 없다 | 리뷰할 것이 없다고 알리고 끝낸다 |
| 여러 개다 | 목록을 보여 주고 어느 것을 볼지 묻는다. 고르면 `--branch loop/<날짜-시간>` 으로 다시 실행한다 |
| 루프가 **진행 중(active)** 이다 | 진행 중이라는 사실과 남은 작업(스크립트가 적어 준다)을 알리고, **그래도 지금까지의 내용을 볼지 묻는다.** 본다고 하면 계속하되, 결과 맨 위에 "중간 상태"라고 적고 5단계 테스트는 돌리지 않으며 결론은 "아직 합칠 수 없음"으로 둔다 |
| 끝난 루프(finished)가 하나다 | 그대로 진행한다 |

진행 중인 루프에 보류(blocked)만 남아 있으면 `answer-blocked` 로 답해야 루프가 끝난다는 것도 알린다.

### 2. 묶음 전체를 요약한다

스크립트 출력의 "2. 묶음 요약"을 정리한다: 처리한 작업 목록, 작업별 에이전트와 시도 횟수, main 대비 바뀐 파일 통계.

- 시도 횟수가 많은 작업(3회 이상)은 눈여겨본다. 테스트를 통과시키려고 테스트나 요구사항을 비튼 경우가 여기서 나온다.
- "루프를 딴 뒤 main 에 커밋이 더 생겼다"는 경고가 있으면, 합칠 때 병합 커밋이 생기고 충돌할 수 있다고 알린다.
- "마지막 작업 완료 커밋 뒤에 커밋이 더 있다", "상태 파일의 처리 목록과 기록이 다르다"는 경고는 루프 밖에서 누가 브랜치를 건드렸다는 뜻일 수 있다. 그 커밋을 `git show` 로 본다.

### 3. 작업마다 확인한다

스크립트 출력의 "3. 작업별 자료"에 작업마다 변경 범위, 바뀐 파일, 완료 조건, 새 테스트 이름, 하지 말 것, 가정, 보고서 원문이 있다. 이것은 자료일 뿐이고 **판단은 직접 코드를 읽고 한다.** 작업마다 그 범위의 변경을 읽는다.

```
git diff <이전 커밋> <완료 커밋>                 # 스크립트가 작업마다 적어 준다
git show <루프 브랜치>:docs/history/<문서이름>.md   # 작업 문서 원본
git show <루프 브랜치>:<경로>                     # 파일 전체
```

**완료 조건 앞의 표시 읽는 법.** `make-tasks` 는 화면 작업의 완료 조건 앞에 표시를 붙인다. 표시에 따라 확인하는 방법이 다르다.

| 표시 | 뜻 | 리뷰에서 할 일 |
| --- | --- | --- |
| `[테스트]` 또는 표시 없음 | 에딧 모드 테스트로 판정한다 | 대응하는 테스트를 찾는다. 없으면 "빠짐" |
| `[플레이 모드]` | 실제 실행이 필요한 것을 플레이 모드 테스트로 판정한다 | `Assets/Tests/PlayMode/` 에서 대응하는 테스트를 찾는다. 없으면 "빠짐" |
| `[컴파일]` | 컴파일되고 기존 테스트가 모두 통과한다. 루프가 이미 판정했다 | 테스트를 찾지 않는다. "빠진 테스트"로 세지 않는다. 표에는 "루프가 판정"이라고 적는다 |
| `[사람 확인]` | 보기 좋은지, 위치가 맞는지처럼 기계가 판정할 수 없는 것 | 테스트를 찾지 않는다. "빠진 테스트"로 세지 않는다. **"에디터에서 직접 봐야 하는 것"에 그대로 옮긴다** |

스크립트가 이 표시를 읽어 조건마다 어떻게 판정하는지 적어 주고, `[컴파일]`·`[사람 확인]`뿐인 작업은 새 테스트가 없어도 문제 삼지 않는다. `[사람 확인]`뿐이고 `[컴파일]`조차 없는 작업은 작업 문서가 잘못 만들어진 것이니 그렇게 알린다.

**보고서 읽는 법.** 보고서는 `## 보고서` 아래에 정해진 소제목 다섯 개로 적힌다: `### 한 일`, `### 바뀐 파일`, `### 가정`, `### 사람이 확인할 것`, `### 테스트 결과`. 스크립트는 이 소제목을 먼저 찾고, 없으면(예전 양식이거나 에이전트가 양식을 따르지 않았으면) 어림으로 찾은 뒤 어느 쪽으로 찾았는지 적어 준다. "어림으로 찾음"이나 "찾지 못함"이면 보고서 원문을 직접 읽어 빠진 것이 없는지 확인한다.

작업마다 네 가지를 본다.

1. **보고서의 한 일과 실제 변경이 맞는가.** 보고서에 "했다"고 적힌 것이 코드에 정말 있는지, 보고서에 없는 변경이 끼어 있는지 본다. 스크립트의 "보고서와 실제 변경 비교"는 파일 이름만 어림한 것이니 출발점으로만 쓴다. 요구사항 중 구현되지 않은 것도 여기서 찾는다.
2. **완료 조건마다 대응하는 테스트가 있는가.** 보고서에 "완료 조건 전부에 테스트를 썼다"고 적혀 있어도 믿지 않고 센다. 테스트가 필요한 완료 조건(`[테스트]`, `[플레이 모드]`, 표시 없음)을 하나씩 놓고, 그 조건을 실제로 검사하는 테스트를 테스트 코드에서 찾는다. 이름만 보지 말고 본문의 검사(Assert)가 그 조건을 확인하는지 읽는다. 결과는 조건별 표로 적는다. 대응하는 테스트가 없으면 **어느 조건이 빠졌는지** 적는다. 이름은 맞는데 검사가 비어 있거나 다른 것을 확인하면 "약함"으로 적는다.
3. **"가정"을 전부 모은다.** 줄이거나 고르지 말고 전부 보여 준다. 사람이 몰랐던 결정이 여기 있다. 스크립트가 "가정 항목을 찾지 못했다"고 하면 보고서 원문에서 직접 찾는다. 보고서에 가정이 없다고 되어 있는데 코드에 임시 수치나 스스로 정한 동작이 보이면 "적히지 않은 가정"으로 따로 적는다. 가정마다 사양(`docs/spec/`, 공용 문서)과 어긋나는 것이 있으면 표시한다.
4. **"하지 말 것" 범위를 건드렸는가.** 작업 문서의 "하지 말 것" 항목을 하나씩 놓고, 바뀐 파일과 변경 내용이 그 범위에 들어가는지 본다. 건드렸으면 무엇이 달라졌는지(예: 다른 기능의 공개 메서드 동작이 바뀜)까지 적는다. 앞 작업이 만든 코드를 뒤 작업이 고친 경우가 여기에 자주 걸린다. 다른 기능의 내부 코드를 직접 고친 것(연결 지점을 거치지 않은 것)도 여기서 적는다.

보류됐다가 풀린 작업은 문서에 `## 보류 사유` 와 `## 답변` 이 남아 있다. 사람이 한 답대로 구현됐는지도 본다.

### 4. 규칙 위반을 찾는다

스크립트 출력의 "4. 규칙 점검"이 기계로 찾을 수 있는 것을 찾아 준다. `[위반]` 과 `[확인 필요]` 항목은 **가리키는 줄을 직접 열어 보고** 진짜인지 확인한 뒤 보고한다. 주석이나 문자열 안의 낱말처럼 잘못 잡힌 것은 빼고, 뺀 이유를 한 줄 적는다.

| 점검 | 기준 | 스크립트가 못 잡는 것 (직접 본다) |
| --- | --- | --- |
| `PlumSword.Core` 에 유니티 의존 | `Assets/Scripts/Core/` 는 순수 C#. `UnityEngine`, `Time.*`, `Debug.Log`, `DateTime.Now`, `PlayerPrefs`, `Mathf` 등을 쓰지 않는다 | 반대 방향: 계산이 Game(화면 코드)에 들어간 것. 화면 코드는 입력 전달과 표시만 한다 |
| 어셈블리 정의 변경 | `.asmdef` 는 바꾸지 않는다. 바꿨다면 작업 문서에 근거가 있고 `docs/dev/architecture.md` 도 함께 고쳐야 한다 | `noEngineReferences` 를 끄거나 참조를 늘린 것은 특히 무겁게 본다 |
| 씬·프리팹·설정 변경 | `.unity`, `.prefab`, `.asset`, `ProjectSettings/`, `Packages/` 는 고치지 않는다. 화면은 코드로 조립한다 | 테스트 실행이 저절로 바꾼 것일 수도 있다. 그래도 합치기 전에 사람이 알아야 한다 |
| `.meta` 짝 | `Assets/` 아래 모든 파일·폴더에 `.meta` 가 있다 | — |
| 루프 자체를 바꾸는 변경 | `tools/loop/`, `CLAUDE.md`, `AGENTS.md`, `.claude/`, `.gitignore`, 지난 `docs/history/` 기록 | 작업 문서가 그 변경을 시킨 것이 아니면 합치지 않는다. 루프가 자기 검사 장치를 고치는 것은 가장 무거운 위반이다 |
| 테스트를 지우거나 약하게 만든 변경 | 있던 테스트 삭제, `[Ignore]`, 검사(Assert) 삭제·완화, 검사 없는 테스트. 작업 단계마다 비교하므로 **앞 작업이 쓴 테스트를 뒤 작업이 약하게 만든 것**도 잡는다 | 기대값을 구현에 맞춰 바꾼 것, 조건을 느슨하게 한 것 (`EqualTo` → `LessThanOrEqualTo` 등). 스크립트가 지워진 검사와 새 검사를 나란히 보여 주니 뜻이 약해졌는지 읽고 판단한다 |
| 줄 끝만 바뀐 파일 | 내용은 같고 CRLF/LF 만 바뀐 파일. 규칙 위반은 아니지만 합치면 main 의 파일이 통째로 바뀐 것으로 남는다 | 스크립트는 이런 파일을 다른 목록과 통계에서 뺀다. 수가 많으면 에이전트의 편집 도구나 깃 설정(`core.autocrlf`) 문제이니 따로 알린다 |

규칙 위반은 서로 이어져 있는 경우가 많다. 예를 들어 Core 가 유니티를 쓰는데도 테스트가 통과했다면, 그것을 막는 두 장치(`noEngineReferences`, `CoreAssemblyTests`)가 같이 꺼졌다는 뜻이다. 위반 하나를 찾으면 **"이것이 왜 테스트에 안 걸렸는가"** 를 따라가 본다.

이 밖에 `docs/dev/architecture.md` 의 다른 규칙도 눈에 띄면 적는다: 네임스페이스가 폴더와 맞는지, 파일 하나에 공개 타입 하나인지, 테스트 이름이 `<상황>_<기대 결과>` 인지, 새 연결 지점이 `docs/` 에 반영됐는지. 이런 것은 가벼운 지적으로 분류한다.

### 5. 테스트 결과를 확인한다

루프는 작업마다 전체 테스트를 통과해야 완료로 처리한다. 그래도 사용자가 원하면 루프 브랜치 끝에서 한 번 더 돌려 확인한다. **먼저 돌릴지 묻는다** (첫 실행은 전체 임포트 때문에 오래 걸릴 수 있다).

- 루프가 끝나면 worktree 는 루프 브랜치 끝에 detached 상태로 있다. 스크립트 출력의 "worktree" 절이 "테스트 다시 돌리기: 가능"일 때만 돌린다.
  ```
  python tools/loop/run_unity_tests.py --project <worktree 경로>
  ```
  종료 코드 0 이면 통과, 2 는 환경 문제(유니티를 못 찾음, 에디터가 그 폴더를 열고 있음)라 판정할 수 없음, 그 밖은 실패다.
- **루프가 진행 중이면 돌리지 않는다.** 루프가 그 worktree 를 쓰고 있다.
- worktree 가 루프 브랜치 끝이 아니거나 변경이 남아 있으면 돌리지 않는다. 돌려도 이 브랜치의 결과가 아니다. worktree 를 직접 옮기지도 않는다. 사실만 알린다.
- 돌리지 않았으면 결과에 "다시 돌리지 않음 (루프가 작업마다 통과를 확인함)"이라고 적는다. 돌리지 않은 것을 통과했다고 적지 않는다.

### 6. 결론을 낸다

셋 중 하나로 정한다.

| 결론 | 언제 |
| --- | --- |
| **합쳐도 됨** | 위반이 없고, 완료 조건마다 테스트가 있고, 가정이 받아들일 만하다 (가벼운 지적만 있음) |
| **고친 뒤 합침** | 합쳐도 main 이 망가지지는 않지만 빠진 것이 있다: 테스트 없는 완료 조건, 사양과 어긋난 가정, 가벼운 규칙 위반. 합친 뒤 후속 작업으로 고치거나, 고친 뒤 합친다. 둘 중 어느 쪽을 권하는지 적는다 |
| **합치지 않음** | main 에 들어가면 안 되는 것이 있다: 루프 자체를 바꾼 변경, 구조 규칙을 무너뜨린 변경(Core 의 유니티 의존, `noEngineReferences` 해제), 테스트를 지우거나 무력화한 변경, 테스트 실패, 작업 문서의 "하지 말 것" 침범으로 다른 기능이 망가진 것 |

- 루프 브랜치는 통째로 합친다. 작업 하나만 골라 합칠 수 없으므로, **가장 나쁜 작업이 묶음의 결론을 정한다.**
- 근거는 **중요한 순서로** 적는다. 위반 → 빠진 테스트 → 사람이 판단할 가정 → 가벼운 지적.
- **사람이 에디터에서 직접 봐야 하는 것**을 따로 적는다. 화면 모양, 배치, 글자 크기, 플레이 느낌, 수치 균형은 테스트로 판정하지 못한다. 스크립트 출력의 "5. 에디터에서 직접 볼 후보"에 세 가지가 모여 있다: 완료 조건의 `[사람 확인]`, 보고서의 "사람이 확인할 것", 바뀐 화면 코드·리소스. 앞의 둘은 빼지 말고 전부 옮기고, 셋째는 코드를 읽어 볼 것을 더한다. 무엇을 열고 무엇을 눌러 무엇을 보면 되는지 구체적으로 적는다. 볼 것이 없으면 없다고 적는다.
- 확인하지 못한 것은 못 했다고 적는다 (예: 테스트 다시 돌리지 않음, 에디터에서 실행해 보지 않음).

결과는 아래 "결과 모양"대로 보여 준다.

### 7. 합치는 명령을 보여 주고, 시키면 합친다

스크립트 출력의 "6. 명령"을 그대로 보여 준다 (`docs/dev/loop.md` "루프가 끝난 뒤 main 에 합치기" 기준). 프로젝트 폴더의 main 에서 실행한다.

```
git merge loop/<날짜-시간>
git branch -d loop/<날짜-시간>
git branch -d task/<문서이름> ...
```

- 합치고 나면 다음 실행(감시 모드면 다음 확인 때)이 새 루프를 시작한다는 것을 알린다.
- **합치지 않고 버릴 때**의 명령(`git branch -D`, `.loop/state.json` 과 그 루프의 `tasks/done/` 문서 삭제)은 보여 주기만 한다. 되돌릴 수 없는 일이라 이 스킬이 하지 않는다.
- **고칠 것이 있으면** `make-tasks` 스킬로 후속 작업을 만들라고 안내한다. 후속 작업에 넣을 내용(무엇을 고칠지, 어느 완료 조건의 테스트가 빠졌는지)을 목록으로 정리해 주면 `make-tasks` 에 그대로 넘길 수 있다. 사양 자체가 바뀌어야 하면 `plan-feature` 를 먼저 안내한다.

**사용자가 분명히 "합쳐 줘"라고 하면** 아래 순서로 한다. 하나라도 걸리면 멈추고 알린다.

1. 루프가 끝난 상태(finished)인지 확인한다. 진행 중이면 합치지 않는다.
2. 프로젝트 폴더가 main 브랜치에 있는지 확인한다 (`git status`). 아니면 브랜치를 바꾸지 말고 알린다.
3. 결론이 "합치지 않음"이었으면 그 이유를 다시 말하고 정말 합칠지 한 번 더 확인한다.
4. `git merge loop/<날짜-시간>` 을 실행한다. 충돌이 나면 직접 풀지 말고 상태를 알린다 (`git merge --abort` 로 되돌릴 수 있다고 알려 준다).
5. 합쳐졌으면 결과(`git log --oneline -3`)를 보여 준다. 브랜치 삭제(`git branch -d`)는 사용자가 그것까지 시켰을 때만 한다.
6. 푸시는 하지 않는다. 필요하면 사용자가 직접 한다.

## 결과 모양

아래 틀로 보여 준다. 결론을 맨 위에 둔다. 내용이 없는 절은 "없음"이라고 적고 절 자체는 남긴다 (봤는데 없다는 것과 안 본 것을 구분하기 위해서다).

```markdown
# 루프 리뷰: loop/<날짜-시간> (묶음 <이름>)

## 결론: 합쳐도 됨 / 고친 뒤 합침 / 합치지 않음
한두 문장으로 이유.

### 근거 (중요한 순서)
1. [위반] ... (파일:줄)
2. [빠진 테스트] 작업 <이름>의 완료 조건 n) ...
3. [가정] ...

### 에디터에서 직접 봐야 하는 것
- 무엇을 열고, 무엇을 눌러, 무엇을 보면 되는지

### 확인하지 못한 것
- 테스트 다시 돌리지 않음 / ...

## 묶음 요약
| 작업 | 에이전트와 시도 | 바뀐 파일 | 판정 |
(main 대비 통계 한 줄)

## 작업별 확인
### <문서이름>
- 보고서와 실제 변경: 맞음 / 다름 (무엇이)
- 완료 조건과 테스트:
  | 완료 조건 | 대응하는 테스트 | 판정 |
  (판정: 있음 / 약함 / 빠짐. [컴파일] 은 "루프가 판정", [사람 확인] 은 "사람 확인"으로 적고 빠짐으로 세지 않는다)
- 하지 말 것: 지킴 / 건드림 (무엇을)
- 가정: (전부)

## 가정 모음
작업 구분 없이 전부. 사람이 판단해야 하는 것에는 표시.

## 규칙 점검
| 점검 | 결과 | 근거 |

## 테스트
다시 돌린 결과, 또는 돌리지 않은 이유.

## 다음에 할 일
합치는 명령, 또는 후속 작업으로 만들 것 목록 (make-tasks).
```

## 스크립트가 안 될 때

같은 내용을 손으로 본다 (모두 조회만 한다).

```
git for-each-ref --format="%(refname:short)" refs/heads/loop/
git merge-base --is-ancestor <루프 브랜치> main        # 종료 코드 0 이면 이미 합쳐짐
git log --oneline main..<루프 브랜치>
git diff --stat main...<루프 브랜치>
git diff --name-status main...<루프 브랜치>
git diff --name-status --diff-filter=A main...<루프 브랜치> -- docs/history   # 이번 루프가 끝낸 작업
git ls-tree -r --name-only <루프 브랜치> -- Assets      # .meta 짝 확인
```

- 상태 파일: `.loop/state.json` (`status`, `loop_branch`, `bundle`, `processed`)
- 작업별 에이전트와 시도: 작업 문서 끝의 `## 루프 기록`
- worktree 위치: `tools/loop/loop_config.json` 의 `worktree_path`

## 예행 연습

`--root <폴더>` 로 다른 폴더(복제본)를 볼 수 있다. 복제본에 가짜 `loop/*` 브랜치와 `.loop/state.json` 을 만들어 스킬을 따라가 볼 때 쓴다.
