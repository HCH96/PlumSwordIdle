# 매화검 키우기 — AI 자동 개발 루프 프로젝트 계획서

## 1. 프로젝트 개요

- **목적**: 넷마블네오 지원서(2026년 11월 24일 제출 마감)의 AI 활용 경험 소재. 출시가 목표가 아님
- **게임**: 무협 화산파 테마의 2D 픽셀아트 방치형 키우기, 제목은 '매화검 키우기'
- **엔진**: Unity (빠른 개발 우선)
- **핵심 어필 포인트**: 게임 자체보다 "AI를 개발 과정에 어떻게 넣었는가"
- **포트폴리오 구성**: 데이브릭(명세 → 목업 → 계획 → 구현 → 테스트 흐름) + 이번 게임 프로젝트

### 출발점: 데이브릭에서 느낀 병목

데이브릭 개발 시 사람이 실제로 하는 일은 요구사항 작성과 결과 확인·수정 정도였는데, 단계마다 직접 스킬을 실행하고 끝나기를 기다렸다가 다음 단계를 돌려야 했다. 이번 프로젝트는 이 단계 전환을 자동화해서, 사람은 판단이 필요한 지점에만 개입하는 구조를 만든다.

### 참고한 구조

'슬랙 → N8N → FastAPI → 메시지 큐 → 워커 AI' 형태의 자동화 아키텍처를 개인 규모로 축소했다.

| 참고 아키텍처 | 이번 프로젝트 |
| --- | --- |
| 슬랙 메시지 | 작업 문서 작성 |
| N8N + FastAPI | 파이썬 루프 스크립트 |
| 메시지 큐 | 작업 폴더 |
| 워커 AI | 클로드 코드 (사용량 한도 시 코덱스) |

자체 인프라 구축과 깃허브 액션 연동은 기간(2주)과 유니티 라이선스 설정 부담 때문에 제외한다.

## 2. 게임 설계

### 진행 방식

- 스테이지 선택창 없이 전투가 끊기지 않고 이어진다
- 화면 위쪽은 자동 전투, 아래쪽은 항상 떠 있는 강화 UI
- 몬스터 처치 시 재화 획득, 일정 수 처치 시 보스 등장
- 보스 처치 시 다음 스테이지, 실패 시 이전 스테이지로 돌아가 재화를 모으며 강해짐

### 구현 범위

**목표 범위 (필수)**

1. 자동 전투: 문하생이 자동으로 적을 공격, 처치 시 재화 드롭
2. 스테이지 진행: 일정 수 처치 후 보스, 보스 처치 시 다음 스테이지
3. 능력치 강화: 재화로 공격력·체력·공격 속도 강화
4. 저장과 오프라인 보상: 이어하기, 꺼져 있던 시간만큼 보상
5. 경지 돌파: 삼류 → 일류 → 절정 등 경지 상승 시 큰 보너스

**후보 (시간이 남으면)**

- 무공 습득 (검법·심법이 스킬처럼 자동 발동)
- 환생 (영구 보너스를 받고 처음부터)
- 장비 뽑기와 강화
- 동료 문하생 수집
- 일일 퀘스트·업적

## 4. AI 자동 개발 루프 설계

사람은 기획·승인·최종 확인만 하고, 계획·구현·테스트는 파이썬 루프 스크립트가 클로드 코드를 호출해 자동으로 진행한다. 루프는 본인 PC에서 실행한다.

이 장은 설계 배경과 큰 그림이다. 실제 동작과 설정값은 [loop.md](loop.md), 작업 문서 양식은 [task_template.md](task_template.md)가 기준이다.

### 사람과 AI의 역할 분담

- **루프 밖 (대화 단계)**: 요구사항 명세, 목업 승인은 클로드와 대화하며 끝낸다. "더 물어볼 것이 없는 문서"만 대기 폴더에 넣는다. 대기 폴더에 들어간다는 것 자체가 승인 완료다
- **루프 안 (자동 단계)**: 구현 중 애매한 점은 세 가지로 처리한다
  1. 기본 판단 규칙: "애매하면 기존 코드 스타일을 따르고, 수치는 임시값" 등을 미리 문서화
  2. 가정 기록: 사소한 것은 AI가 정하고 보고서에 기록
  3. 보류: 진행 불가능하면 질문을 남기고 보류 폴더로 이동, 디스코드 알림. 답을 달면 대기 폴더로 복귀

### 폴더 구조

| 폴더 | 경로 | 의미 |
| --- | --- | --- |
| 대기 | `tasks/todo/` | 승인된 작업 문서. 루프가 여기서 꺼냄 |
| 선행 대기 | `tasks/wait/` | 선행 작업이 끝나길 기다리는 문서. 스크립트가 옮기고, 선행 작업이 끝나면 대기로 올림 |
| 진행 중 | `tasks/doing/` | AI가 작업 중인 문서 |
| 보류 | `tasks/blocked/` | 사람의 답이 필요한 문서 (AI의 질문, 선행 작업 순환 등) |
| 완료 | `tasks/done/` | 테스트 통과 + 보고서가 붙은 문서 |
| 공용 문서 | `docs/` | 프로젝트 사양, 중요한 결정, 연결 지점(인터페이스). 색인 문서로 필요한 문서만 읽게 함 |
| 작업 기록 | `docs/history/` | 완료된 작업 문서 원본. 루프가 완료 커밋에 함께 넣음 |

문서가 폴더 사이를 이동하는 것이 곧 작업 상태다. 폴더 이동은 스크립트(또는 사람)가 하고, AI는 옮기지 않는다. `tasks/`는 깃에서 제외된 로컬 상태판이다. 작업이 끝날 때마다 AI가 공용 문서와 색인을 직접 갱신한다.

### 작업 문서 양식

| 항목 | 내용 |
| --- | --- |
| 목표 | 이 작업으로 무엇을 만드는지 한두 줄 |
| 묶음 | 한 루프에서 함께 처리할 작업 묶음. 루프 하나는 묶음 하나만 처리 |
| 선행 작업 | 먼저 끝나야 하는 작업 |
| 참고 문서 | 읽어야 할 공용 문서 |
| 요구사항 | 구체적인 동작 |
| 완료 조건 | 기계가 참/거짓을 판정할 수 있는 테스트 기준 (가장 중요) |
| 하지 말 것 | 건드리면 안 되는 범위 |

양식은 직접 쓰지 않고, 기획 대화 끝에 클로드가 이 양식으로 뽑아준다.

### 루프 스크립트 흐름 (파이썬)

1. 꺼내기: 대기 폴더에서 이번 묶음이고 선행 작업이 끝난 문서를 골라 진행 중으로 이동. 선행 작업이 안 끝난 문서는 선행 대기로 보냄
2. 브랜치 생성: 묶음마다 루프 브랜치, 작업마다 기능 브랜치
3. 계획·구현: 에이전트가 작업 문서와 필요한 공용 문서를 읽고 계획을 세운 뒤, 코드와 완료 조건에 맞는 테스트를 함께 작성. 공용 문서 갱신과 보고서 작성까지 한 번의 실행으로 처리
4. 테스트: 스크립트가 테스트 명령을 실행. 실패 시 실패 내용을 넘겨 다시 실행. 재시도 횟수 제한(5회) 초과 시 보류
5. 마무리: 스크립트가 커밋하고 루프 브랜치에 합친 뒤 완료 폴더로 이동
6. 알림 후 1번으로. 묶음이 끝나면 사람이 루프 브랜치를 확인하고 main에 직접 합침

- **작업 공간 분리**: 루프는 프로젝트 폴더 옆의 별도 git worktree에서 일한다. 사람은 프로젝트 폴더에서 유니티를 켜고 main으로 작업하고, 루프의 브랜치 전환·커밋과 부딪히지 않는다. 스크립트는 main에 커밋·병합·푸시하지 않는다.
- **실행 방식**: 한 번 돌고 끝나는 방식과 계속 켜두고 폴더를 감시하는 방식(`--watch`)을 모두 지원한다. PC 절전 모드와 클로드 코드 사용량 한도에 주의한다.
- **중단 대비**: 에이전트 시간 초과·실행 실패는 재시도에 넣고, 루프가 중간에 멈춰도 다음 실행이 남은 변경을 작업 중 커밋으로 넣고 이어간다. 네트워크 같은 일시적 오류는 감시 모드에서 간격을 두고 다시 시도한다.
- **권한**: 에이전트는 worktree 안에서만 쓰고, 깃 상태 변경과 `.env` 접근은 막는다. 코덱스는 샌드박스로, 클로드는 권한 규칙과 검사 훅으로 막는다.

### 사용량 한도 대응: 클로드 → 코덱스 전환

- 클로드 코드 실행 결과에 사용량 한도 초과가 나오면, 스크립트가 같은 작업 문서를 코덱스 CLI(ChatGPT Plus)에 넘겨 계속 진행한다
- 전환 판단은 AI가 아니라 파이썬 스크립트의 조건문으로 처리한다
- 작업 문서와 공용 문서가 모두 폴더의 파일이라, 어느 에이전트가 집어가도 같은 맥락으로 이어서 작업할 수 있다
- 클로드와 코덱스 모두 한도에 걸리면 루프를 멈추고 알림을 보낸다
- 사전 준비: 클로드 코드 CLI와 코덱스 CLI 모두 설치·로그인

### 기능 간 충돌 방지

병렬 실행은 필수가 아니며 순차 자동화로 시작한다. 다만 아래 세 가지는 "사람 없이 돌리기 위한 장치"로 넣는다.

- 연결 지점 사전 정의: 예) 재화 지급·소비 인터페이스를 먼저 정해 스테이지와 레벨업 기능이 서로의 코드를 건드리지 않게 함
- 선행 작업 명시: 스크립트가 순서를 자동으로 잡음
- 합친 후 전체 테스트: 새 기능이 기존 기능을 깨뜨리는지 확인

### 테스트

- 유니티 테스트 러너 사용: 에딧 모드(계산 검사, 빠름) + 플레이 모드(실제 실행 검사)
- 게임 로직(재화, 강화 수치, 스테이지 진행)은 순수 C#로 화면 코드와 분리해 대부분을 에딧 모드로 검사
- 루프는 유니티를 화면 없이 명령어로 실행해 테스트 결과 파일을 읽고 통과 여부 판단
- 밸런스 시뮬레이터: 화면 없이 수백 시간 플레이를 빠르게 돌려 경지 돌파·성장 곡선 점검 (시간이 되면)

### 알림

디스코드 웹훅으로 채널 네 개에 나눠 보낸다.

- 작업 완료(DONE): 무엇을 했는지 요약, 루프 종료
- 보류(BLOCKED): AI가 남긴 질문, 선행 작업 순환, 선행 작업이 아직 없음
- 루프 멈춤(STOPPED): 클로드·코덱스 모두 사용량 한도 초과, 오류, 시작 전 점검 실패
- 진행 기록(LOG): 루프·작업 시작, 재시도, 에이전트 전환, 중단 복구, 선행 대기 이동·해제

## 5. 스킬 목록

세부 명세는 추후 하나씩 디벨롭한다.

**사용자가 쓰는 스킬**

| 스킬 | 하는 일 |
| --- | --- |
| 기획 | 대화로 기능을 구체화하고 애매한 점을 질문해 정리 |
| 작업 만들기 | 기획 결과를 작업 문서 양식으로 쪼개 대기 폴더에 넣음 (선행 작업·완료 조건 포함) |
| 보류 답하기 | 보류 문서의 질문에 답하고 대기 폴더로 되돌림 |
| 리뷰 | 완료 보고서와 변경 코드를 요약해 합칠지 판단을 도움 |
| 현황 | 폴더별 작업 상태를 한눈에 정리 |

**루프가 하는 일**

처음에는 단계별 스킬 네 개로 나누려 했지만, 실제로는 스크립트의 프롬프트 하나와 프로젝트 규칙(`CLAUDE.md`, `AGENTS.md`)으로 합쳤다. 클로드와 코덱스가 같은 지시를 받는다.

| 단계 | 하는 일 | 맡는 쪽 |
| --- | --- | --- |
| 계획 | 작업 문서와 공용 문서를 읽고 구현 계획 수립 | 에이전트 |
| 구현 | 계획대로 코드와 테스트 작성 | 에이전트 |
| 마무리 | 공용 문서·색인 갱신, 보고서 작성, 가정·질문 기록 | 에이전트 |
| 테스트·수정 | 테스트 명령 실행, 실패 시 실패 내용을 넘겨 다시 실행 | 스크립트 |

**나중에 만들 스킬**

- 밸런스 점검: 밸런스 시뮬레이터를 돌리고 성장 곡선 문제를 보고. 시간이 남으면 제작

## 6. 포트폴리오 어필 포인트

- 전 프로젝트(데이브릭)에서 직접 느낀 병목을 다음 프로젝트에서 개선한 흐름
- 자동화 아키텍처를 개인 규모에 맞게 축소한 판단 (인프라·깃허브 액션을 빼을 이유 포함)

- 방치형은 수치만으로 게임을 돌려볼 수 있어, 기계가 완료를 판정하는 루프에 잘 맞는 장르라는 선택 근거
- 작업 문서·보고서·커밋 기록이 그대로 과정의 증거가 됨
