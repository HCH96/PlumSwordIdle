# AI 자동 개발 루프 (2차 버전)

`tasks/todo/`의 작업 문서를 선행 작업과 묶음 규칙에 따라 하나씩 꺼내, 루프 전용 git worktree에서 클로드 코드 CLI(사용량 한도 시 코덱스 CLI)로 계획·구현하고, 테스트를 통과하면 커밋한다. 설계 배경은 [plan.md 4장](plan.md), 작업 문서 양식은 [task_template.md](task_template.md) 참고.

## 실행

```
python tools/loop/run_loop.py           # 한 번 돌고 끝남
python tools/loop/run_loop.py --watch   # 끝나지 않고 일정 간격으로 todo 확인
```

- 종료 코드: `0` 정상, `1` 오류로 멈춤, `2` 모든 에이전트 사용량 한도로 멈춤, `3` 시작 전 점검 실패, `4` 같은 프로젝트에서 루프가 이미 실행 중이라 시작하지 않음 (아래 "실행 중 기록과 실행 로그").
- 준비물: 깃, 클로드 코드 CLI와 코덱스 CLI(둘 다 로그인), 파이썬 3.11 이상(외부 패키지 없음), 프로젝트 버전에 맞는 유니티(유니티 허브로 설치, 로그인).
- **Ctrl+C** (또는 Ctrl+Break): 첫 번째는 "지금 하던 작업까지만 끝내고 종료"(기다리는 중이면 바로 종료). 두 번째는 즉시 중단하고 상태를 건드리지 않은 채 STOPPED 알림.

### 실행 중 기록과 실행 로그

루프가 지금 돌고 있는지는 `.loop/running.json`으로 판단한다. `state.json`은 루프가 없거나(`꺼낼 작업이 없음`) `finished`여도 실행은 있을 수 있어서 따로 둔다.

```json
{
  "pid": 12345,
  "mode": "once",
  "started_at": "2026-11-13T19:35:30",
  "log_file": "run_20261113-193530.log",
  "root": "C:\\...\\PlumSwordIdle",
  "script": "C:\\...\\PlumSwordIdle\\tools\\loop\\run_loop.py"
}
```

| 키 | 내용 |
| --- | --- |
| `pid` | 루프 프로세스 번호 |
| `mode` | `once`(한 번 돌기) 또는 `watch`(감시 모드) |
| `started_at` | 시작 시각 (현지 시각, 초 단위 ISO 8601) |
| `log_file` | 이 실행의 로그 파일 이름 (`.loop/logs/` 안) |
| `root` / `script` | 사용자 폴더와 실행한 스크립트의 절대 경로 (참고용) |

- **생기는 때**: 한 번 돌기·감시 모드 모두 시작하자마자 만든다. **지우는 때**: 정상 종료, 시작 전 점검 실패, 오류, 사용량 한도, Ctrl+C 등 스크립트가 끝나는 모든 경로에서 지운다. 자기 PID의 기록만 지운다.
- **강제 종료로 남은 기록**: 다음 실행이 기록된 PID를 확인한다. 그 프로세스가 없거나, 있어도 명령줄에 `run_loop`가 없으면(PID 재사용) 남은 기록으로 보고 덮어쓴다. 실행 로그에 "남은 실행 중 기록을 덮어씀" 줄과 원래 기록이 남는다.
- **이미 실행 중**: 기록된 PID가 살아 있고 `run_loop` 프로세스면 두 번째 실행은 아무것도 하지 않고 종료 코드 `4`로 끝난다(알림 없음, 로그에 "이 프로젝트에서 루프가 이미 실행 중이라 시작하지 않음" 줄). 명령줄을 확인하지 못하면 안전하게 실행 중으로 보고, 아니라고 확신하면 `.loop/running.json`을 지우고 다시 실행한다.
- 기록은 프로젝트 폴더의 `.loop/` 안에 있으므로, 상대 경로로 실행한 루프도 어느 프로젝트 것인지 파일 위치로 정해진다.

실행 로그(`.loop/logs/run_<날짜-시간>.log`)는 항상 아래 두 줄로 시작하고 끝난다. 끝 줄이 없으면 강제 종료(창 닫힘, PC 꺼짐 등)된 실행이다.

```
[19:35:13] 실행 시작 (PID 30700, 모드 once)
...
[19:35:13] 실행 끝 (종료 코드 0)
```

종료 코드는 "실행" 절의 것과 같다. Ctrl+C 두 번(즉시 중단)도 `실행 끝 (종료 코드 1)`이 남는다.

### tasks 폴더

| 폴더 | 의미 |
| --- | --- |
| `todo` | 대기. 승인된 작업 문서 |
| `wait` | 선행 작업이 끝나길 기다리는 작업. 스크립트가 옮기고 올린다. 기능 브랜치를 만들지 않는다 |
| `doing` | 진행 중 |
| `blocked` | 사람의 답이 필요한 작업 (질문·순환 등) |
| `done` | 완료 |

## git worktree

루프는 사용자 폴더와 분리된 worktree에서만 일한다. 사용자는 프로젝트 폴더에서 유니티를 켜고 main으로 작업하고, 루프의 브랜치 전환·커밋과 서로 부딪히지 않는다.

- **위치**: `worktree_path` (기본 `../PlumSwordIdle_loop`, 프로젝트 폴더 옆).
- **생성**: 없으면 스크립트가 `git worktree add --detach <경로> main`으로 만들고, 이후 루프마다 다시 쓴다. 그 경로에 worktree가 아닌 폴더가 있으면 시작하지 않는다.
- **사용자 폴더**: 스크립트는 사용자 폴더에서 브랜치 생성(`git branch loop/<ID> main`)과 조회만 한다. 체크아웃·커밋·병합은 worktree 안에서만 한다.
- **커밋 안 된 변경 점검**은 worktree 기준이다. 사용자 폴더에 변경이 있어도 루프는 돈다.
- **루프가 끝나면** worktree를 detached 상태로 돌려놓는다 (사용자가 루프 브랜치를 합친 뒤 지울 수 있게).
- **정리** (필요할 때): 사용자 폴더에서
  ```
  git worktree remove ../PlumSwordIdle_loop
  git worktree prune
  ```
  다음 실행 때 자동으로 다시 만든다.

### 에이전트에게 작업 문서를 넘기는 방식

처리 중인 문서 1건만 worktree의 `tasks/doing/`에 복사해 넘기고(깃에서 제외된 폴더), 에이전트 실행이 끝날 때마다 보고서가 붙은 문서를 사용자 폴더로 되돌려 복사한다. 결과 파일은 worktree의 `.loop/result.json`. 그래서 에이전트는 worktree 밖에 쓸 필요가 없다.

## 브랜치 구조

```
main                      스크립트는 체크아웃·커밋·병합·푸시하지 않는다 (사용자 폴더)
 └─ loop/<날짜-시간>        루프 브랜치 (묶음 하나). 이번 묶음이 끝날 때까지 계속 쓴다
     ├─ task/<문서이름>     기능 브랜치. 완료되면 루프 브랜치에 fast-forward 병합
     └─ task/<문서이름>     보류되면 작업 중 상태를 커밋해 남겨둔다
```

- 푸시는 하지 않는다. 루프 브랜치를 main에 합치는 것은 사람이 확인하고 직접 한다.

### 루프가 끝난 뒤 main에 합치기

DONE 채널의 "루프 종료" 알림을 받으면, 먼저 `review-loop` 스킬로 묶음을 확인한다(보고서와 실제 변경, 완료 조건별 테스트, 가정, 규칙 위반). 그다음 사용자 폴더(main)에서:

```
git merge loop/<날짜-시간>
git branch -d loop/<날짜-시간>
git branch -d task/<문서이름> ...   # 필요하면
```

합치고 나면 다음 실행(감시 모드면 다음 확인 때)이 새 루프를 시작한다. 합치지 않고 버리려면 루프·기능 브랜치를 `git branch -D`로 지우고 `.loop/state.json`과 그 루프의 `tasks/done` 문서를 지운다.

### 진행 중인 루프와 완료된 루프

`.loop/state.json`의 `status`로 구분한다.

- `active`(진행 중): 다시 실행하면 새로 만들지 않고 이 루프 브랜치와 묶음을 이어서 쓴다.
- `finished`(완료): 이번 묶음의 todo·doing·blocked가 모두 비었을 때 이 상태가 되고 DONE 채널로 "루프 종료"(처리 목록, 작업 에이전트, 루프 브랜치, 남은 wait·다른 묶음)를 보낸다. **wait는 종료 조건에 들어가지 않는다.**
- 이번 묶음의 todo만 비고 보류가 남으면 루프는 `active`로 남는다(LOG).
  - **의도한 설계다.** 보류가 하나라도 남아 있으면 그 루프는 끝나지 않고, 다른 묶음의 루프도 시작되지 않는다. 묶음 하나를 사람이 한 번에 확인하고 main에 합치게 하려는 것이다.
  - 풀려면 보류 문서의 질문에 답하고 todo로 옮기거나, 그 작업을 이번 묶음에서 빼려면 문서를 `tasks/` 밖으로 옮긴다. 그러면 다음 실행에서 루프가 끝나고 "루프 종료" 알림이 온다.
- 진행 중인 루프가 아닌 `loop/*` 브랜치가 main에 합쳐져 있지 않으면 "완료됐지만 안 합쳐진 루프"로 보고 시작하지 않는다.

## 선행 작업과 wait

스크립트가 작업 문서의 `## 선행 작업` 칸을 직접 읽어 판단한다(별도 색인 없음). 양식은 [task_template.md](task_template.md).

| 경우 | 처리 |
| --- | --- |
| 선행 작업이 `없음`이거나 모두 완료 | 꺼낼 수 있음 (todo) |
| 선행 작업이 todo·doing·blocked·wait 중 한 곳에 있음 (묶음 무관) | wait로 이동, LOG |
| 선행 작업이 tasks 어디에도 없고 기록도 없음 | wait로 이동, BLOCKED "선행 작업이 아직 없음" (todo→wait로 옮길 때 한 번만) |
| 선행 작업 순환 | blocked로 이동하고 사유를 적음, BLOCKED |

- **완료 판정**: `tasks/done/<이름>.md`가 있거나 기준 브랜치에 `docs/history/<이름>.md`가 있으면 완료.
- **wait → todo**:
  - 루프 안에서 작업이 완료될 때마다, 그 작업을 기다리던 **같은 묶음**의 wait 문서 중 선행 작업이 모두 끝난 것 (루프 브랜치 기준). 다른 묶음은 다음 루프에서.
  - 새 루프를 시작할 때, 모든 wait 문서 중 **main 기준**(`docs/history`)으로 선행 작업이 끝난 것.
  - 진행 중인 루프를 이어서 실행할 때, 같은 묶음의 wait 문서 (루프 브랜치 기준).
  - 옮길 때마다 LOG.

## 묶음

- 루프 하나는 묶음 하나만 처리한다. 새 루프를 시작할 때 꺼낼 수 있는 문서 중 번호가 제일 작은 문서의 묶음을 이번 묶음으로 정하고 `state.json`의 `bundle`에 기록한다.
- 다른 묶음의 문서는 todo에 두고 다음 루프(main에 합친 뒤)에서 처리한다.
- `## 묶음` 칸이 없거나 비어 있으면 `기본` 묶음.

## 흐름 (한 번 돌기)

1. **시작 전 점검**: worktree 준비. 이전 실행이 중간에 멈춰 worktree에 변경이 남아 있으면 복구한다(아래 "중단 복구"). 복구 대상이 아닌 변경이 있거나, 완료됐지만 main에 안 합쳐진 루프 브랜치가 있으면 시작하지 않고 STOPPED.
2. **루프 브랜치 준비**: 진행 중인 루프가 있으면 worktree에서 체크아웃. 없으면 wait 재확인(main 기준) → todo 판단 → 묶음을 정하고 main에서 `loop/<날짜-시간>` 생성. 꺼낼 작업이 없으면 대기 목록을 LOG로 보내고 끝.
3. **상태 맞추기**: doing에 남은 문서는 기록 커밋이 있으면 합치고 done으로, 없으면 todo로. done인데 기록이 없으면 기능 브랜치에서 합치거나 blocked로.
4. **wait 재확인과 todo 판단** (위 "선행 작업과 wait").
5. **꺼내기**: 이번 묶음의 todo에서 번호가 제일 작은 문서를 doing으로. LOG "작업 시작".
6. **기능 브랜치**: `task/<문서이름>`을 루프 브랜치에서 만든다. 이미 있으면(보류됐던 작업) 루프 브랜치를 먼저 병합해 최신으로 맞추고, 충돌하면 기존 기능 브랜치를 지우고 새로 만든다.
7. **에이전트 실행**: 작업 문서를 처리하고 `## 보고서`(소제목 `### 한 일`, `### 바뀐 파일`, `### 가정`, `### 사람이 확인할 것`, `### 테스트 결과`. `review-loop` 스킬이 이 제목으로 찾는다)를 덧붙인 뒤 `.loop/result.json`을 쓴다. 에이전트가 규칙을 어기고 커밋하면 커밋만 되돌리고(변경은 유지) LOG.
8. **테스트**: 실패하거나 결과 파일이 없으면 실패 내용을 넘겨 다시 실행(클로드는 같은 세션 `--resume`, 코덱스는 새로 실행). LOG "재시도 n/5회째".
   - 에이전트 **시간 초과와 실행 실패**도 실패한 시도 1회로 센다. 남은 변경은 그대로 두고, 끊긴 이유를 넘겨 새 세션으로 다시 실행한다. 시간 초과 때는 에이전트가 띄운 하위 프로세스까지 끝낸다.
   - 실행 실패가 일시적 오류로 판정되면 시도 횟수에 넣지 않는다(아래 "일시적 오류").
9. **완료**: 문서에 `## 루프 기록`(작업 에이전트, 브랜치) 추가 → `docs/history/`로 복사 → 기능 브랜치에 커밋 → 루프 브랜치에 fast-forward 병합 → 성공하면 done으로 이동. DONE 알림(요약, 작업 에이전트, 브랜치). 그 작업을 기다리던 같은 묶음 wait 문서를 todo로 올린다.
10. **보류**: 에이전트가 blocked를 보고하거나 재시도 한도를 넘으면 작업 중 상태를 기능 브랜치에 커밋하고, 문서에 `## 보류 사유`(사유·질문·추천안)를 적어 blocked로. BLOCKED 알림. 다음 작업으로 계속한다.
    - 사람의 답은 문서 끝에 `## 답변 (날짜 시각)` 절로 적고(answer-blocked 스킬) todo로 옮긴다. 그러면 같은 기능 브랜치에서 작업 중 커밋을 이어서 처리한다(6번). 에이전트 프롬프트는 답변 절이 앞의 보류 사유·보고서보다 우선한다고 알린다.
11. 이번 묶음의 todo가 비면 끝("진행 중인 루프와 완료된 루프" 참고).

## 테스트

에이전트가 `done`을 보고하면 스크립트가 `test_command`를 worktree에서 실행한다. 기본값은 유니티 테스트 래퍼다.

```
{python} "{loop_tools}/run_unity_tests.py" --project .
```

- 래퍼는 유니티를 화면 없이 실행해 에딧 모드 테스트를 돌린다. `Assets/Tests/PlayMode` 폴더가 생기면 플레이 모드 테스트도 돌린다.
- 유니티는 `ProjectSettings/ProjectVersion.txt`의 버전에 맞는 유니티 허브 설치를 찾는다. 다른 위치면 `UNITY_EXE` 환경 변수나 `--unity` 인자로 알려 준다.
- 래퍼는 **사용자 폴더의 사본**을 쓴다. 에이전트가 worktree에서 래퍼를 고쳐도 판정은 바뀌지 않는다.
- 결과 파일과 유니티 로그는 worktree의 `.loop/test/`에 남는다 (깃에서 제외).

| 상황 | 판정 | 에이전트에게 넘어가는 내용 |
| --- | --- | --- |
| 모든 테스트 통과 | 통과 (종료 코드 0) | — |
| 컴파일 오류 | 실패 | 로그의 `error CS…` 줄 (파일, 줄 번호, 메시지) |
| 테스트 실패 | 실패 | 실패한 테스트 이름, 메시지, 위치 |
| 테스트가 0개 | 실패 | "테스트가 없으면 통과로 보지 않는다" |
| 시간 초과 | 실패 | 로그 위치 |
| 유니티를 못 찾음, 컴파일 오류 없이 결과 파일이 안 만들어짐 (에디터가 같은 폴더를 열고 있음, 로그인 문제 등) | 실행할 수 없음 (종료 코드 2) | 넘기지 않는다. 에이전트가 고칠 수 없는 환경 문제라 재시도하지 않고 루프를 멈춘다 (STOPPED). 원인을 해결하고 다시 실행하면 이어진다 |

`test_command`를 다른 명령으로 바꿀 때도 같은 약속을 쓴다: 종료 코드 0은 통과, 2는 환경 문제로 루프 멈춤, 그 밖은 실패로 재시도.

- worktree에는 `Library` 폴더가 없어서 **첫 실행은 전체 임포트**를 한다. 그 뒤로는 빠르다. `test_timeout_min`이 이 시간을 넘지 않게 한다.
- 유니티가 worktree에서 실행되면서 새 파일의 `.meta`를 만들고, 완료 커밋에 함께 들어간다.
- 같은 폴더를 에디터로 열어 둔 상태에서는 실행할 수 없다. worktree는 에디터로 열지 않는다.
- 래퍼를 직접 돌려 볼 때: 사용자 폴더에서 에디터를 닫고 `python tools/loop/run_unity_tests.py`.
- 에이전트도 작업 중에 worktree에서 같은 래퍼를 돌려 볼 수 있다. 코덱스 샌드박스 안에서도 유니티 테스트가 실행된다 (2026-11-13 확인, TEMP 쓰기와 네트워크가 막힌 상태).

## 감시 모드 (`--watch`)

- "한 번 돌기"를 `watch_interval_sec`마다 반복한다. 매번 상태 파일과 폴더를 다시 읽는다.
- 시작 전 점검 실패(안 합쳐진 루프, worktree 변경)는 멈추지 않고 기다린다. STOPPED 알림은 같은 내용으로 한 번만 보내고, 조건이 풀리면(main에 합치면) 다음 확인 때 새 루프를 시작한다.
- 일시적 오류는 종료하지 않고 `transient_retry_wait_sec` 뒤에 다시 시도한다. 같은 오류가 `transient_max_repeats`회 연속이면 STOPPED로 종료한다(종료 코드 1).
- 예상 못 한 오류, 모든 에이전트 한도 초과는 한 번 돌기와 같이 멈추고 종료한다. 다시 실행하면 이어진다.

## 중단 복구

루프가 작업 도중에 멈추면(예상 못 한 오류, Ctrl+C 두 번, 프로세스 강제 종료, PC 꺼짐) worktree에 커밋 안 된 변경이 남는다. 다음 실행의 시작 전 점검이 이를 복구한다.

- **복구 조건**: 진행 중인 루프가 있고, worktree가 기능 브랜치에 있고, 그 브랜치가 doing 문서나 상태 파일의 처리 중 작업과 맞을 때.
- **복구 내용**: 남은 변경을 그 기능 브랜치에 "중단 복구(작업 중 상태)" 커밋으로 넣는다. 문서는 todo로 돌아가고 같은 기능 브랜치에서 다시 처리한다. 에이전트에게는 "작업 중 커밋이 있으니 확인하고 이어서 하라"고 알린다.
- **멈춘 이유**: 스크립트가 멈출 때 `.loop/state.json`의 `last_stop`에 이유를 적어 두고, 복구 커밋 메시지와 LOG 알림 "중단 복구"에 그대로 남긴다. 강제 종료처럼 적을 틈이 없었으면 "기록 없음 (강제 종료 추정)"으로 남는다.
- **복구하지 않는 경우**: 기능 브랜치가 아닌 곳(루프 브랜치, detached)에 변경이 있거나 진행 중인 루프가 없으면 출처를 알 수 없으므로 시작하지 않는다. worktree에서 직접 확인하고 정리한다.

## 일시적 오류

에이전트 실행 실패 내용이 `transient_error_patterns`(네트워크 끊김, 서버 오류 등)에 맞으면 일시적 오류로 본다.

- 시도 횟수에 넣지 않는다. 넣으면 네트워크가 끊긴 동안 묶음의 작업이 전부 보류로 가기 때문이다.
- 작업 중 상태를 기능 브랜치에 커밋하고 문서를 todo로 되돌린 뒤 이번 실행을 접는다.
- 한 번 돌기: STOPPED를 보내고 종료(종료 코드 1). 다시 실행하면 이어진다.
- 감시 모드: LOG "일시적 오류, 다시 시도 예정 (n/3)"을 보내고 기다렸다가 다시 시도한다. 같은 오류가 연속으로 한도에 이르면 STOPPED "같은 오류가 계속됨"으로 종료한다. 중간에 한 번이라도 정상으로 돌면 횟수는 0으로 돌아간다.

## 클로드 권한

코덱스는 샌드박스가 worktree 밖 쓰기를 운영체제 수준에서 막는다. 클로드 코드는 윈도우에서 샌드박스를 지원하지 않아(2026-11 기준, WSL2에서만 가능), 아래 세 겹으로 같은 범위를 막는다.

1. **권한 모드 `dontAsk`와 허용 목록**: `claude_allowed_tools`에 없는 도구 호출은 묻지 않고 거부한다.
2. **금지 규칙**: `claude_disallowed_tools`의 깃 상태 변경 명령(Bash·PowerShell)에, 스크립트가 실행할 때 사용자 폴더와 그 `.env`의 실제 경로 규칙을 덧붙인다.
3. **검사 훅** (`tools/loop/claude_guard.py`): 모든 도구 호출 전에 실행된다. 훅이 실행되지 못하거나 검사 중 오류가 나면 그 호출은 막힌다.

| 대상 | 훅이 막는 것 |
| --- | --- |
| 파일 도구 (Read, Edit, Write, Glob, Grep 등) | worktree 밖 쓰기, 사용자 폴더 안의 모든 경로, 이름이 `.env`인 파일 |
| Bash·PowerShell | 깃 상태를 바꾸는 하위 명령(`git -C x commit` 같은 전역 옵션 포함), `.env`가 들어간 명령, 사용자 폴더 경로가 들어간 명령 |

- 훅은 **사용자 폴더의 사본**(`tools/loop/claude_guard.py`)을 쓴다. 에이전트가 worktree에서 훅 파일을 고쳐도 실행 중인 검사는 바뀌지 않는다.
- 깃 하위 명령은 이름으로만 판단해서 `git stash list`, `git branch`처럼 조회만 하는 형태도 막힌다. `status`, `diff`, `log`, `show`, `add`는 허용된다.
- 에이전트 실행 전후로 사용자 폴더의 `tasks/`와 `.env`를 비교해, 바뀌었으면 STOPPED 채널로 경고한다(루프는 계속). 실행 중에 사람이 하는 정상 작업은 경고하지 않는다:
  - `tasks/todo/`에 새 문서가 생김 (새 작업을 넣거나, 보류 문서를 todo로 옮김)
  - `tasks/blocked/` 문서가 바뀜 (보류에 답을 적음)
  - `tasks/blocked/` 문서가 사라짐 (todo로 옮기거나 `tasks/` 밖으로 버림)
  - 처리 중인 문서(doing)가 바뀌거나 사라지는 것, `.env` 변경, 그 밖의 폴더(todo·wait·done의 기존 문서) 변경은 그대로 경고한다.

**남는 한계**: 훅은 호출 내용의 글자를 검사한다. 에이전트가 스크립트 파일을 만들어 실행하고 그 스크립트가 worktree 밖에 쓰거나, 경로를 변수로 조립해 넘기면 막지 못한다. 사용자 폴더 밖의 다른 위치에 셸 명령으로 쓰는 것도 막지 못한다(파일 도구로 쓰는 것은 막는다). 완전히 막으려면 클로드를 WSL2 안에서 샌드박스를 켜고 돌려야 한다.

### 클로드가 정상 작업 중에 막힐 때 확인하는 곳

허용 목록이나 훅 규칙이 좁아서 필요한 호출이 막히면, 에이전트는 보통 그 사실을 보고서나 보류 사유에 적는다. 정확한 내용은 아래에서 확인한다.

| 확인할 곳 | 내용 |
| --- | --- |
| 실행 로그 `.loop/logs/run_<날짜-시간>.log` | "클로드 권한 거부 n건 (도구 이름…)" 줄. 거부가 있었던 실행을 찾는다 |
| `.loop/logs/guard.log` | 검사 훅이 막은 호출. 시각, 도구, 막은 이유, 명령이나 경로 |
| `.loop/logs/<문서이름>_attempt<n>_claude.out.txt` | 클로드 출력의 `permission_denials` 항목. 훅뿐 아니라 허용 목록·금지 규칙으로 거부된 호출까지 전부 들어 있다 |

고치는 방법:

- `guard.log`에는 없고 `permission_denials`에만 있으면 허용 목록 문제다. `claude_allowed_tools`에 도구를 추가한다 (예: `WebFetch`, `Bash`를 좁힌 경우 `Bash(dotnet *)`). 잠깐 시험할 때는 `loop_config.local.json`에 적는다.
- `guard.log`에 있으면 훅 규칙 문제다. `claude_guard.py`의 `GIT_BLOCKED` 목록이나 검사 함수를 고친다. 훅은 사용자 폴더의 사본을 쓰므로 main에서 고치면 다음 실행부터 적용된다.
- 금지 규칙(`claude_disallowed_tools`)에 걸린 것이면 그 규칙을 지우기 전에, 훅이 같은 것을 막고 있는지 먼저 확인한다.

## 클로드 → 코덱스 전환

- 클로드 실행이 사용량 한도로 판정되면 같은 작업 문서를 `codex exec`로 넘겨 계속한다. 작업 트리의 변경은 그대로 두고, 코덱스 프롬프트에 "이전 에이전트가 하던 변경이 남아 있다"는 안내와 마지막 실패 내용을 넣는다. 한도로 끊긴 실행은 재시도 횟수에 넣지 않는다. LOG "에이전트 전환".
- 한 번 돌기에서는 클로드가 한도에 걸리면 **그 실행의 나머지 작업은 코덱스로** 처리한다. 감시 모드에서는 `limit_retry_after_min`이 지나면 다시 클로드를 먼저 시도한다.
- 코덱스 실행: `codex exec -s workspace-write -c approval_policy=never -C <worktree> --json -o <로그> -` (+ `codex_extra_args`). 코덱스는 AGENTS.md를 읽고, 결과는 똑같이 `.loop/result.json`에 쓴다.
  - 권한: worktree 안 파일 수정만 허용(기본으로 TEMP 쓰기도 막음), 네트워크 차단, 승인 요청 없음. `--dangerously-*` 옵션은 쓰지 않는다.
  - 윈도우 확인(2026-11-12, codex-cli 0.167.2, `[windows] sandbox = "elevated"`): 워크트리 밖 사용자 폴더 쓰기는 "액세스 거부", 네트워크는 실패. TEMP 폴더는 기본으로 쓰기 허용이라 `codex_extra_args`로 막는다.
- 클로드는 "클로드 권한"의 세 겹으로, 코덱스는 샌드박스로 worktree 밖 쓰기를 막는다.
- 에이전트가 모두 한도에 걸리면 작업 중 상태를 기능 브랜치에 커밋, 문서를 todo로 되돌림, 루프 브랜치는 그대로 두고 STOPPED (종료 코드 2).
- 한도 판단: 실패한 실행은 출력 전체, 성공한 실행은 최종 결과 메시지에서 `usage_limit_patterns`의 정규식을 찾는다.

## 결과 파일 형식 (`.loop/result.json`)

```json
{"status": "done", "summary": "바뀐 내용 요약"}
{"status": "blocked", "reason": "막힌 이유", "question": "질문", "recommendation": "추천안"}
```

## 멈춤

| 상황 | 처리 |
| --- | --- |
| 모든 에이전트 사용량 한도 | 작업 중 상태를 기능 브랜치에 커밋, 문서를 todo로 되돌림, 루프 브랜치는 그대로. STOPPED |
| 일시적 오류 | 작업 중 상태를 기능 브랜치에 커밋, 문서를 todo로 되돌림. 한 번 돌기는 STOPPED, 감시 모드는 다시 시도 후 같은 오류가 계속되면 STOPPED |
| 예상 못 한 오류 | 상태를 건드리지 않고 멈춘 이유를 상태 파일에 적은 뒤 STOPPED. 다음 실행이 복구한다 ("중단 복구") |
| 시작 전 점검 실패 | 한 번 돌기: 시작하지 않고 STOPPED. 감시 모드: 기다리며 STOPPED 한 번만 |
| Ctrl+C 두 번 | 에이전트 프로세스까지 끝내고 즉시 중단, 멈춘 이유를 적고 STOPPED. 다음 실행이 복구한다 |
| 같은 프로젝트에서 루프가 이미 실행 중 | 아무것도 하지 않고 종료 코드 4. 알림 없음 ("실행 중 기록과 실행 로그") |

어느 경우든 `.loop/running.json`을 지우고 실행 로그 끝에 `실행 끝 (종료 코드 n)`을 남긴다. 프로세스가 강제 종료되면 둘 다 남지 않는다.

에이전트 시간 초과와 실행 실패는 루프를 멈추지 않는다. 실패한 시도로 세고 재시도한다 ("흐름" 8번).

## 디스코드 알림

`.env`의 키 4개로 채널을 나눈다. 값이 비어 있으면 그 채널은 건너뛴다. 전송 실패는 로그에만 남기고 루프는 계속한다.

| 키 | 보내는 내용 |
| --- | --- |
| `DISCORD_WEBHOOK_DONE` | 작업 완료(요약, 작업 에이전트, 브랜치), 루프 종료(처리 목록, 루프 브랜치, 남은 작업) |
| `DISCORD_WEBHOOK_BLOCKED` | 보류(막힌 이유, 질문, 추천안), 선행 작업 순환, 선행 작업이 아직 없음 |
| `DISCORD_WEBHOOK_STOPPED` | 사용량 한도, 오류, 일시적 오류로 멈춤, 시작 전 점검 실패, 즉시 중단, 에이전트 실행 중 사용자 폴더가 바뀜(경고) |
| `DISCORD_WEBHOOK_LOG` | 루프 시작, 작업 시작, 재시도, 에이전트 전환, 중단 복구, 일시적 오류 재시도, wait 이동·해제, 대기 목록, 감시 모드 시작·종료 |
