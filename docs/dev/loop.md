# AI 자동 개발 루프 (3차 버전)

`tasks/todo/`의 작업 문서를 선행 작업과 묶음 규칙에 따라 하나씩 꺼내, 루프 전용 git worktree에서 설정된 에이전트 CLI(기본 Claude, 사용량 한도 시 Codex)로 계획·구현한다. 작업마다 **테스트 → 관문 검사 → 교차 리뷰**를 통과해야 완료되고, 묶음이 끝나면 **증거**(`docs/evidence/`)를 남기고 **통합 브랜치**(`integration`)에 합친 뒤 곧바로 다음 묶음으로 넘어간다. 사람은 todo 가 다 비었을 때 증거를 한 번에 보고 main 에 올린다. 작업 문서 양식은 [task_template.md](task_template.md) 참고.

한눈에 보는 흐름:

```
todo ─▶ 루프 브랜치에서 작업 처리 (작업마다 테스트 → 관문 → 교차 리뷰)
            │ 묶음의 todo 가 비면
            ▼
        루프 검증 (관문 → 전체 테스트 + 화면 갈무리) ─▶ 증거 커밋 ─▶ integration 에 병합 + 태그
            │                                                              │
            └─ 떨어지면: 합치지 않고 작업을 blocked 로                        ▼
                                                                다음 묶음 (todo 가 빌 때까지 반복)
사람: 고정 SHA의 증거·코드 리뷰 ─▶ main 에서 git merge --ff-only <승인 SHA> ─▶ 푸시
```

## 실행

```
python tools/loop/run_loop.py           # 꺼낼 작업이 없을 때까지 묶음을 차례로 처리하고 끝남
python tools/loop/run_loop.py --watch   # 끝나지 않고 일정 간격으로 todo 확인
python tools/loop/run_loop.py --first codex   # 이번 실행만 코덱스에게 먼저 구현을 맡김 (--watch 와 함께 써도 됨)
```

- `--first claude|codex`: 그 에이전트를 `agents` 순서의 맨 앞으로 올린다. 나머지는 설정 순서를 따르고, 한도 전환과 교차 리뷰(구현하지 않은 쪽)도 바뀐 순서로 동작한다. 빼면 설정 순서 그대로. 실행 로그 첫머리에 "에이전트 순서"가 찍힌다.

- 종료 코드: `0` 정상, `1` 오류로 멈춤, `2` 모든 에이전트 사용량 한도로 멈춤, `3` 시작 전 점검 실패, `4` 같은 프로젝트에서 루프가 이미 실행 중이라 시작하지 않음 (아래 "실행 중 기록과 실행 로그").
- 준비물: 깃, 클로드 코드 CLI와 코덱스 CLI(둘 다 로그인), 파이썬 3.11 이상(외부 패키지 없음), 프로젝트 버전에 맞는 유니티(유니티 허브로 설치, 로그인).
- **Ctrl+C** (또는 Ctrl+Break): 첫 번째는 "지금 하던 작업까지만 끝내고 종료"(기다리는 중이면 바로 종료). 두 번째는 즉시 중단하고 상태를 건드리지 않은 채 STOPPED 알림.

### 실행 중 기록과 실행 로그

루프가 지금 돌고 있는지는 `.loop/running.json`으로 판단한다. `state.json`은 루프가 없거나(`꺼낼 작업이 없음`) `finished`여도 실행은 있을 수 있어서 따로 둔다.

```json
{
  "pid": 12345,
  "mode": "once",
  "started_at": "2026-11-13T19:35:30",
  "log_file": "run_20261113-193530.log",
  "root": "C:\\...\\PlumSwordIdle",
  "script": "C:\\...\\PlumSwordIdle\\tools\\loop\\run_loop.py"
}
```

| 키 | 내용 |
| --- | --- |
| `pid` | 루프 프로세스 번호 |
| `mode` | `once`(한 번 돌기) 또는 `watch`(감시 모드) |
| `started_at` | 시작 시각 (현지 시각, 초 단위 ISO 8601) |
| `log_file` | 이 실행의 로그 파일 이름 (`.loop/logs/` 안) |
| `root` / `script` | 사용자 폴더와 실행한 스크립트의 절대 경로 (참고용) |

- **생기는 때**: 한 번 돌기·감시 모드 모두 시작하자마자 만든다. **지우는 때**: 정상 종료, 시작 전 점검 실패, 오류, 사용량 한도, Ctrl+C 등 스크립트가 끝나는 모든 경로에서 지운다. 자기 PID의 기록만 지운다.
- **강제 종료로 남은 기록**: 다음 실행이 기록된 PID를 확인한다. 그 프로세스가 없거나, 있어도 명령줄에 `run_loop`가 없으면(PID 재사용) 남은 기록으로 보고 덮어쓴다. 실행 로그에 "남은 실행 중 기록을 덮어씀" 줄과 원래 기록이 남는다.
- **이미 실행 중**: 기록된 PID가 살아 있고 `run_loop` 프로세스면 두 번째 실행은 아무것도 하지 않고 종료 코드 `4`로 끝난다(알림 없음, 로그에 "이 프로젝트에서 루프가 이미 실행 중이라 시작하지 않음" 줄). 명령줄을 확인하지 못하면 안전하게 실행 중으로 보고, 아니라고 확신하면 `.loop/running.json`을 지우고 다시 실행한다.
- 기록은 프로젝트 폴더의 `.loop/` 안에 있으므로, 상대 경로로 실행한 루프도 어느 프로젝트 것인지 파일 위치로 정해진다.

실행 로그(`.loop/logs/run_<날짜-시간>.log`)는 항상 아래 두 줄로 시작하고 끝난다. 끝 줄이 없으면 강제 종료(창 닫힘, PC 꺼짐 등)된 실행이다.

```
[19:35:13] 실행 시작 (PID 30700, 모드 once)
...
[19:35:13] 실행 끝 (종료 코드 0)
```

종료 코드는 "실행" 절의 것과 같다. Ctrl+C 두 번(즉시 중단)도 `실행 끝 (종료 코드 1)`이 남는다.

## git worktree

루프는 사용자 폴더와 분리된 worktree에서만 일한다. 사용자는 프로젝트 폴더에서 유니티를 켜고 main으로 작업하고, 루프의 브랜치 전환·커밋과 서로 부딪히지 않는다.

- **위치**: `worktree_path` (기본 `../PlumSwordIdle_loop`, 프로젝트 폴더 옆).
- **생성**: 없으면 스크립트가 `git worktree add --detach <경로> main`으로 만들고, 이후 루프마다 다시 쓴다. 그 경로에 worktree가 아닌 폴더가 있으면 시작하지 않는다.
- **사용자 폴더**: 스크립트는 사용자 폴더에서 브랜치·태그 생성과 삭제(`git branch`, `git tag`), 조회만 한다. 체크아웃·커밋·병합은 worktree 안에서만 한다. 사용자 폴더의 작업 트리와 main 은 건드리지 않는다.
- **커밋 안 된 변경 점검**은 worktree 기준이다. 사용자 폴더에 변경이 있어도 루프는 돈다.
- **루프가 끝나면** worktree를 detached 상태로 돌려놓는다.
- **통합 브랜치는 사용자 폴더에서 체크아웃하지 않는다.** 깃은 한 브랜치를 두 곳에서 체크아웃하지 못하므로, 사용자 폴더가 `integration` 에 있으면 루프가 합치지 못하고 멈춘다.
- **정리** (필요할 때): 사용자 폴더에서
  ```
  git worktree remove ../PlumSwordIdle_loop
  git worktree prune
  ```
  다음 실행 때 자동으로 다시 만든다.

### 에이전트에게 작업 문서를 넘기는 방식

처리 중인 문서 1건만 worktree의 `tasks/doing/`에 복사해 넘기고(깃에서 제외된 폴더), 에이전트 실행이 끝날 때마다 보고서가 붙은 문서를 사용자 폴더로 되돌려 복사한다. 결과 파일은 worktree의 `.loop/result.json`. 그래서 에이전트는 worktree 밖에 쓸 필요가 없다.

## 브랜치 구조

```
main                          사람이 일하는 브랜치. 스크립트는 읽기만 한다 (사용자 폴더)
 └─ integration               통합 브랜치. 검증을 통과한 루프가 병합 커밋 하나씩으로 쌓인다
     ├─ loop/<날짜-시간>        루프 브랜치 (묶음 하나). 합쳐지면 지우고, 병합 커밋에 태그 loop-merged/<날짜-시간> 를 남긴다
     │   ├─ task/<문서이름>     기능 브랜치. 완료되면 루프 브랜치에 fast-forward 병합
     │   └─ task/<문서이름>     보류되면 작업 중 상태를 커밋해 남겨둔다
     └─ rejected/<날짜-시간>    검증에서 떨어져 합쳐지지 않은 루프 (사람이 확인한 뒤 지운다)
```

- **통합 브랜치**: 없으면 스크립트가 main 에서 만든다. 새 루프를 시작할 때마다 main 의 새 커밋(사양 문서 등)을 통합 브랜치에 합친다. 동기화한 통합 커밋은 그때의 main 을 포함하므로, main 이 이후 바뀌지 않았다면 리뷰한 대상 SHA까지 fast-forward 로 올릴 수 있다. main 과 충돌하면 시작하지 않고 STOPPED.
- **푸시와 main 병합은 하지 않는다.** 원격에 올라가는 것은 사람이 확인한 것뿐이다.
- 합쳐진 루프 브랜치와 기능 브랜치는 스크립트가 지운다. 보류된 작업의 기능 브랜치(작업 중 커밋)는 남는다.

### 사람이 확인하고 main 에 올리기

DONE 채널에 "모든 작업 끝: 확인할 차례" 알림이 오면 (또는 아무 때나) 원본 프로젝트에서:

```
python tools/skills/review_scan.py
```

출력의 리뷰 기준 SHA·대상 SHA·main SHA를 기록하고, 그 커밋의 코드와 증거를 확인한다. 스크립트는 자동 관문의 검사 함수를 작업별로 재사용하고, 각 작업 기록의 관문 예외만 적용한다. `--loop`로 한 묶음만 본 것은 부분 리뷰다. main에 올리기 전에는 아래 누적 범위를 리뷰한다.

```
python tools/skills/review_scan.py --base <리뷰 시 main SHA> --head <대상 SHA>
git show <대상 SHA>:docs/evidence/index.md
git show <대상 SHA>:docs/evidence/<루프>/report.md
```

사용자가 반영을 지시한 뒤 main HEAD가 리뷰 때와 같은지, 대상이 여전히 integration에 포함되는지 확인한다. main이 바뀌면 다시 리뷰한다. 루프가 계속 돌아도 승인한 커밋까지만 반영한다.

```
git merge --ff-only <리뷰하고 승인한 대상 SHA>
```

화면 갈무리만으로 부족하면 올린 뒤 에디터에서 플레이해 보고, 푸시는 사람이 그다음에 한다. 양쪽 스킬의 공통 사용법과 이미지 추출은 [workflow.md](workflow.md)를 따른다.

**되돌릴 때** (푸시하기 전):

| 상황 | 방법 |
| --- | --- |
| main 에 올린 뒤 루프 하나만 빼고 싶다 | main 에서 `git revert -m 1 loop-merged/<루프>`. 뒤 루프가 그 코드에 기대고 있으면 충돌한다. 그때는 아래 방법을 쓴다 |
| 어느 루프부터 뒤를 전부 버리고 싶다 (아직 main 에 안 올림) | **루프를 멈춘 뒤** `git branch -f integration loop-merged/<마지막으로 남길 루프>`. 버린 루프의 작업을 다시 하려면 그 문서를 `tasks/done/` 에서 `tasks/todo/` 로 옮긴다 (`docs/history` 기록이 통합 브랜치에서 사라졌으므로 다시 처리된다) |
| 고쳐서 쓰고 싶다 | 그대로 올리고, 고칠 것을 후속 작업 문서로 만든다 (`make-tasks`) |

되돌린 루프의 증거 폴더와 태그는 지우지 않아도 된다 (기록으로 남는다).

### 진행 중인 루프와 끝난 루프

`.loop/state.json`의 `status`로 구분한다.

- `active`(진행 중): 다시 실행하면 새로 만들지 않고 이 루프 브랜치와 묶음을 이어서 쓴다.
- `finished`(끝남): 이번 묶음의 todo·doing 이 비어 루프를 닫았다. `merged_into`(합친 브랜치), `tag`, `evidence`(보고서 경로)가 함께 적힌다. 완료된 작업이 하나도 없어 합칠 것이 없었으면 `merged_into` 가 비어 있다.
- `rejected`(합치지 않음): 합치기 전 검증에서 떨어졌다. `rejected_branch` 와 `reject_reason` 이 적힌다.
- **보류(blocked)가 남아 있어도 루프는 닫힌다.** 끝난 작업만 합치고, 보류 작업과 그것을 기다리는 작업(wait)은 사람이 답한 뒤 다음 루프에서 처리한다. 보류된 작업의 기능 브랜치는 그대로 남아, 다시 꺼낼 때 새 루프 브랜치를 합쳐 이어서 쓴다.
- 진행 중인 루프가 아닌 `loop/*` 브랜치가 통합 브랜치에 합쳐져 있지 않으면 시작하지 않는다 (STOPPED). 스크립트 밖에서 만든 브랜치이거나, `auto_merge` 가 꺼져 있어 사람이 합치길 기다리는 루프다.

## 검증

사람이 루프마다 확인하지 않으므로, 합쳐지기 전에 세 겹을 통과해야 한다. 앞의 두 겹은 스크립트가 판정하고 에이전트가 말로 넘어갈 수 없다.

| 겹 | 언제 | 누가 판정 | 떨어지면 |
| --- | --- | --- | --- |
| 테스트 | 작업마다, 그리고 루프를 합치기 직전에 전체 | 스크립트 (유니티 테스트 래퍼) | 작업: 실패 내용을 넘겨 재시도. 루프: 합치지 않음 |
| 관문 | 작업마다, 그리고 루프를 합치기 직전에 전체 | 스크립트 (`loop_gate.py`) | 작업: 위반 목록을 넘겨 재시도. 루프: 합치지 않음 |
| 교차 리뷰 | 작업마다 | 구현하지 않은 쪽 에이전트 | "고쳐라": 지적을 넘겨 재시도. "사람 필요": 보류 |

### 관문 (`tools/loop/loop_gate.py`)

두 커밋 사이의 변경을 읽어 아래를 **위반**으로 판정한다. 하나라도 있으면 합쳐지지 않는다.

| 위반 | 내용 |
| --- | --- |
| 루프 자체를 바꿈 | `tools/loop/`, `tools/skills/`, `.claude/`, `.codex/`, `.agents/`, `.github/`, `CLAUDE.md`, `AGENTS.md`, `.gitignore`, `docs/dev/loop.md`, `docs/dev/task_template.md`. 예외를 줄 수 없다 (사람이 직접 고친다) |
| 사람용 문서, 기록, 증거를 바꿈 | `docs/design/`, `docs/project/`, `docs/archive/`, `docs/history/`(스크립트가 넣는 새 기록 말고), `docs/evidence/` |
| Core 에 유니티 의존 | `Assets/Scripts/Core/` 에 `UnityEngine`, `Time.*`, `Debug.Log`, `DateTime.Now`, `Mathf` 등이 들어옴. `noEngineReferences` 가 꺼짐 |
| 어셈블리 정의를 바꿈 | `.asmdef`, `.asmref`, `csc.rsp` (관문 예외 `asmdef`) |
| 씬·프리팹·에셋 파일을 바꿈 | `.unity`, `.prefab`, `.asset` (관문 예외 `scene`) |
| ProjectSettings·Packages 를 바꿈 | (관문 예외 `settings`) |
| `.meta` 짝이 맞지 않음 | `Assets/` 아래 파일·폴더에 `.meta` 가 없거나, 짝 없는 `.meta` |
| 테스트를 지우거나 약하게 만듦 | 테스트 파일·메서드 삭제, `[Ignore]`·`[Explicit]`·`Assert.Pass`, 항상 참인 검사, 검사가 없는 테스트, 있던 테스트의 검사(Assert) 수 감소. 루프 전체를 볼 때는 작업 단계마다 비교해 앞 작업의 테스트를 뒤 작업이 약하게 만든 것도 잡는다 |
| 새 테스트가 없음 | 테스트로 판정할 완료 조건(`[테스트]`, `[플레이 모드]`, 표시 없음)이 있는데 새 테스트가 0개 |

위반은 아니지만 **확인 필요**로 남기는 것: 있던 검사 줄을 바꿈(지워진 줄과 새 줄을 함께 적는다), `docs/dev/architecture.md` 변경, 줄 끝만 바뀐 파일. 교차 리뷰어에게 넘어가고 증거에도 남는다.

**관문 예외.** 작업이 정말로 어셈블리 정의나 씬을 바꿔야 하면, 작업 문서에 `## 관문 예외` 칸을 두고 이름(`asmdef`, `scene`, `settings`)을 적는다 ([task_template.md](task_template.md)). todo 에 넣은 문서는 사람이 승인한 것이므로 그 예외를 인정한다. 스크립트는 **에이전트가 실행되기 전의 문서**에서 예외를 읽고, 에이전트가 작업 문서의 양식 칸을 고치면 원래대로 되돌린다 (보고서만 덧붙일 수 있다).

직접 관문만 돌릴 때: `python tools/loop/loop_gate.py --base <기준 SHA> --head <대상 SHA>` (종료 코드 0 위반 없음, 1 위반 있음). 이 명령은 작업별 관문 예외를 자동 복원하지 않는다. 누적 사람 리뷰는 `tools/skills/review_scan.py`를 쓴다.

### 교차 리뷰

테스트와 관문을 통과한 작업을 **구현하지 않은 쪽 에이전트**가 읽기 전용으로 확인한다 (클로드가 구현했으면 코덱스가). 다른 쪽이 사용량 한도에 걸려 있거나 `agents`에 한쪽만 설정했으면 같은 에이전트가 새 세션으로 리뷰하고, 기록에 "같은 에이전트"라고 남는다.

- 보는 것: 완료 조건마다 그것을 실제로 검사하는 테스트가 있는지, 요구사항이 빠짐없이 구현됐는지, 테스트를 구현에 맞춰 비틀지 않았는지, "하지 말 것" 침범, 화면 코드에 들어간 계산, 사양과 어긋나는 가정, 사람의 답변대로 됐는지.
- 판정은 마지막 메시지의 JSON 으로 받는다: `pass`(합쳐도 됨), `fix`(구현한 에이전트가 고칠 수 있음), `human`(사람의 결정이 필요함). 완료 조건별 테스트 표와 지적 목록이 함께 오고, 증거에 그대로 실린다.
- JSON의 필수 필드, 모든 완료 조건의 번호·원문·근거, 판정 일관성을 검사한다. 누락·중복·모순은 통과시키지 않고 리뷰 실패로 처리한다.
- `fix` 는 지적을 구현 에이전트에게 넘겨 다시 시도한다 (시도 횟수에 들어간다). `review_max_fix_rounds` 번 고친 뒤에도 `fix` 면 보류한다. 구현 에이전트는 지적이 틀렸다고 판단하면 보고서에 근거를 적을 수 있고, 리뷰어는 그것을 읽고 다시 판단한다.
- `human` 은 리뷰어의 질문과 추천안을 보류 사유로 적어 blocked 로 보낸다.
- 리뷰어 권한: 클로드는 파일을 고치는 도구를 뺀 허용 목록, 코덱스는 읽기 전용 샌드박스. 그래도 작업 폴더가 바뀌었으면 스크립트가 리뷰 전 상태로 되돌린다.
- 리뷰 실행이 두 번 실패하면(형식이 틀린 답 포함) 보류한다. 일시적 오류와 사용량 한도는 구현 에이전트와 같게 처리한다.

**한계.** 교차 리뷰는 증명이 아니다. 리뷰어도 틀리고, 두 모델이 같은 것을 놓칠 수 있다. 그래서 스크립트 판정(테스트, 관문)을 먼저 통과해야 하고, 리뷰의 판단 근거를 증거에 남겨 사람이 나중에 볼 수 있게 한다. 보기 좋은지, 수치가 재미있는지는 누구도 판정하지 않는다. 화면 갈무리와 "사람이 볼 것"을 사람이 본다.

### 루프를 합치기 전

묶음의 todo 가 비면 루프 브랜치 전체에 대해 관문을 다시 돌리고, `final_test_command` 로 전체 테스트를 돌린다 (플레이 모드 테스트가 화면 갈무리를 남긴다). 둘 다 통과하면 증거를 루프 브랜치에 커밋하고 통합 브랜치에 `--no-ff` 로 합친 뒤 병합 커밋에 태그를 붙인다. 이 테스트 실행이 만든 변경(유니티가 저절로 고친 파일)은 버린다.

떨어지면 합치지 않는다: 루프 브랜치를 `rejected/<날짜-시간>` 으로 이름을 바꿔 남기고, 그 루프의 작업 문서를 `tasks/done/` 에서 `tasks/blocked/` 로 옮기며 이유를 적는다 (BLOCKED 알림). 그 작업을 기다리던 문서는 wait 에 남고, 상관없는 묶음은 계속 진행한다. 답하고 todo 로 옮기면 처음부터 다시 처리한다.

## 증거 (`docs/evidence/`)

루프가 통합 브랜치에 합쳐질 때 스크립트가 쓰고, 그 루프의 병합에 함께 들어간다. 그래서 증거가 코드와 같은 버전으로 남는다.

| 파일 | 내용 |
| --- | --- |
| `docs/evidence/index.md` | 루프마다 한 줄: 묶음, 합친 시각, 작업 수, 테스트 통과 수, 리뷰어, 사람이 볼 것의 수, 보고서 링크 |
| `docs/evidence/<루프>/report.md` | 판정, 사람이 볼 것(완료 조건의 `[사람 확인]`, 보고서의 "사람이 확인할 것", 리뷰의 사람 지적), 에이전트가 정한 가정 전부, 화면 갈무리, 작업별 구현·리뷰 에이전트와 시도, 완료 조건별 대응 테스트 표, 관문의 확인 필요 항목, 되돌리는 명령 |
| `docs/evidence/<루프>/results.json` | 같은 내용의 원자료 (테스트 합계, 관문 결과, 리뷰 판정 원문) |
| `docs/evidence/<루프>/screenshots/` | 합치기 직전의 코드로 게임을 실행해 찍은 화면 (실행 후 1초, 10초, 30초) |

- 화면 갈무리는 플레이 모드 테스트 `Assets/Tests/PlayMode/Capture/ScreenCaptureTests.cs` 가 찍는다. 환경 변수 `PLUMSWORD_CAPTURE_DIR` 이 있을 때만 찍고(래퍼의 `--capture-dir`), 평소 테스트에서는 그냥 지나간다. 찍는 시점은 그 파일의 `Marks` 로 정한다.
- 보고서의 "완료 조건별 테스트"와 리뷰 의견은 리뷰 에이전트의 판단이고, 테스트 수·관문 결과는 스크립트가 센 것이다. 보고서에 구분해 적혀 있다.
- 에이전트는 이 폴더를 고치지 않는다 (관문 위반).

## 선행 작업과 wait

스크립트가 작업 문서의 `## 선행 작업` 칸을 직접 읽어 판단한다(별도 색인 없음). 양식은 [task_template.md](task_template.md).

| 경우 | 처리 |
| --- | --- |
| 선행 작업이 `없음`이거나 모두 완료 | 꺼낼 수 있음 (todo) |
| 선행 작업이 todo·doing·blocked·wait 중 한 곳에 있음 (묶음 무관) | wait로 이동, LOG |
| 선행 작업이 tasks 어디에도 없고 기록도 없음 | wait로 이동, BLOCKED "선행 작업이 아직 없음" (todo→wait로 옮길 때 한 번만) |
| 선행 작업 순환 | blocked로 이동하고 사유를 적음, BLOCKED |

- **완료 판정**: 통합 브랜치(루프 안에서는 루프 브랜치)에 `docs/history/<이름>.md`가 있으면 완료. `tasks/done/` 에 있어도 합쳐지지 않은 작업은 끝난 것으로 보지 않는다 (검증에서 떨어진 루프의 작업에 기대지 않게).
- **wait → todo**:
  - 루프 안에서 작업이 완료될 때마다, 그 작업을 기다리던 **같은 묶음**의 wait 문서 중 선행 작업이 모두 끝난 것 (루프 브랜치 기준). 다른 묶음은 다음 루프에서.
  - 새 루프를 시작할 때, 모든 wait 문서 중 **통합 브랜치 기준**(`docs/history`)으로 선행 작업이 끝난 것.
  - 진행 중인 루프를 이어서 실행할 때, 같은 묶음의 wait 문서 (루프 브랜치 기준).
  - 옮길 때마다 LOG.

## 묶음

- 루프 하나는 묶음 하나만 처리한다. 새 루프를 시작할 때 꺼낼 수 있는 문서 중 번호가 제일 작은 문서의 묶음을 이번 묶음으로 정하고 `state.json`의 `bundle`에 기록한다.
- 다른 묶음의 문서는 todo에 두고 다음 루프에서 처리한다. 앞 루프가 통합 브랜치에 합쳐지면 곧바로 시작한다.
- 묶음은 **증거와 되돌리기의 단위**다. 묶음 하나가 병합 커밋 하나, 증거 보고서 하나가 된다.
- `## 묶음` 칸이 없거나 비어 있으면 `기본` 묶음.

## 흐름 (루프 하나)

한 번 실행은 아래를 꺼낼 작업이 없을 때까지 되풀이한다 (감시 모드는 그 뒤에도 기다리며 계속 확인한다).

1. **시작 전 점검**: worktree 준비. 이전 실행이 중간에 멈춰 worktree에 변경이 남아 있으면 복구한다(아래 "중단 복구"). 진행 중인 루프가 없으면 통합 브랜치를 만들거나 main 의 새 커밋을 합친다. 복구 대상이 아닌 변경이 있거나, 끝났지만 통합 브랜치에 안 합쳐진 루프 브랜치가 있으면 시작하지 않고 STOPPED.
2. **루프 브랜치 준비**: 진행 중인 루프가 있으면 worktree에서 체크아웃. 없으면 wait 재확인(통합 브랜치 기준) → todo 판단 → 묶음을 정하고 통합 브랜치에서 `loop/<날짜-시간>` 생성. 꺼낼 작업이 없으면 대기 목록을 LOG로 보내고, 통합 브랜치가 main 보다 앞서 있으면 DONE "모든 작업 끝: 확인할 차례"를 한 번 보내고 끝.
3. **상태 맞추기**: doing에 남은 문서는 기록 커밋이 있으면 합치고 done으로, 없으면 todo로. done인데 기록이 없으면 기능 브랜치에서 합치거나 blocked로.
4. **wait 재확인과 todo 판단** (위 "선행 작업과 wait").
5. **꺼내기**: 이번 묶음의 todo에서 번호가 제일 작은 문서를 doing으로. LOG "작업 시작".
6. **기능 브랜치**: `task/<문서이름>`을 루프 브랜치에서 만든다. 이미 있으면(보류됐던 작업) 루프 브랜치를 먼저 병합해 최신으로 맞추고, 충돌하면 기존 기능 브랜치를 지우고 새로 만든다.
7. **에이전트 실행**: 작업 문서를 처리하고 `## 보고서`(소제목 `### 한 일`, `### 바뀐 파일`, `### 가정`, `### 사람이 확인할 것`, `### 테스트 결과`. 관문과 증거가 이 제목으로 찾는다)를 덧붙인 뒤 `.loop/result.json`을 쓴다. 에이전트가 규칙을 어기고 커밋하면 커밋만 되돌리고(변경은 유지) LOG.
8. **테스트**: 실패하거나 결과 파일이 없으면 실패 내용을 넘겨 다시 실행(클로드는 같은 세션 `--resume`, 코덱스는 새로 실행). LOG "재시도 n/5회째".
   - 에이전트 **시간 초과와 실행 실패**도 실패한 시도 1회로 센다. 남은 변경은 그대로 두고, 끊긴 이유를 넘겨 새 세션으로 다시 실행한다. 시간 초과 때는 에이전트가 띄운 하위 프로세스까지 끝낸다.
   - 실행 실패가 일시적 오류로 판정되면 시도 횟수에 넣지 않는다(아래 "일시적 오류").
   - 테스트를 통과하면 **관문**을, 그다음 **교차 리뷰**를 거친다 (위 "검증"). 관문 위반과 리뷰의 "고쳐라"도 실패한 시도로 세고, 내용을 넘겨 다시 실행한다.
9. **완료**: 문서에 `## 루프 기록`(작업 에이전트, 리뷰, 브랜치) 추가 → `docs/history/`로 복사 → 기능 브랜치에 커밋 → 루프 브랜치에 fast-forward 병합 → 성공하면 done으로 이동. DONE 알림(요약, 작업 에이전트, 리뷰, 브랜치). 그 작업을 기다리던 같은 묶음 wait 문서를 todo로 올린다.
10. **보류**: 에이전트가 blocked를 보고하거나, 재시도 한도를 넘거나, 리뷰가 사람의 결정이 필요하다고 하면 작업 중 상태를 기능 브랜치에 커밋하고, 문서에 `## 보류 사유`(사유·질문·추천안)를 적어 blocked로. BLOCKED 알림. 다음 작업으로 계속한다.
    - 사람의 답은 문서 끝에 `## 답변 (날짜 시각)` 절로 적고(answer-blocked 스킬) todo로 옮긴다. 그러면 같은 기능 브랜치에서 작업 중 커밋을 이어서 처리한다(6번). 에이전트 프롬프트는 답변 절이 앞의 보류 사유·보고서보다 우선한다고 알린다.
11. **루프 닫기**: 이번 묶음의 todo가 비면 루프 전체를 검증하고 증거를 남긴 뒤 통합 브랜치에 합친다 (위 "루프를 합치기 전", "증거"). DONE "루프 합침". 완료된 작업이 하나도 없으면 합칠 것이 없으므로 브랜치만 지운다. 그리고 곧바로 다음 묶음으로 넘어간다.

## 테스트

에이전트가 `done`을 보고하면 스크립트가 `test_command`를 worktree에서 실행한다. 기본값은 유니티 테스트 래퍼다.

```
{python} "{loop_tools}/run_unity_tests.py" --project .
```

- 래퍼는 유니티를 화면 없이 실행해 에딧 모드 테스트와 플레이 모드 테스트(`Assets/Tests/PlayMode`)를 돌린다. 플레이 모드에는 게임이 오류 없이 켜지는지 보는 `GameBootTests` 가 있어, 화면 코드의 조립 오류가 작업마다 잡힌다.
- 합계는 `.loop/test/summary.json` 에도 쓴다 (증거가 읽는다). `--capture-dir <폴더>` 를 주면 화면 갈무리를 남긴다.
- 유니티는 `ProjectSettings/ProjectVersion.txt`의 버전에 맞는 유니티 허브 설치를 찾는다. 다른 위치면 `UNITY_EXE` 환경 변수나 `--unity` 인자로 알려 준다.
- 래퍼는 **사용자 폴더의 사본**을 쓴다. 에이전트가 worktree에서 래퍼를 고쳐도 판정은 바뀌지 않는다.
- 결과 파일과 유니티 로그는 worktree의 `.loop/test/`에 남는다 (깃에서 제외).

| 상황 | 판정 | 에이전트에게 넘어가는 내용 |
| --- | --- | --- |
| 모든 테스트 통과 | 통과 (종료 코드 0) | — |
| 컴파일 오류 | 실패 | 로그의 `error CS…` 줄 (파일, 줄 번호, 메시지) |
| 테스트 실패 | 실패 | 실패한 테스트 이름, 메시지, 위치 |
| 테스트가 0개 | 실패 | "테스트가 없으면 통과로 보지 않는다" |
| 시간 초과 | 실패 | 로그 위치 |
| 유니티를 못 찾음, 컴파일 오류 없이 결과 파일이 안 만들어짐 (에디터가 같은 폴더를 열고 있음, 로그인 문제 등) | 실행할 수 없음 (종료 코드 2) | 넘기지 않는다. 에이전트가 고칠 수 없는 환경 문제라 재시도하지 않고 루프를 멈춘다 (STOPPED). 원인을 해결하고 다시 실행하면 이어진다 |

`test_command`를 다른 명령으로 바꿀 때도 같은 약속을 쓴다: 종료 코드 0은 통과, 2는 환경 문제로 루프 멈춤, 그 밖은 실패로 재시도.

- worktree에는 `Library` 폴더가 없어서 **첫 실행은 전체 임포트**를 한다. 그 뒤로는 빠르다. `test_timeout_min`이 이 시간을 넘지 않게 한다.
- 유니티가 worktree에서 실행되면서 새 파일의 `.meta`를 만들고, 완료 커밋에 함께 들어간다.
- 같은 폴더를 에디터로 열어 둔 상태에서는 실행할 수 없다. worktree는 에디터로 열지 않는다.
- 래퍼를 직접 돌려 볼 때: 사용자 폴더에서 에디터를 닫고 `python tools/loop/run_unity_tests.py`.
- 에이전트도 작업 중에 worktree에서 같은 래퍼를 돌려 볼 수 있다. 코덱스 샌드박스 안에서도 유니티 테스트가 실행된다 (2026-11-13 확인, TEMP 쓰기와 네트워크가 막힌 상태).

## 감시 모드 (`--watch`)

- "한 번 돌기"를 `watch_interval_sec`마다 반복한다. 매번 상태 파일과 폴더를 다시 읽는다.
- 시작 전 점검 실패(안 합쳐진 루프, worktree 변경)는 멈추지 않고 기다린다. STOPPED 알림은 같은 내용으로 한 번만 보내고, 조건이 풀리면 다음 확인 때 새 루프를 시작한다.
- 일시적 오류는 종료하지 않고 `transient_retry_wait_sec` 뒤에 다시 시도한다. 같은 오류가 `transient_max_repeats`회 연속이면 STOPPED로 종료한다(종료 코드 1).
- 모든 에이전트가 사용량 한도에 걸리면 종료하지 않고 `limit_retry_after_min` 분 뒤에 다시 시도한다 (STOPPED 알림은 보낸다).
- 루프 하나를 닫으면 간격을 기다리지 않고 바로 다음 묶음을 본다.
- 예상 못 한 오류는 한 번 돌기와 같이 멈추고 종료한다. 다시 실행하면 이어진다.

## 중단 복구

루프가 작업 도중에 멈추면(예상 못 한 오류, Ctrl+C 두 번, 프로세스 강제 종료, PC 꺼짐) worktree에 커밋 안 된 변경이 남는다. 다음 실행의 시작 전 점검이 이를 복구한다.

- **복구 조건**: 진행 중인 루프가 있고, worktree가 기능 브랜치에 있고, 그 브랜치가 doing 문서나 상태 파일의 처리 중 작업과 맞을 때.
- **복구 내용**: 남은 변경을 그 기능 브랜치에 "중단 복구(작업 중 상태)" 커밋으로 넣는다. 문서는 todo로 돌아가고 같은 기능 브랜치에서 다시 처리한다. 에이전트에게는 "작업 중 커밋이 있으니 확인하고 이어서 하라"고 알린다.
- **멈춘 이유**: 스크립트가 멈출 때 `.loop/state.json`의 `last_stop`에 이유를 적어 두고, 복구 커밋 메시지와 LOG 알림 "중단 복구"에 그대로 남긴다. 강제 종료처럼 적을 틈이 없었으면 "기록 없음 (강제 종료 추정)"으로 남는다.
- **복구하지 않는 경우**: 기능 브랜치가 아닌 곳(루프 브랜치, detached)에 변경이 있거나 진행 중인 루프가 없으면 출처를 알 수 없으므로 시작하지 않는다. worktree에서 직접 확인하고 정리한다.

## 일시적 오류

에이전트 실행 실패 내용이 `transient_error_patterns`(네트워크 끊김, 서버 오류 등)에 맞으면 일시적 오류로 본다.

- 시도 횟수에 넣지 않는다. 넣으면 네트워크가 끊긴 동안 묶음의 작업이 전부 보류로 가기 때문이다.
- 작업 중 상태를 기능 브랜치에 커밋하고 문서를 todo로 되돌린 뒤 이번 실행을 접는다.
- 한 번 돌기: STOPPED를 보내고 종료(종료 코드 1). 다시 실행하면 이어진다.
- 감시 모드: LOG "일시적 오류, 다시 시도 예정 (n/3)"을 보내고 기다렸다가 다시 시도한다. 같은 오류가 연속으로 한도에 이르면 STOPPED "같은 오류가 계속됨"으로 종료한다. 중간에 한 번이라도 정상으로 돌면 횟수는 0으로 돌아간다.

## 클로드 권한

코덱스는 샌드박스가 worktree 밖 쓰기를 운영체제 수준에서 막는다. 클로드 코드는 윈도우에서 샌드박스를 지원하지 않아(2026-11 기준, WSL2에서만 가능), 아래 세 겹으로 같은 범위를 막는다.

1. **권한 모드 `dontAsk`와 허용 목록**: `claude_allowed_tools`에 없는 도구 호출은 묻지 않고 거부한다.
2. **금지 규칙**: `claude_disallowed_tools`의 깃 상태 변경 명령(Bash·PowerShell)에, 스크립트가 실행할 때 사용자 폴더와 그 `.env`의 실제 경로 규칙을 덧붙인다.
3. **검사 훅** (`tools/loop/claude_guard.py`): 모든 도구 호출 전에 실행된다. 훅이 실행되지 못하거나 검사 중 오류가 나면 그 호출은 막힌다.

| 대상 | 훅이 막는 것 |
| --- | --- |
| 파일 도구 (Read, Edit, Write, Glob, Grep 등) | worktree 밖 쓰기, 사용자 폴더 안의 모든 경로, 이름이 `.env`인 파일 |
| Bash·PowerShell | 깃 상태를 바꾸는 하위 명령(`git -C x commit` 같은 전역 옵션 포함), `.env`가 들어간 명령, 사용자 폴더 경로가 들어간 명령 |

- 훅은 **사용자 폴더의 사본**(`tools/loop/claude_guard.py`)을 쓴다. 에이전트가 worktree에서 훅 파일을 고쳐도 실행 중인 검사는 바뀌지 않는다.
- 깃 하위 명령은 이름으로만 판단해서 `git stash list`, `git branch`처럼 조회만 하는 형태도 막힌다. `status`, `diff`, `log`, `show`, `add`는 허용된다.
- 에이전트 실행 전후로 사용자 폴더의 `tasks/`와 `.env`를 비교해, 바뀌었으면 STOPPED 채널로 경고한다(루프는 계속). 실행 중에 사람이 하는 정상 작업은 경고하지 않는다:
  - `tasks/todo/`에 새 문서가 생김 (새 작업을 넣거나, 보류 문서를 todo로 옮김)
  - `tasks/blocked/` 문서가 바뀜 (보류에 답을 적음)
  - `tasks/blocked/` 문서가 사라짐 (todo로 옮기거나 `tasks/` 밖으로 버림)
  - 처리 중인 문서(doing)가 바뀌거나 사라지는 것, `.env` 변경, 그 밖의 폴더(todo·wait·done의 기존 문서) 변경은 그대로 경고한다.

**남는 한계**: 훅은 호출 내용의 글자를 검사한다. 에이전트가 스크립트 파일을 만들어 실행하고 그 스크립트가 worktree 밖에 쓰거나, 경로를 변수로 조립해 넘기면 막지 못한다. 사용자 폴더 밖의 다른 위치에 셸 명령으로 쓰는 것도 막지 못한다(파일 도구로 쓰는 것은 막는다). 완전히 막으려면 클로드를 WSL2 안에서 샌드박스를 켜고 돌려야 한다.

### 클로드가 정상 작업 중에 막힐 때 확인하는 곳

허용 목록이나 훅 규칙이 좁아서 필요한 호출이 막히면, 에이전트는 보통 그 사실을 보고서나 보류 사유에 적는다. 정확한 내용은 아래에서 확인한다.

| 확인할 곳 | 내용 |
| --- | --- |
| 실행 로그 `.loop/logs/run_<날짜-시간>.log` | "클로드 권한 거부 n건 (도구 이름…)" 줄. 거부가 있었던 실행을 찾는다 |
| `.loop/logs/guard.log` | 검사 훅이 막은 호출. 시각, 도구, 막은 이유, 명령이나 경로 |
| `.loop/logs/<문서이름>_attempt<n>_claude.out.txt` | 클로드 출력의 `permission_denials` 항목. 훅뿐 아니라 허용 목록·금지 규칙으로 거부된 호출까지 전부 들어 있다 |

고치는 방법:

- `guard.log`에는 없고 `permission_denials`에만 있으면 허용 목록 문제다. `claude_allowed_tools`에 도구를 추가한다 (예: `WebFetch`, `Bash`를 좁힌 경우 `Bash(dotnet *)`). 잠깐 시험할 때는 `loop_config.local.json`에 적는다.
- `guard.log`에 있으면 훅 규칙 문제다. `claude_guard.py`의 `GIT_BLOCKED` 목록이나 검사 함수를 고친다. 훅은 사용자 폴더의 사본을 쓰므로 main에서 고치면 다음 실행부터 적용된다.
- 금지 규칙(`claude_disallowed_tools`)에 걸린 것이면 그 규칙을 지우기 전에, 훅이 같은 것을 막고 있는지 먼저 확인한다.

## 클로드 → 코덱스 전환

- 클로드 실행이 사용량 한도로 판정되면 같은 작업 문서를 `codex exec`로 넘겨 계속한다. 작업 트리의 변경은 그대로 두고, 코덱스 프롬프트에 "이전 에이전트가 하던 변경이 남아 있다"는 안내와 마지막 실패 내용을 넣는다. 한도로 끊긴 실행은 재시도 횟수에 넣지 않는다. LOG "에이전트 전환".
- 한 번 돌기에서는 클로드가 한도에 걸리면 **그 실행의 나머지 작업은 코덱스로** 처리한다. 감시 모드에서는 `limit_retry_after_min`이 지나면 다시 클로드를 먼저 시도한다.
- 코덱스 실행: `codex exec -s workspace-write -c approval_policy=never -C <worktree> --json -o <로그> -` (+ `codex_model`·`codex_effort`, `codex_extra_args`). 코덱스는 AGENTS.md를 읽고, 결과는 똑같이 `.loop/result.json`에 쓴다.
  - 권한: worktree 안 파일 수정만 허용(기본으로 TEMP 쓰기도 막음), 네트워크 차단, 승인 요청 없음. `--dangerously-*` 옵션은 쓰지 않는다.
  - 윈도우 확인(2026-11-12, codex-cli 0.167.2, `[windows] sandbox = "elevated"`): 워크트리 밖 사용자 폴더 쓰기는 "액세스 거부", 네트워크는 실패. TEMP 폴더는 기본으로 쓰기 허용이라 `codex_extra_args`로 막는다.
- 클로드는 "클로드 권한"의 세 겹으로, 코덱스는 샌드박스로 worktree 밖 쓰기를 막는다.
- 에이전트가 모두 한도에 걸리면 작업 중 상태를 기능 브랜치에 커밋, 문서를 todo로 되돌림, 루프 브랜치는 그대로 두고 STOPPED (한 번 돌기는 종료 코드 2, 감시 모드는 기다렸다가 다시 시도).
- 한도 판단: 실패한 실행은 출력 전체, 성공한 실행은 최종 결과 메시지에서 `usage_limit_patterns`의 정규식을 찾는다.

## 결과 파일 형식 (`.loop/result.json`)

```json
{"status": "done", "summary": "바뀐 내용 요약"}
{"status": "blocked", "reason": "막힌 이유", "question": "질문", "recommendation": "추천안"}
```

**한글 깨짐 검사**: 결과 파일의 글이나 이번 시도에 덧붙인 절(마지막 `## 보류 사유`·`## 답변` 뒤, `## 루프 기록` 제외)의 한글이 `?` 로 깨졌으면 받아들이지 않는다. 대체 문자(U+FFFD)가 있거나, 한글이 하나도 없는데 `??` 가 이어 나오고 `?` 가 4개 이상이면 깨진 것으로 본다. 깨진 곳을 알려 주고 다시 실행하며, 실패한 시도 1회로 센다 (blocked 보고도 깨졌으면 보류하지 않고 다시 쓰게 한다). 윈도 PowerShell 5.1 은 파이프로 넘기는 글을 ASCII 로 바꿔 한글을 `?` 로 만든다. 그래서 에이전트에게 파일 편집 도구로 UTF-8 그대로, 줄바꿈은 실제 줄바꿈으로 쓰라고 지시하고, 에이전트 프로세스에는 `PYTHONUTF8=1`, `PYTHONIOENCODING=utf-8` 을 넣는다.

## 멈춤

| 상황 | 처리 |
| --- | --- |
| 모든 에이전트 사용량 한도 | 작업 중 상태를 기능 브랜치에 커밋, 문서를 todo로 되돌림, 루프 브랜치는 그대로. STOPPED. 감시 모드는 종료하지 않고 기다렸다가 다시 시도 |
| 일시적 오류 | 작업 중 상태를 기능 브랜치에 커밋, 문서를 todo로 되돌림. 한 번 돌기는 STOPPED, 감시 모드는 다시 시도 후 같은 오류가 계속되면 STOPPED |
| 예상 못 한 오류 | 상태를 건드리지 않고 멈춘 이유를 상태 파일에 적은 뒤 STOPPED. 다음 실행이 복구한다 ("중단 복구") |
| 시작 전 점검 실패 | 한 번 돌기: 시작하지 않고 STOPPED. 감시 모드: 기다리며 STOPPED 한 번만 |
| Ctrl+C 두 번 | 에이전트 프로세스까지 끝내고 즉시 중단, 멈춘 이유를 적고 STOPPED. 다음 실행이 복구한다 |
| 같은 프로젝트에서 루프가 이미 실행 중 | 아무것도 하지 않고 종료 코드 4. 알림 없음 ("실행 중 기록과 실행 로그") |

어느 경우든 `.loop/running.json`을 지우고 실행 로그 끝에 `실행 끝 (종료 코드 n)`을 남긴다. 프로세스가 강제 종료되면 둘 다 남지 않는다.

에이전트 시간 초과와 실행 실패는 루프를 멈추지 않는다. 실패한 시도로 세고 재시도한다 ("흐름" 8번).

## 디스코드 알림

`.env`의 키 4개로 채널을 나눈다. 값이 비어 있으면 그 채널은 건너뛴다. 전송 실패는 로그에만 남기고 루프는 계속한다.

| 키 | 보내는 내용 |
| --- | --- |
| `DISCORD_WEBHOOK_DONE` | 작업 완료(요약, 작업 에이전트, 리뷰, 브랜치), 루프 합침(처리 목록, 태그, 증거 경로, 남은 보류), 모든 작업 끝: 확인할 차례(합쳐진 루프 목록, 올리는 명령) |
| `DISCORD_WEBHOOK_BLOCKED` | 보류(막힌 이유, 질문, 추천안. 리뷰가 보류시킨 것 포함), 루프를 합치지 않음(검증 실패), 선행 작업 순환, 선행 작업이 아직 없음 |
| `DISCORD_WEBHOOK_STOPPED` | 사용량 한도, 오류, 일시적 오류로 멈춤, 시작 전 점검 실패, 즉시 중단, 에이전트 실행 중 사용자 폴더가 바뀜(경고) |
| `DISCORD_WEBHOOK_LOG` | 루프 시작, 작업 시작, 재시도, 에이전트 전환, 중단 복구, 일시적 오류 재시도, wait 이동·해제, 대기 목록, 합칠 것 없이 닫은 루프, 에이전트가 고친 작업 문서·리뷰어가 고친 파일을 되돌림, 감시 모드 시작·종료 |
